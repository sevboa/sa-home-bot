- **Готово:** `pip install -e ".[dev]"`, `sa-home-bot --help`,
  `sa-home-bot --config ./config.toml --check-config` работают.

- `db/store.py` — `Store` со скелетом и методами под smoke-тест.
- **Тест:** открыть БД во временной директории, мигрировать, закрыть.

## Этап 2. Датчики (адаптер источника)

- `sensors/cpu.py` — чтение температур CPU через `psutil.sensors_temperatures()`,
  fallback на `sensors -j`. Возвращает `list[SensorReading]`.
- `sensors/disks.py` — чтение температур дисков через `smartctl -j -A`
  (подпроцесс), парсинг JSON. Автоопределение устройств или список из конфига.
- `sensors/source.py` — `SensorSource.read_cpu()/read_disks()`, всё через
  `run_in_executor`.
- **Тест:** мок `psutil` и фейковый вывод `smartctl` (фикстуры JSON) → проверка
  парсинга в `SensorReading`. Реальное железо в тестах не трогаем.

## Этап 3. Доменная логика (чистая, ядро)

- `domain/models.py` — `SensorReading`, `HealthState`, `Transition`, `Event`,
  `HealthDiff`.
- `domain/policy.py` — `ThresholdPolicy` (Protocol) + `FixedThresholdPolicy`
  (warn-порог + гистерезис).
- `domain/health.py` — `compute_health_diff(current, known)` → started / cleared
  / unchanged. Логика гистерезиса (N подряд срезов) — здесь.
- `domain/render.py` — тексты «🔥 перегрев …» и «✅ остыл …» (HTML), без БД/aiogram.
- **Тесты (полное покрытие):** новый компонент перегрелся; остыл; дребезг у
  порога не вызывает событий (гистерезис); идемпотентность повторного diff;
  рендер.

## Этап 4. Подписки

- `subscriptions/models.py` — `Subscription` (frozen, **без `quiet_hours`**),
  `accepts_event`, `allows_command`, `with_broken`.
- `subscriptions/book.py` — `SubscriptionBook.from_config`, `for_chat`,
  `validate_on_startup` (через `bot.get_chat`, пометка broken).
- **Тесты:** подписка ловит свой event_type; `"*"` ловит всё; права команд.

## Этап 5. Queue + Worker + Job-контракт

- `worker/queue.py` — `DedupQueue` (asyncio.Queue + set ключей; ключ
  освобождается на `get()`).
- `jobs/base.py` — `SensorJob` Protocol, `JobContext` (store, sensors, notifier,
  subscriptions, config), `JobResult` (метрики).
- `worker/worker.py` — `JobWorker`: get → run → запись `job_runs` → task_done;
  падение job'а не валит worker; stop-sentinel.
- **Тесты:** два одинаковых job'а → один; разные → оба; корректный shutdown.

## Этап 6. Главный job — SensorScanJob (с отправкой в лог-заглушку)

- `jobs/scan.py`: снять срез (`SensorSource`) → `FixedThresholdPolicy` →
  `HealthState` → читать известные состояния из БД → `compute_health_diff` →
  в одной транзакции записать новые состояния/переходы → собрать pending
  уведомления (по `notified_*_at IS NULL`) → разослать подписчикам → пометить
  notified только после успеха. «Остыл» — reply на «перегрев» (сохранённый
  `message_id`).
- На этом этапе `Notifier` — заглушка (пишет в лог), реальный Telegram на этапе 8.
- **Интеграционный тест:** мок `SensorSource` с двумя последовательными срезами
  (норма → перегрев → норма), проверить корректные переходы и pending-записи в БД.

## Этап 7. Scheduler

- `scheduler/setup.py` — `build_scheduler` (`AsyncIOScheduler`),
  `register_jobs`: `SensorScanJob` по `scan_cron`, housekeeping по
  `housekeeping_cron`; все `coalesce=True`, `max_instances=1`. Cron-callback
  только кладёт job в `DedupQueue`.
- **Готово:** сверху вниз в лог: cron → queue → worker → notifier-stub.

## Этап 8. Telegram-бот (реальная отправка) + системные события

- `bot/notifier.py` — реальная отправка через aiogram (ретраи 429, чанкование,

- `bot/setup.py` — сборка Bot/Dispatcher, цепочка middleware,

- `bot/handlers/basic.py` — `/start`, `/help` (контекстная по правам чата),

- `subscriptions/book.validate_on_startup` — реальный `get_chat`.
- **Тесты:** рендер/рассылка системных сообщений (мок Notifier);

## Схема БД (MVP)

```sql
-- история прогонов job'ов (для /stats)
CREATE TABLE IF NOT EXISTS job_runs (
    id           INTEGER PRIMARY KEY AUTOINCREMENT,
    job_type     TEXT NOT NULL,
    started_at   TEXT NOT NULL,
    finished_at  TEXT,
    status       TEXT NOT NULL DEFAULT 'running',  -- running/ok/error
    error        TEXT,
    metrics_json TEXT
);

-- техническое KV (last_shutdown_clean и пр.)
CREATE TABLE IF NOT EXISTS app_state (
    key   TEXT PRIMARY KEY,
    value TEXT NOT NULL
);

-- текущее состояние здоровья компонента (одна строка на component_id)
-- жизненный цикл: ok → alerting (started) → ok (cleared).
CREATE TABLE IF NOT EXISTS health_states (
    component_id          TEXT PRIMARY KEY,    -- "cpu:package" / "disk:/dev/sda"
    kind                  TEXT NOT NULL,       -- cpu / disk
    label                 TEXT NOT NULL,
    status                TEXT NOT NULL,       -- ok / alerting
    last_temperature_c    REAL,
    consecutive_count     INTEGER NOT NULL DEFAULT 0,  -- для гистерезиса
    alerting_since        TEXT,                -- когда перешёл в alerting; NULL если ok
    first_seen_at         TEXT NOT NULL,
    last_seen_at          TEXT NOT NULL,
    notified_alert_at     TEXT,                -- когда успешно разослали "перегрев"
    notified_cleared_at   TEXT                 -- когда успешно разослали "остыл"
);

-- отправленные сообщения: по одному на (component, chat, kind) —
-- нужно для reply "остыл" на исходный "перегрев".
CREATE TABLE IF NOT EXISTS health_notifications (
    component_id  TEXT NOT NULL,
    chat_id       INTEGER NOT NULL,
    kind          TEXT NOT NULL,               -- alert / cleared
    message_id    INTEGER,
    sent_at       TEXT NOT NULL,
    PRIMARY KEY (component_id, chat_id, kind),
    FOREIGN KEY (component_id) REFERENCES health_states(component_id) ON DELETE CASCADE
);
```

**Этап 2 добавит** таблицу `readings` (история показаний для `BaselinePolicy`) и
таблицу `mutes` — без изменения существующих.

## Проверка end-to-end (после MVP)

1. **Конфиг:** `sa-home-bot --config ./config.toml --check-config` — печатает
   разобранный конфиг без ошибок.
2. **Unit + lint:** `pytest` (всё зелёное), `ruff check .` (чисто).
3. **Сухой прогон с мок-датчиками:** прогнать `SensorScanJob` на фикстурах
   норма→перегрев→норма; убедиться, что в БД появились переходы и pending, а в
   логи/чат ушли «перегрев» и «остыл».
4. **Системные события:** запустить бота, отправить `/ping` и `/status`; затем
   `Ctrl+C` — должно прийти «ухожу в офлайн»; снова запустить — «снова с вами».
5. **Реальное железо:** запустить на домашней машине, нагрузить CPU
   (`stress-ng`/`yes`), убедиться, что приходит алерт и затем «остыл»; проверить
   `smartctl` доступен и температуры дисков читаются.
6. **Идемпотентность:** во время отправки убить процесс (`kill -9`), перезапустить
   — повторных дублей «перегрев» нет, недосланное досылается.

## Видение и дорожная карта: нода как основа

### Видение

Целевая картина — **рой равноправных нод** на разных машинах и ОС. Главная
сущность — **сервис ноды** (демон): он представляет машину в системе, владеет
её конфигом и **назначениями** (assignments) и супервизирует назначенные ему
службы. Базовый интерфейс управления нодой — **локальная консоль**.

Всё остальное — службы, которые нода поднимает по назначению и за здоровьем
которых следит:

- **monitor** — контроль температуры/SMART/аптайма той машины, где развёрнута
  нода (нынешняя основная функциональность бота);
- **telegram-bot** — пользовательский фронтенд: по запросу получает состояние,
  принимает события-оповещения от ноды/монитора и доставляет их в чаты;
- позже — inference, камеры/микрофоны, рендер и т.п.

Службы общаются между собой по одному протоколу (запрос состояния / команда /
событие). Тот же формат ляжет в основу межнодового общения: «локальный сосед»
и «удалённая нода» должны выглядеть для клиента одинаково. Два принципа,
закладываемых сразу:

- **Фронтенд общается только со своей локальной нодой.** Запросы к удалённым
  нодам маршрутизирует нода — у бота ровно одно подключение, адресация нод —
  забота протокола (`node_id` в конверте сообщения), а не фронтенда.
- **Доступные действия открываются динамически.** Служба в `describe` сообщает
  список своих действий (id, название, параметры); фронтенды строят UI и
  проверяют права по этому списку, ничего не хардкодя. Новая capability на
  любой ноде = новая кнопка в боте без изменения кода бота.

Как именно ноды будут находить друг друга в рое (discovery, общий секрет) —
пока сознательно не фиксируем; в коде не должно быть зашито понятие
«центральной» ноды.

Инварианты роя зафиксированы в `ARCHITECTURE.md` §11 «Правила роя»
(равноправие, прозрачная маршрутизация «спроси любого», общий каталог умений,
presence/честная деградация, одно умение — много исполнителей); принцип
деления исходников (монорепо ядра vs репозитории `sa-mod-*`) — там же, §12.

### Этап 12. Протокол v0 (локальный) — ✅ сделано

- Модуль `proto/` + короткий документ: сообщения `hello/describe` (кто ты,
  версия, capabilities **и список действий**: id, название, параметры),
  `get_state`, `command`, `event` — JSON поверх unix-сокета (на Windows позже —
  127.0.0.1 с токеном). В конверте сообщения — адресат (`node_id`/служба),
  чтобы маршрутизация к удалённым нодам легла в тот же формат.
- Клиентская и серверная обвязка на asyncio.
- **Тесты:** пара клиент↔сервер в памяти; сериализация/версионирование сообщений.

### Этап 13. Монитор — отдельный процесс — ✅ сделано (кроме describe-UI)

- Выделить из бота службу `monitor`: датчики + политики порогов + scheduler +
  своя БД (readings, health_states, SMART, downtime).
- Наружу по протоколу: `get_state` (здоровье, температуры, диски, статистика),
  `command scan_now`, поток `event`'ов (`overheat_*`, `smart_*`).
- Бот становится клиентом монитора: `/status` и алерты — через протокол, без
  прямого доступа к датчикам и БД мониторинга. Подписки, авторизация и рендер
  остаются в боте; набор действий в карточке и проверка прав строятся из
  `describe`, а не из захардкоженного списка.
- **Тесты:** монитор эмитит событие → бот-клиент получает и рассылает (в моках);
  обрыв соединения бот переживает и переподключается.
- **Остаток закрыт (2026-07-07):** кнопки действий строятся из `describe`
  (действия монитора — под `/status`, действия ноды — в разделе `/node`,
  с 2026-07-09 — `/nodes`; значения параметров — из `choices`), права —
  `действие@служба` в `allowed_commands` (голое имя — совместимость).
  Захардкожены только представления самого бота
  (подробно/статистика/отключения).

### Этап 14. Сервис ноды (супервизор) + консоль — ✅ сделано

- Демон ноды: читает конфиг назначений, запускает `monitor` и `telegram-bot`
  как дочерние процессы, следит за здоровьем (heartbeat по протоколу),
  рестартит упавших, эмитит `service_started`/`service_failed`.
- systemd-юнит остаётся один — у ноды; остальными процессами управляет она.
- Консольный клиент `nodectl`: статус ноды, список служб, start/stop/restart,
  живой хвост событий. Это базовый интерфейс управления нодой.
- **Тесты:** супервизия фейковой службы (падение → рестарт → событие).
- **Остаток (перенесён вперёд):** здоровье пока на уровне процессов
  (жив/упал/рестарт); protocol-heartbeat (hello к сокету службы, рестарт
  зависшей-но-живой) — к этапу 15, вместе с presence удалённых нод.

### Этапы 15–18. Рефокус ядра ноды: права, реальный apps, динамика, join ✅

Сделано 2026-07-14 по итогам ревизии с пользователем: проект «поплыл» в сторону
роя как самоцели (протокол, пиринг, симметричное управление), а базовые вещи
остались недоделаны — root на новой машине решался вручную и только на одной
ноде, а карточка apps выглядела как управление, но ничего не запускала.
Решили: сузить фокус на ядро (сервис ноды) и достроить три конкретные вещи, не
расширяя рой дальше вширь (Windows-нода и настоящий discovery — отложены,
см. этап 19 и «Дальше»). Полный план — в архиве сессии; здесь — что реально
сделано.

Сквозной инвариант по всем четырём этапам: **консоль (`nodectl` → своя нода) —
канонический интерфейс управления.** Любая новая возможность сначала появилась
как действие/`get_state` службы `node`/`apps` по протоколу v0; бот дёргает те
же действия той же локальной ноды, никакой обходной логики.

**Этап 15 — модель повышения привилегий + `nodectl fix`.** `Requirement`
(`utils/requirements.py`) теперь различает `missing_program` /
`unsupported_platform` / `needs_privilege` (последнее — только по факту
неудачного вызова: `looks_like_permission_error()` по stderr, репортится в
модульный `requirements_registry`). `monitor.get_state()` отдаёт структурный
`requirements: [{id,status,hint}]` вместо плоского `missing_requirements`;
`/status` в боте различает «нет программы» (подсказка apt/pacman/...) и «не
хватает прав» («выполните `nodectl fix`»). Новый `nodectl fix` (единственная
команда nodectl, которая **не** ходит по протоколу — короткоживущий процесс,
запускается вручную по SSH, зовёт настоящий интерактивный `sudo`, ничего не
хранит): идемпотентно ставит `smartmontools`, кладёт узкий `sudoers.d`-снипет
на резолвленный путь `smartctl` (плюс по одному снипету на юнит `apps`, под
этап 16), добавляет пользователя в группу `systemd-journal`. Долгоживущий
процесс ноды по-прежнему `sudo` не вызывает и прав не хранит.

**Этап 16 — реальное управление apps.** `AppsService` (`apps/service.py`)
получил `start`/`stop`/`restart` (общий параметр `name`, `sudo -n systemctl
<action> <unit>`) — карточка qBittorrent/Jellyfin в боте реально
перезапускает юнит, а не только показывает статус. Отказ по правам —
`ProtoError(needs_privilege, …)`, бот отдельно говорит «зайдите по SSH,
`nodectl fix`». Общий помощник кнопок-по-choices вынесен в
`bot/actions.py:build_choice_keyboard` и переиспользован в `node_view.py`.

**Этап 17 — динамические assignments.** `node.assignments` в TOML — теперь
стартовый набор, не единственный источник: новый `node/state.py` (`NodeState`,
атомарная запись) хранит фактический список, `NodeService.assign`/`unassign`
(права `assign@node`/`unassign@node`, кнопки «➕ Назначить»/на карточке службы
«➖ Снять») меняют его в рантайме без правки конфига и без рестарта процесса
ноды — только затронутая дочерняя служба (`Supervisor.assign/unassign`).
`nodectl assign|unassign <name>`.

**Этап 18 — присоединение к рою по токену.** Новое действие `swarm_join`
(входящее — сосед присоединяется к нам) и `join` (исходящее — `nodectl join
tcp://host:port` или `[swarm].join` при первом старте новой ноды): разовый
запрос, ответ несёт полный текущий граф пиров, присоединяющийся связывается
со всеми напрямую («один seed → полный mesh»). Замыкание сетки — третий узел,
не участвовавший в handshake напрямую, узнаёт о новичке через ретрансляцию
события `node_joined` (уже существующий канал `on_peer_event`) и
автоматически связывается сам (`node/app.py:_relay_peer_event`) — отдельного
каталога умений роя заводить не пришлось. Бот получает системное уведомление
о присоединении новой ноды (`bot/node_events.py`). `[[swarm.nodes]]`
(статический список) продолжает работать наравне с `join`.

Живая проверка (2026-07-14): две ноды на TCP-loopback, `nodeB` с одним
`[swarm].join` в конфиге видит `nodeA` и наоборот сразу после старта, без
единой ручной правки `[[swarm.nodes]]`; `nodectl assign apps` на голой ноде
поднимает реальный дочерний процесс `apps`, `PeerLink` реконнектится, как
только появляется сокет; состояние переживает проверенный рестарт процесса.

### Этап 21. Самообновление ноды через pipx ✅

Сделано 2026-07-14 по запросу пользователя: pipx (в отличие от `nodectl fix`)
не требует root — переустановку можно делать прямо из долгоживущего
процесса ноды, без отдельного процесса с интерактивным sudo. Явное
требование: **обновление не перезапускает процесс** — только доустанавливает
файлы на диске (`pipx install --force`), «увидеть» новую версию можно только
после рестарта, который выполняет человек (`restart_node`, уже был с v0.20.0).

Новый `node/update.py`: `origin_repo_url()` (PEP 610 `direct_url.json` —
откуда пакет реально поставлен; editable/не-git установка → None, умения не
объявляются вовсе), `installed_version()` (версия НА ДИСКЕ прямо сейчас,
перечитывается каждый раз), `latest_tag()` (`git ls-remote --tags`, без
токена), `pipx_reinstall()` (без sudo/TTY). Общая покомпонентная сортировка
версий вынесена в `utils/version.py:version_key` (была приватной копией в
`swarm_view.py`).

`NodeService`: `check_update@node` (сверить работающую/на диске/в
репозитории, без изменений) и `update@node` (без параметров — всегда до
последнего тега; уже свежая версия → не дёргает pipx; повторный вызов во
время выполнения → `bad_request`, защита от гонки двух `pipx install` в один
venv; переустановка — фоновая задача, ответ сразу, по завершении — событие
`update_finished` через тот же `emit`, что и `node_joined`). `get_state()`
получает дешёвое (без сети) `update.restart_required` — сравнение
работающей и установленной версии строкой. Кнопки в боте не потребовали
нового кода — это зеро-параметрические действия, автоматически попадающие в
уже существующий генерик (`node_view._simple_action_buttons`, переименован
из `_power_buttons` — там уже жил `restart_node`, название было устаревшим).
`bot/node_events.py` — ветка `update_finished` (работает и для пиров —
ретрансляция событий уже была с этапа join). `nodectl check_update`/`update`.

Живая проверка: в этом (editable) dev-чекауте `origin_repo_url()` честно
возвращает `None` — умения `check_update`/`update` не объявляются вовсе
(проверено на реальном запущенном процессе ноды), `command("check_update")`
отклоняется `unknown_action`, pipx не дёргается.

### Этап 22. Типы нод, резерв синглтонов и репликация настроек ✅

штатном завершении не приходят оповещения? Приходят только бесполезные и
неправильные».

1. **Сообщение `leave` перед остановкой.** Нода, гасясь штатно, говорит
   соседям «ухожу» — до закрытия сокетов. Даёт мгновенный и, главное,
   ТОЧНЫЙ детект: сосед знает, что это не авария, и не ждёт `down_after_s`.
   Соседи по `leave` сразу роняют свой линк (тот же путь, что
   `PeerLink.reconnect_now`) и не поднимают ложную тревогу. Windows-нода
   успевает: WinSW шлёт Ctrl+C и даёт 90 с (`stoptimeout`) — сегодня она
   молчит не из-за нехватки времени, а потому что механизма нет.
2. **Разделить «ушла» и «пропала».** Сейчас есть только `node_down`/`node_up`,
   и первое рождается лишь для `always_on`-нод через 5 минут. Нужны разные
   события и разные тексты: штатный уход (инфо, сразу), возвращение (инфо,
   сразу), пропажа без предупреждения (авария для сервера/VDS, тихо для
   рабочей станции). Отдельно чинится и то, что `node_up` сейчас приходит
   ТОЛЬКО если до этого был `node_down` — возвращение рабочей станции не
   видно вообще (`node/watch.py::check_once`, множество `_reported_down`).
3. **Тип ноды перестаёт быть единственным фильтром.** `always_on` решает,
   авария ли МОЛЧАЛИВАЯ пропажа. Штатный уход и возвращение осмысленны для
   любой ноды и не должны зависеть от `kind`.
4. **Хвост конфигурации.** Дефолт `[node].kind` — `"server"`, и незаданный
   тип делает из ноутбука «машину, обязанную быть в сети всегда» (отсюда
   бесполезные алерты про arch-t480). winpc исправлена на `workstation`
   2026-07-28; **arch-t480 ещё нет — поправить, когда машина включится**.
   Задать чужой `kind` у себя нельзя: он приезжает в `hello` соседа и
   перезаписывается (`node/watch.py::_remember_kinds`). Стоит подумать, не
   сделать ли дефолтом `workstation` — консервативнее молчать, чем шуметь.

### Этап 24. Мультиадресность линков: локальная сеть как основной путь — ✅ v0.45.0 (2026-07-28)

Сделано: `[node].listen` принимает и строку (как раньше), и список; слушатели
поднимаются независимо — ждём адрес, только пока не поднялся НИ ОДИН, дальше
нода стартует и добирает отстающий фоном (`ProtoServer._bind_later`), а
EADDRINUSE по-прежнему валит старт сразу. Нода объявляет рою в `hello`
(`ServiceInfo.endpoints`) то, что реально слушает: без unix, без loopback,
с раскрытием `0.0.0.0` в адреса интерфейсов (`proto/endpoints.advertisable`).
`PeerLink` держит список кандидатов и перебирает их — последний удачный →
LAN → оверлей (`endpoint_rank`, CGNAT 100.64/10 отделён от «просто
приватного»), потолок `CONNECT_TIMEOUT_S` на попытку; удачный адрес встаёт
первым и сохраняется в `node/state.py` (`SwarmNodeConfig.endpoints`), поэтому
выученное переживает рестарт. Обмен адресами добавлен и в `swarm_join`/`join`/
`node_joined` — поле необязательное, ноды старых версий работают как прежде.
Правило зафиксировано в ARCHITECTURE §11 п. 9.

Нюансы, найденные по дороге:
- **Отбраковка адреса по имени — мягкая.** Кандидат, ответивший чужим
  `node`, уступает любому другому, но принимается, если других нет: имя в
  `[[swarm.nodes]]` человек пишет как ему удобно, и оно законно может не
  совпадать с hostname соседа (жёсткий вариант ломал два теста и сломал бы
  прод). Loopback из чужого hello при этом не берётся никогда — по нему мы
  попадём к себе.
- **`ProtoServer.stop()` вис на соединении, принятом в момент останова**
  (в `_connections` попасть не успело — закрывать его writer было некому,
  а `wait_closed()` с Python 3.12 ждёт всех обработчиков). Лечится флагом
  `_stopping` (обработчик такого соединения сразу выходит) плюс потолок
  `CLOSE_TIMEOUT_S` на `wait_closed()`. Поймано teardown'ом теста двух нод,
  который начал виснуть от одного лишнего хопа планировщика.

Живая находка деплоя (v0.45.1, 2026-07-29): **адреса виртуальных сетей рою не
объявляем**. На winpc есть WSL и Hyper-V, и `0.0.0.0` раскрылся в том числе в
`172.18.64.1`, `172.26.48.1`, `172.30.160.1` — хост-сторону NAT-сетей
контейнеров, снаружи недостижимую никогда. У всех ранг `RANK_LAN`, сортировка
стабильная, поэтому настоящий `192.168.0.105` оказался ЧЕТВЁРТЫМ в очереди
проб: цель этапа («LAN как основной путь») деплоем не достигалась, а холодный
старт без интернета стоил бы трёх таймаутов подряд. Отличить такой адрес можно
только по имени интерфейса — диапазон у него честно приватный; фильтр
`proto/endpoints.is_virtual_iface` (vEthernet/docker/virbr/vmnet/br-/veth).
`br0` под фильтр не попадает намеренно — это обычно реальный мост LAN, в
отличие от docker'ова `br-<hash>`.

Ops — ✅ развёрнуто 2026-07-29: `listen = ["tcp://0.0.0.0:8710"]` на alfred и
winpc (v0.45.1). Проверено живьём по сокетам: `alfred → winpc` и `winpc →
alfred` идут по LAN (`192.168.0.101 ↔ 192.168.0.105`), tailscale у этой пары
остался запасным путём — ровно то, что просили. Две подробности деплоя:

- **Windows-фаервол.** Правил для ноды не было вовсе: inbound на tailscale
  пропускало правило самого Tailscale, а Ethernet на winpc классифицирован
  как `Public`, и порт 8710 там был закрыт. Заведено правило
  `sa-home-node (TCP-In)`, TCP 8710, `-RemoteAddress LocalSubnet` — сеть
  переклассифицировать в Private не потребовалось.
- **Липкий last-good.** Рабочий линк сам на LAN не переезжает: последний
  удачный адрес намеренно держится, пока отвечает (иначе рой дёргал бы
  соединения на каждом изменении). alfred переехал сам (его состояние
  чистилось от мусорных 172.x), winpc — после правки `endpoint` в
  `node-state.json`. Для новых линков и после разрыва порядок и так
  правильный: LAN раньше оверлея.

Что именно правилось (а то формулировка «добавить LAN-адрес» вводит в
заблуждение): объявление адресов автоматическое (сосед узнаёт все пути из
`hello`,
в `[[swarm.nodes]]` по-прежнему хватает одного), но объявить нода может только
то, на чём реально слушает — `advertised_endpoints()` строится из
`bound_endpoints`. Иначе рою уехал бы адрес, на котором ноды нет, и сосед
записал бы себе мёртвый путь в кандидаты. А слушать LAN-интерфейс при одном
tailscale-адресе в конфиге нельзя: `bind()` привязывается к конкретному
интерфейсу.

Поэтому правка — не «перечислить свои IP», а «разрешить слушать LAN», и она
сделана одной строкой:

```toml
listen = ["tcp://0.0.0.0:8710"]   # alfred, winpc
```

`advertisable()` сама раскроет `0.0.0.0` в адреса интерфейсов, отсеет loopback
и поставит LAN раньше CGNAT. Перечислять IP руками хуже: при смене адреса по
DHCP запись протухает, `0.0.0.0` — нет.

**Дефолтом `0.0.0.0` не сделан сознательно:** jeeves — публичный VDS, там это
означало бы выставить порт роя в интернет (токен на TCP обязателен, но
поверхность лишняя). Дома за NAT безопасно, на публичной машине нет — значит
выбор остаётся за конфигом, а на jeeves `listen` остаётся явным
tailscale-адресом. arch-t480 (ноутбук в той же локалке) тоже пока не тронут —
LAN-путь ему включается той же одной строкой, когда понадобится.

Исходная постановка (для истории):

Повод — вопрос из эксплуатации: «если есть более удобный, например локальный,
способ связи, то Tailscale между этими нодами можно не использовать; он типа

Важное уточнение к постановке: Tailscale **уже** ходит между домашними нодами

Отсюда две настоящие боли:
- нода не может подняться, пока Tailscale не отдал адрес (40–60 с после

- **без интернета домашний рой не собирается вовсе** — после перезагрузки

  друг друга, хотя LAN исправна.

1. **Нода слушает несколько адресов.** К loopback и tailscale добавляется
   локальный (или `0.0.0.0`). Безопасность: TCP и так требует `auth` токеном

2. **Обмен адресами.** Половина уже есть: `ServiceInfo.wake` возит `mac`/`ip`/

3. **Порядок проб и кэш.** Линк пробует адреса по очереди: последний удачный →
   локальный → tailscale. Known-good адрес переживает рестарт в

4. **Связь с discovery.** Пункт «настоящий discovery роя» ниже (UDP-маячок на

### Этап 25. Стенд для сетевых тестов

Повод — за одну ночь 2026-07-28 вышло пять релизов, два из которых чинили
регрессии предыдущих. Причина не в спешке, а в отсутствии места, где
воспроизводится полумёртвый TCP: правки живучести проверялись по логам прода.

Рассматривалась идея катать ноды в Docker на winpc. **Отклонено как основа**,
по двум причинам:
- Docker на Windows — это Linux-контейнеры в WSL2, и Windows-специфику в них
  не воспроизвести. А именно ею была половина находок той ночи: бинд до
  подъёма Tailscale, WinSW, сдающийся после двух ретраев, `DELAYED` autostart,
  BOM от PowerShell в конфиге.
- Сам стенд оказался бы ненадёжнее продукта: WSL-VM гаснет при простое (унося
  контейнеры), голый `dockerd` без Docker Desktop рвёт соединения — флакающие
  тесты хуже отсутствующих, они съедают доверие к зелёному прогону.

Три слоя вместо этого:

1. **Управляемая сеть в pytest** (первый и главный). Asyncio-прокси между
   клиентом и сервером, умеющий заморозиться (перестать пересылать, НЕ закрывая
   сокет — это и есть настоящий half-open), умереть молча без FIN, задерживать,
   забивать очередь отправки. Настоящий TCP, но детерминированно и за секунды.
   Покрыл бы взаимный цикл переподключений, зависание `wait_closed()`,
   неподнимающийся линк — то есть все сетевые регрессии той ночи.
   ✅ Сделано 2026-07-28: `tests/netlab.py` (freeze/drop_silently/restore/
   delay) + `tests/unit/test_netlab.py`. Нюанс реализации: слушатель прокси
   закрывается без `wait_closed()` — с Python 3.12 тот ждёт закрытия всех
   принятых соединений, а они у стенда нарочно полумёртвые.
2. **`docker compose` на Linux** (не на winpc): три ноды, реальные рестарты,
   разрывы через `docker network disconnect`. Нужен для многонодовых сценариев
   этапа 23 — кто объявитель, аренда синглтона, presence. Крутить на
   arch-t480: alfred боевой, и его двух ядер Celeron впритык.
3. **Windows-специфика — только на самой winpc**: smoke-скрипт «перезагрузись →
   нода поднялась за N секунд, порт слушается, пиры зелёные». Ровно те находки,
   что не покрываются ничем другим.

### Этап 27. Приватный вход: молчание для чужих + инвайт-коды — ✅ v0.52.0 (2026-07-29)

Две проблемы одного узла. Первая — бот отвечает **кому угодно**: `/help`,
`/ping`, `/whoami`, `/start` универсальны (`AUTHORIZATION.md` §3.1), а отказ
`⛔️ Команда недоступна в этом чате` сам по себе подтверждает, что бот живой и
права у кого-то есть. Вторая — дверь открывается только руками: правка пакета
настроек + рестарт, «привести человека» на ходу нельзя.

**Меняются два инварианта** (`AUTHORIZATION.md` §8 п. 2 и §9 «сознательно не
делается»): универсальные команды перестают быть безусловными, а набор
подписок становится частично динамическим. Оба изменения ограничены гостевым
контуром — модель прав остаётся chat-level, права по-прежнему не выдаются
командами (`/grant` не появляется), меняется только *кто вообще попадает в
книгу подписок*.

1. **Гейт молчания — один outer-middleware на `dp.update`**, до всей
   остальной цепочки. Именно на `update`, а не на `message`: путей к боту
   сегодня минимум шесть (команда, реплай в треде, любое сообщение в личке,
   упоминание в группе, `.torrent`-файл, callback-кнопка) — размазать проверку
   по ним значит однажды забыть одну. Логика: чат подписной и не broken →
   пропустить (дальше всё как сегодня, `DENIED_TEXT` остаётся, но только для
   своих без конкретного права); не подписной → апдейт может значить ровно
   одно, предъявление инвайта (`/start <код>` из deep-link или сообщение,
   равное коду), всё прочее → `return None` без единого байта наружу.
   Неверный код тоже не получает ответа: «код неверный» было бы оракулом
   «бот здесь есть».
   Побочно `/whoami` для чужих исчезает — chat_id гостя админ теперь узнаёт
   из уведомления об активации.
   Чего гейт **не** даёт: бот остаётся виден в поиске Telegram, его профиль и
   присутствие в группе видны, `getChat` работает. Молчание скрывает
   функциональность и делает бота бесполезным для чужого, но не невидимым.

2. **Гостевые подписки — отдельный пакет `instances/telegram-bot.<инст>.guests.toml`.**
   Почему не БД бота: подписки обязаны пережить переезд синглтона на резерв
   (jeeves), а БД не реплицируется — гость молча исчез бы после failover.
   Почему не дописывать в основной пакет: тот файл правит человек, и второй
   писатель в нём — это и риск затереть комментарии, и расхождение ревизий
   при одновременной правке.

   Находка: расширять механизм репликации почти не нужно. `InstanceStore`
   разбирает имя файла по **первой** точке (`instances.py::known`), поэтому

   `telegram-bot`, инстанс `alfred.guests` — `known`/`refresh_all`/`apply`
   работают как есть. Нужно только научить `ConfigReplicator` понятию
   **сателлита**: `_cares_about` считает `<инст>.guests` своим, если назначен
   базовый `<инст>`, а `_apply_to_running_service` перезапускает слот
   базового инстанса (у сателлита своего слота нет).

   Файл целиком ведёт бот (шапка «правки будут перезаписаны»), и
   перегенерируется целиком, а не дописывается — тогда отзыв гостя это просто
   перегенерация без его блока.

   В `config.py` — второй `TomlConfigSettingsSource` и **отдельное поле**
   `guest_subscriptions`: pydantic-settings не мержит списки из разных
   источников, второй `[[subscriptions]]` затёр бы владельческий. Складывает
   их `SubscriptionBook.from_config`.

3. **`SubscriptionBook` перестаёт быть иммутабельной**: `add`/`remove` в
   рантайме плюс признак происхождения подписки (`guest`). Нужно, чтобы гость
   не ждал рестарта: бот пишет пакет, сразу добавляет подписку в память и
   отвечает приветствием; рестарт от репликатора (≤30 с) подтверждает то же
   состояние, long polling за это время ничего не теряет.

4. **`/invite` — выпуск одноразового кода.** Право `invite` (админский `*`
   его уже покрывает; глобального суперадмина по-прежнему нет). В ответе —
   код, готовая ссылка `t.me/<bot>?start=КОД`, срок жизни и что код даст.
   Формат: 8 символов Crockford base32 (без `I L O U` — нет пары «1/I»,
   «0/O», код можно продиктовать голосом), показывать как `K7M4-QP2R`, при
   проверке нормализовать. 32⁸ ≈ 1.1·10¹².
   Хранение — таблица `invites` в БД бота (код, кто выпустил, TTL, кем
   погашен). Это сознательно **эфемерная** часть: при переезде бота на резерв
   непогашенные коды пропадут, что при TTL в час неважно — админ выпустит
   новый. Постоянное (подписка) живёт в пакете, эфемерное — в БД.

5. **Права гостя — из конфига, не хардкод**: `[invites] grant_commands`,
   по умолчанию `["chat@llm", "recall@memory", "remember@memory"]` —
   говорить с Альфредом и быть им запомненным; `grant_events = []` (алерты о
   температуре дисков гостю не нужны). Тулы Альфреда фильтруются подпиской
   как обычно (`AUTHORIZATION.md` §3.4), так что гость не увидит ни роя, ни
   торрентов. Память привязана к чату — в чужой чат ничего не утечёт.

6. **Приветствие пишет Альфред, а не шаблон.** Контекст: `[[people]]` по
   `username`/`telegram_id` (имя, возраст, город), recall памяти по `chat_id`
   — а в личке `chat_id == user_id`, поэтому старые знания о человеке
   находятся, даже если подписку когда-то снимали, — и кто пригласил. Если
   LLM-нода спит, сразу уходит статичный текст (будить машину ради «привет»
   не стоит), Альфред подхватывает со следующего сообщения.

7. **Антибрутфорс.** В неподписном чате не больше 5 попыток «похожего на
   код» в час, дальше игнор; при превышении — одно уведомление админу, иначе
   он о подборе не узнает. Цена молчания: гость с опечаткой не поймёт, что
   ошибся, — поэтому основной путь это ссылка, а ручной ввод кода запасной
   (для групп, куда ссылка не годится).

8. **Дверь открывается в обе стороны.** `/guests` — список гостевых подписок
   (кто, когда, кем приглашён) с кнопкой «отозвать» (перегенерация пакета без
   блока + `remove` из книги), плюс отзыв ещё не погашенного кода.

### Этап 29. Зависший останов ноды на jeeves — `restart_node` не доводит дело до конца — ✅ v0.56.0 (2026-07-30)

Найдено вживую 2026-07-30 при выкатке v0.53.1. Нода jeeves принимает
`restart_node`, пишет «запрошен само-рестарт» — и продолжает работать: процесс
не завершается. Дальше хуже: `systemctl --user restart` тоже не помогает,
юнит висит в `deactivating` около 90 секунд, пока systemd не добивает его по
`TimeoutStopSec`. После этого нода поднимается нормально и уже с новой
версией.

Почему это важно, а не косметика: `restart_node` — единственный штатный способ
применить обновление (`nodectl update` кладёт файлы на диск и процесс не
трогает) и новый пакет настроек. Пока останов зависает, **резервная нода
обновляется только руками**, а вся схема «рой обновляет себя сам» на ней не
работает.

Что известно:

- на alfred тот же путь (`os.execv` после чистого останова, `cli.py`) работает
  штатно — значит дело в состоянии именно этой ноды, а не в коде рестарта;
- у jeeves особенность конфигурации: единственная служба — `telegram-bot@alfred`
  в роли standby (не запущена), связь с роем только через tailscale, и она
  публичный VDS — то есть кандидаты на «кто не отпускает event loop» это
  PeerLink'и и серверные сокеты, а не дочерние процессы;
- похоже по природе на half-open PeerLink (память проекта, 2026-07-28):
  соединение считается живым, а запись в него не завершается;
- **важное уточнение того же дня:** сразу после того, как systemd поднял ноду
  заново, `restart_node` на jeeves отработал штатно (v0.53.1 → v0.54.0, без
  зависания). То есть ломается не механизм рестарта, а состояние ноды,
  проработавшей долго: за четверо суток аптайма в ней накапливается то, что
  не даёт останову закончиться. Это сильно сужает поиск — смотреть надо на
  ресурсы, живущие всё время работы (линки к пирам, серверные сокеты,
  фоновые задачи presence/аренды), а не на путь выключения.

**Что оказалось на самом деле.** Воспроизводить не пришлось: журнал jeeves за
тот день читается однозначно, если сравнить зависший останов с полудюжиной
удачных. В удачных за «Останов ноды...» через доли секунды идёт «Нода
остановлена чисто»; в зависшем (09:41:15) второй строки нет вовсе — и при этом
в 09:42:20, минутой позже, нода **принимает ещё один `restart_node` и отвечает
на него**. То есть event loop жив, сервер обслуживает запросы, а
последовательность останова стоит.

Так и нашлось место: `ProtoServer.stop()` закрывал клиентские соединения
циклом `writer.close(); await writer.wait_closed()` — **по очереди и без
потолка**. У полумёртвого соединения (данные в Send-Q не уходят, FIN не
подтверждается — та же природа, что у half-open PeerLink) `wait_closed()` не
возвращается никогда. Останов вставал на первом же таком соединении, а
остальные оставались открытыми, и их обработчики продолжали принимать команды
— ровно то, что видно в логе. Момент совпадения тоже объяснился: в 09:41:14
alfred попрощался (`node_leaving`) и ушёл в свой рестарт, оставив jeeves
соединение, в которое уже ничего не уходило.

Долгий аптайм, на который указывало уточнение выше, оказался не причиной, а
множителем вероятности: чем дольше нода работает, тем больше шансов, что в
момент останова хотя бы одно соединение окажется полумёртвым.

**Что сделано (v0.56.0).** Лечится не одно место, а класс: голый `await` в
пути останова — это всегда ставка на добрую волю собеседника.

- Новый `utils/shutdown.py`: `ShutdownBudget` (потолок на шаг + общий дедлайн,
  просроченный шаг называется в логе и бросается), `dump_pending_tasks()`
  (список незавершённых задач с именами — ровно та диагностика, которой не
  хватало) и `arm_hard_exit()` — сторожевой поток, добивающий процесс, если
  останов не уложился даже в бюджет. Последнее не паранойя: `asyncio.run()`
  в конце сам отменяет оставшиеся задачи и ждёт их **без потолка**, и это уже
  вне нашего кода. Нода, которая не может выключиться, хуже упавшей.
- `node/app.py`: вся последовательность останова переведена на бюджет
  (`stop_timeout_s` + 20 с; детям — их честный срок, всему остальному общий).
  Финальная строка теперь либо «остановлена чисто», либо «с оговорками» с
  перечнем не уложившихся шагов.
- `proto/server.py`: соединения закрываются параллельно и под общим потолком
  (`CLOSE_TIMEOUT_S`); то же — в `finally` обработчика соединения. Нода в
  состоянии останова больше не принимает новые команды (в логе того дня она
  успела ответить «принято» на второй `restart_node`, уже выключаясь).
- `node/supervisor.py`: `await self._task` после гашения процесса — под
  потолком с последующей отменой.
- `node/peers.py`: `stop()` выставляет `_stopping` ДО `cancel()`. Без флага
  отмена, пришедшая в окно между нашим же `reconnect_now()` и пробуждением
  `_serve`, проглатывалась как «это мы сами сбросили связь» — линк продолжал
  переподключаться, а `stop()` ждал бы задачу, которая уже не завершится.
  Воспроизвести окно снаружи детерминированно не вышло (в прод-логе оно тоже
  не отметилось), поэтому это укрепление, а не доказанная причина.
- `utils/lifespan.py`: колбэки остановки служб — тоже под потолком.

**Тесты:** `tests/unit/test_shutdown_bounded.py` — на коде до фикса падают два
из них (останов сервера с полумёртвым клиентом и останов службы с зависшей
задачей наблюдения), остальные закрывают бюджет, линк и `Lifespan`.

Про «`restart_node` честно сообщает о неудаче»: отдельного отчёта не
понадобилось. Останов теперь всегда доходит до конца, а если какой-то шаг не
уложился — это видно в логе поимённо, вместе с дампом висящих задач.

### Этап 30. Отложенная задача провалилась: прогрев llm и живучесть бэкенда — ✅ v0.55.0 (2026-07-30)

Живой сбой 2026-07-30, 18:20–18:36: задача по расписанию (id=27) не
выполнилась, пользователь получил «Альбегт: не удалось найти Альфреда».
Разбор показал **две независимые причины**, и обе стоит закрыть.

1. **Бэкенд llm лежал, и поднять его было некому.** Ollama на winpc живёт в
   контейнере внутри WSL-дистрибутива `Docker`, а тот оказался в состоянии
   `Stopped` (WSL усыпляет простаивающий дистрибутив сам). Служба `llm` при
   этом выглядела совершенно здоровой: процесс жив, `describe` отвечает,
   presence не показывает сна, в `nodectl status` она `🟢 running` —
   ломается только сам запрос (`HTTP 000`, соединение рвётся мгновенно).
   `wsl -d Docker` поднял всё за секунды, и Ollama сразу ответила.
   Нужно: перед тем как признать прогрев неудачным, служба llm проверяет свой
   бэкенд (`/api/version`) и, если он мёртв, пробует поднять его сама
   (запустить дистрибутив, при необходимости `docker start ollama`), и только
   потом сдаётся. Это то же «нода лечит себя», что и WoL для спящей машины.
2. **Прогрев сдаётся раньше, чем модель успевает загрузиться.**
   `wake_core.WARMUP_TIMEOUT_S = 180 с`, а замеренный сегодня холодный старт
   `Qwen3.6-35B-A3B` с диска — **201 с** (`load_duration` из ответа Ollama).
   То есть даже при живом бэкенде первый прогрев после долгого простоя
   обречён, а на второй попытке (через 30 с) модель ещё грузится. Поднять
   таймаут до величины, согласованной с `[llm].request_timeout_s` (360 с), и
   сделать настраиваемым — железо у нод разное, и 35B на HDD/SSD грузится
   по-разному.

Побочно всплыло и стоит поправить заодно:

- **Провал задачи не диагностируется.** Пользователю уходит «Альбегт», админу
  — ничего; причину пришлось искать в логах трёх машин. Нужно уведомление
  админам с исходом (`unreachable` / `warmup_failed`) и последней ошибкой —
  как это уже сделано для сбоев `/ai` (`notify_admins`).
- **`nodectl call` жёстко ждёт 10 секунд**, поэтому долгие действия (`warmup`,
  `ask`) им не проверить — консоль отвечает «нода не ответила вовремя», хотя
  служба работает. Добавить `--timeout`.

**Что сделано (v0.55.0).** Потолок прогрева поднят 180 → 360 с и вынесен в
`[llm].warmup_timeout_s` (железо у нод разное); на сроке задачи он ужимается
до остатка `FIRE_GRACE_S` — ждать дольше бюджета бессмысленно. Причина отказа
в прогреве больше не теряется: `try_warmup` пишет в лог код и текст ошибки
службы, поэтому разбор начинается и заканчивается на той ноде, которая
прогрев запрашивала. Провал задачи уходит админам отдельным уведомлением с
причиной (`notify_admins`), пользователю по-прежнему только «Альбегт». У
`nodectl call` появился `--timeout`.

Самолечение бэкенда трогать не пришлось — оно уже есть и вызывается
(`ollama.ensure_running` на каждую попытку в `_post_with_retry`, включая
`preload`). Сегодняшний сбой оно не вытянуло, а причина этого не была видна
ниоткуда — ровно то, что чинит логирование выше. Если повторится, в логе
ноды-инициатора будет точный ответ службы; тогда и решать, чего не хватает
`ensure_running` (прав у Windows-службы на `wsl`, времени, или дистрибутив
не поднимается вовсе).

### Этап 31. Discovery роя: ноды находят друг друга в локалке сами — ✅ v0.57.0 (2026-07-31)

Повод не только в удобстве первой установки. Выученные адреса переживают
рестарт (`node/state.py`), но не переживают **смену адреса**: если DHCP выдал
соседу другой IP, пока тот был недоступен, линк добросовестно долбится в
мёртвый адрес, и чинить это приходилось руками. Не теория — адрес самой
alfred за время проекта уехал дважды (`192.168.0.102` в CLAUDE.md,
`192.168.0.100` в заметках, реально `192.168.0.101`).

Реализован эскиз 2026-07-11 (см. «Дальше» ниже — пункт закрыт этим этапом):
UDP-маячок на порту 32167, запрос broadcast'ом, ответ unicast'ом, оба
подписаны HMAC от `[swarm].token`. Формат кадра и правила дропа —
`PROTOCOL.md`, раздел «Маячок discovery».

Решения, которые стоит держать в голове:

1. **Маячок не строит рой — он зовёт `join`.** Найдя незнакомую ноду,
   discovery вызывает тот же `NodeService.join()`, что и `nodectl join`.
   Оттуда бесплатно достаётся всё остальное: полный граф пиров за один
   round-trip, персистентность и событие `node_joined`, которым рой
   достраивает сетку. Маячок заменяет человека, вводившего команду, а не
   механизм — поэтому и своего события у него нет.
2. **Переезд лечится отдельной веткой.** Известный пир с мёртвым линком и
   новым адресом в ответе не «присоединяется» заново: линк доучивается
   (`learn_endpoints` → сохранение через `on_endpoints`) и будится
   `reconnect_now`, не дожидаясь очередного цикла проб.
3. **Кадеданс адаптивный.** `active_interval_s` (15 с), пока пиров нет вовсе
   или хоть один недоступен, `idle_interval_s` (300 с) в спокойном рое. Эфир
   почти всегда чист, а сосед находится за секунды именно тогда, когда его и
   ищут.
4. **Занятый UDP-порт ноду не роняет** (в отличие от TCP-listen, где
   EADDRINUSE фатален): маячок — удобство поверх работающего транспорта.
   Пустой `[swarm].token` — то же самое: подписывать нечем, discovery молчит.
5. **Порт неотличим от закрытого.** Пакет с неверной подписью, чужой версией
   или мусором дропается без ответа и без записи в лог на INFO.

Границы: broadcast живёт в своём сегменте и через tailscale не проходит —
jeeves (публичный VDS) по-прежнему добавляется статикой. Это принято
осознанно, а не забыто.

Побочно закрыт давний ручной шаг: `deploy/install-node.ps1` теперь сам ставит
правила фаервола Windows — и на UDP-маячок, и на TCP-порт ноды (на втором уже
спотыкались при выкатке этапа 24).

**Тесты:** `tests/unit/test_discovery.py` — кадр и подпись (подмена любого
поля, чужой токен, чужая версия, мусор, переросший лимит кадр), кадеданс,
сквозной обмен двух маячков на 127.0.0.1 с портом от ОС, replay чужого nonce,
эхо собственного broadcast'а, переезд адреса, занятый порт, выключенный
маячок. Стенд `tests/netlab.py` здесь не применим — он про TCP-поток.

**Живая находка на smoke-прогоне.** Цель рассылки бралась из ЛОКАЛЬНОГО порта
сокета, а не из `[swarm.discovery].port`. В проде оба равны 32167, поэтому
ошибка была бы не видна до первой ноды с другим портом — вылезла только
потому, что тестовый экземпляр брал порт у ОС. Закрыта тестом
`test_broadcast_goes_to_the_swarm_port_not_our_own`.

**Долг: две проверки на двух нодах не сделаны.** На 2026-07-31 проверено
только то, что видно с одной машины: юнит-тесты, живой broadcast на LAN
alfred (запрос → ответ → `join`) и работающий маячок на боевой ноде. Обмен
между РАЗНЫМИ нодами не проверялся — winpc спала и отстаёт по версии, а
маячок есть только с v0.57.0. Когда winpc будет включена:

1. разбудить её (`/wake` в боте: MAC живёт в кэше бота, `[wake].mac` в
   конфиге alfred пуст намеренно, ARP-запись к тому времени протухает);
2. `nodectl -n winpc check_update` → `update`; рестартует она себя сама
   задачей планировщика;
3. **находит ли себя рой сам:** убрать winpc из `data/node-state.json` на
   alfred (в `[[swarm.nodes]]` её нет — она известна только по состоянию),
   рестарт ноды → пир winpc должен появиться сам, в логе `discovery: нашли
   ноду winpc (…), присоединились`;
4. **лечится ли переезд:** подменить адрес winpc в состоянии на заведомо
   мёртвый, дождаться разрыва линка → линк обязан переехать на найденный
   маячком адрес (`discovery: у пира winpc новый адрес …`) без рук.

Пока это не пройдено, считать этап проверенным «на одной машине»: путь
запрос→ответ→`join` живой, а вот что сосед на Windows отвечает и что правило
фаервола из `install-node.ps1` действительно открывает UDP — не подтверждено.

### Этап 32. Организация интерфейса бота: витрина умений вместо списка команд

Курс на разделы `/skills` и `/nodes` был намечен ещё при пивоте к рою, но
доведён только наполовину: `/nodes` есть (этап 20), витрины умений нет.
Разбор текущего состояния (2026-07-31) показывает, что это не косметика.

**Что не так сейчас.**

1. **UI бота — это админка нод, а продукт живёт в разговоре.** Меню и
   разделы показывают ноды, службы, приложения. А `torrents`, `memory`,
   `net` (поиск), `tasks` (напоминания) в интерфейсе не представлены вовсе —
   ими пользуются только через `/alfred`. Кто не знает, что рой это умеет,
   не узнает: `/help` перечисляет команды, а не умения.
2. **Меню смешивает уровни.** В одном плоском списке — приложения из
   `describe` службы `apps`, сводка роя, вызов Альфреда и служебные
   `/help`/`/ping`/`/whoami`. Плюс восемь скрытых команд (`/status`,
   `/status_full`, `/stats`, `/downtime`, `/scan_now`, `/wake`, `/invite`,
   `/guests`), которые нельзя найти, не зная о них.
3. **Каждое новое умение требует своего хендлера в боте.** Единственный
   динамический источник UI — `describe` службы `apps`
   (`menu.build_menu_commands`). `torrents` пришлось писать руками
   (`handlers/torrents.py`: приём файла, кнопки `save_path` из `choices`),
   `invites` — тоже. Служба `vpn` (этап 33) станет третьей по счёту, и это
   уже система, а не совпадение.
4. **Параметризованные действия доступны только там, где кто-то написал под
   них форму.** Из меню они исключены сознательно (живой баг 2026-07-18:
   `/start` без «какое приложение» падал), но общего механизма сбора
   параметров нет — есть частный случай в `torrents`.
5. **Диалоги с Альфредом никак не управляются.** Реализованный `/ai`
   (LLM_INTEGRATION_PLAN.md §6) — это голая reply-цепочка: ответил на
   сообщение бота — продолжение, написал обычным текстом — новый вызов.
   Ни списка прошлых диалогов, ни возможности вернуться к теме без
   пролистывания истории чата, ни явного «начать заново» — тред живёт,
   пока собеседник помнит, на какое сообщение отвечать.

**Решения.**

1. **Три явных уровня входа вместо одного плоского списка**: разговор
   (`/alfred`) — для людей; `/skills` — витрина умений роя; `/nodes` —
   админка железа. Меню Telegram сокращается до этих трёх плюс
   универсальные; всё остальное — внутри разделов.
2. **`/skills` строится из `describe`, а не из кода бота.** Раздел
   перечисляет службы роя, которые чат вправе видеть (право
   `действие@служба` у хотя бы одного действия), с одной строкой на службу:
   иконка, заголовок, где выполняется, живость. Новая служба в рое = новая
   строка в витрине без единой правки бота — ровно та же логика, что уже
   работает для `apps`, распространённая на все службы.
3. **Заголовок и иконка службы — в `describe`, не в словаре бота.** Иначе
   витрина превратится в захардкоженную таблицу, и решение 2 обнулится.
   Расширить `describe` полем вида `ui` (`title`, `icon`, порядок); старая
   служба без него получает имя как заголовок — совместимость по тому же
   правилу, что `kind` у дисков в этапе 20.
4. **Общий сборщик форм для параметризованных действий.** Действие с
   `params` открывает диалог: `choices` — кнопками, свободный ввод — ответом
   текстом, всегда есть «отмена». Состояние держать в памяти процесса по
   образцу `PendingTorrents` — `callback_data` ограничен 64 байтами, тащить
   параметры в него нельзя. После этого `torrents` теряет свой частный код,
   а `vpn` получает рабочий UI бесплатно.
5. **Навигация ссылками-командами расширяется на умения**: `/skill_<служба>`
   рядом с существующими `/node_<id>` и `/svc_<нода>_<служба>`. Приём себя
   оправдал: текст кликается, не занимает место кнопками и переживает
   пересылку.
6. **`/help` переписать из «списка команд» в «что я умею»**, по правам и с
   группировкой на те же три уровня. Список команд оставить хвостом для
   админа.
7. **Настройка оповещений — не делаем вовсе.** Обсуждали mute по типу
   события / по ноде — пользователь решил проще: кто хочет отдохнуть от
   сообщений, мьютит сам чат бота штатными средствами Telegram. Это
   закрывает вопрос без единой строки кода: `/mute` из ARCHITECTURE.md §4.7
   («управляющие команды, позже») с повестки снят, писать не нужно.
8. **Диалоги с Альфредом — через Telegram Private Chat Topics, не через
   самодельный `/dialogs` — ✅ сделано 2026-08-01.** Пользователь включил в
   BotFather режим топиков для личных чатов (Bot API 9.4, февраль 2026): бот
   заводит в личном чате «форумные» топики тем же `createForumTopic`, что и
   в супергруппах, а список тредов и переключение между ними рисует сам
   клиент Telegram — то, что решение 5 просило, только бесплатно и без
   единой кнопки в нашем коде. Подробный разбор находки — отдельным блоком в
   LLM_INTEGRATION_PLAN.md §6 (обновление сессии 2026-08-01).
   **Живой спайк на боевом боте (owner-чат) прошёл чисто:** `createForumTopic`,
   две отправки подряд через `message_thread_id`, `editMessageText` внутри
   топика — всё сработало с первой попытки. Регрессия Bot API 10.0
   (`sendMessage` с `message_thread_id` → `400: message thread not found`),
   которую ловили другие проекты, на этом боте НЕ воспроизвелась — `awg`-стиль
   обхода через `direct_messages_topic_id` не понадобился, `message_thread_id`
   работает напрямую.
   **Реализация** — `bot/handlers/ai.py`: `_dialogue_id_for(message)` =
   `message.message_thread_id or message.message_id`. Внутри топика
   `dialogue_id` — id топика: любое сообщение в нём (не только reply) —
   продолжение того же диалога, `/alfred` внутри топика не сбрасывает
   контекст (в отличие от `/alfred` вне топика, который начинает диалог
   заново, как и раньше). Вне топика — поведение не тронуто: reply-цепочка
   (`AiReplyContinuation`) и «всегда новый тред без reply» (живой баг
   2026-08-01) работают как до этой правки — топики строго опциональное
   расширение, не замена. `aiogram` сам пробрасывает `message_thread_id` в
   `message.answer()`/`.reply()` (подтверждено чтением исходников
   установленной версии 3.29.1) — отдельно поддерживать адрес ответа не
   нужно. Заодно — typing-индикатор (`send_chat_action`) теперь показывается
   в конкретном топике, а не в основном треде чата (просьба пользователя).
   **Тесты:** `tests/unit/test_ai_handler.py` — dialogue_id по топику, а не
   по message_id; `/alfred` внутри топика продолжает существующую историю
   (и с текстом, и голый); свежий топик даёт тот же результат, что и вне
   топика; `on_private_message` внутри топика копится без reply (в отличие
   от чата без топиков); typing-индикатор несёт правильный
   `message_thread_id` (и `None` вне топика). Полный прогон: 1210 passed.

**Границы.** Раздел `/skills` — витрина и точка входа, а не замена
разговору: сложные просьбы («поставь качаться, когда место освободится»)
по-прежнему через Альфреда. Меню Telegram остаётся плоским списком (это
ограничение платформы) — иерархию даёт не оно, а разделы. Полноценный
Telegram Mini App (Web App) с настоящими выпадающими списками осознанно
не рассматриваем — новый публичный домен, TLS и параллельная модель
авторизации (`initData`) не окупаются на масштабе «несколько человек»,
когда решения 4 и 8 закрывают ровно те же боли нативными средствами.

**Тесты:** сборка витрины по правам (служба без единого доступного действия
не показывается); служба без поля `ui` в `describe` (совместимость);
сборщик форм — `choices`, свободный ввод, отмена, чужой callback, протухшее
состояние; `/skill_<служба>` для несуществующей и недоступной службы;
после спайка решения 8 — раздельно тестируемая привязка `dialogue_id` к
топику против reply-цепочки (fallback), включая случай отправки в топик,
которого больше нет (`400`, топик удалён).

### Этап 33. VPN на jeeves: доступ по заявке из бота и учёт лимитов — ✅ код v0.65.0 (2026-08-03), деплой на jeeves ещё предстоит

**Реализовано в коде** (пакет `src/sa_home_bot/vpn/`, тесты
`tests/unit/test_vpn_service.py`, `test_vpn_apk.py`, `test_vpn_handler.py`,
дополнения `test_tools.py`/`test_fixups.py`): служба `vpn` (реконсайлер,
сэмплер трафика, issue/reissue/revoke/usage/peers/set_quota), команда `/vpn`
и кнопки в боте, LLM-тул `vpn` (Альфред), `node/fixups.py::AWG_SUDOERS`,
ops-скрипт `deploy/setup-awg-jeeves.sh`. Решения пользователя 2026-08-03,
уточняющие/заменяющие пункты 6 и «открытые вопросы» ниже:

- **Квоты — самообслуживание до потолка.** База 500 ГБ/мес; гость сам
  добавляет по +100 ГБ кнопкой «➕100 ГБ» сколько угодно раз, пока сумма
  месяца не достигла 1 ТБ (`self_ceiling_gb`); выше — заявка админу
  (`request_extra`/`resolve_request`, кнопки approve/deny в уведомлении).
  Добавки не переносятся на новый месяц (база сбрасывается на 500 ГБ).
- **Предупреждение — по абсолютному остатку, не проценту.** На последних
  20 ГБ (`warn_remaining_gb`), не на 80% как в исходном пункте 6 — так порог
  не гуляет вместе с лимитом после докупок.
- **Лимит канала VDS известен: 10 ТБ/мес** (`node_limit_gb`) — снимает
  открытый вопрос «(в)» ниже. При приближении — `vpn_node_quota_warning`
  админам (гостей не касается).
- **Приложение — официальный AmneziaWG, не полный клиент AmneziaVPN.**
  ~17 МБ (репозиторий `amnezia-vpn/amneziawg-android`) укладывается в лимит
  Telegram-бота на файл (50 МБ); полный клиент 68–78 МБ — нет. Кэш на
  jeeves, свежесть по GitHub API на каждый запрос (`vpn/apk.py`); доставка —
  метаданные и, при первом разе, чанки через рой (протокол ограничен 1 МиБ
  на сообщение), дальше — по сохранённому Telegram `file_id` без повторной
  передачи байтов.
- **Перевыпуск = «п.7» исходного плана.** «Получить новый доступ»
  (`reissue`) снимает старый пир с интерфейса и БД (`status='expired'`,
  история расхода сохраняется за старым peer_id) и тут же выпускает новый
  тем же `device_label`.
- **Реконсайлер, а не разрозненные add/remove** (архитектурное решение,
  выходящее за рамки исходных 9 пунктов): желаемое состояние интерфейса
  (БД) сверяется с фактическим (`awg show <iface> transfer`) при старте
  службы и на каждом тике сэмплера — закрывает разом восстановление после
  ребута jeeves, месячную разблокировку 1-го числа и снятие пира при
  блокировке одним и тем же кодом.

**Не реализовано этой сессией:** сам ops-прогон `setup-awg-jeeves.sh` на
jeeves (установка `amneziawg-go`/`amneziawg-tools`, генерация серверных
ключей и параметров обфускации, `[node].assignments += "vpn"`, `nodectl
fix`) — скрипт готов, но выполняется вручную по SSH, не автоматически.

jeeves — публичный VDS с белым IP `78.31.250.224`, и это единственная нода
роя, до которой достаёт кто угодно снаружи. Задача: раздавать VPN-доступ
людям (себе и приглашённым), выдавая конфиг прямо из бота, и следить за
лимитами трафика.

**Назначение подтверждено (2026-08-01): личный выходной узел в открытый
интернет** — для устойчивого доступа к сервисам, доступность которых из
дома нестабильна (мессенджеры, видеосервисы и т.п.). Это снимает вопрос (а)
из прежней версии плана (не вход в домашнюю сеть — её уже закрывает
Tailscale) и решает развилку по протоколу: раз важна именно устойчивость
соединения, а не только шифрование канала, **вариант «ванильный WG сейчас,
обфускация потом» отклонён** — провайдерский DPI умеет детектировать и
рвать по сигнатуре именно WireGuard-хендшейка, так что закладывать это
первым шагом — гарантированно переделывать после первого же разрыва.

**Что на jeeves уже есть (проверено 2026-07-31):** Debian 12, ядро 6.1,
`iptables` (backend nf_tables), sudo без пароля (`/etc/sudoers.d/90-sevboa`),
3 vCPU / 2.9 ГиБ / 25 ГБ. Ванильный модуль `wireguard` в ядре уже есть, но
он не понадобится — идём через AmneziaWG (решение 1 ниже), собранный отдельно.
Нужно: собрать/поставить `amneziawg-go` + `amneziawg-tools` (`awg`,
`awg-quick`; готовых `.deb` под bookworm нет, ставить из исходников или
готового бинарника проекта), включить `net.ipv4.ip_forward` (сейчас `0`) и
NAT. Текущий расход канала — около 4 ГБ за 6 суток (rx 3.4 ГБ, tx 0.6 ГБ),
то есть весь трафик VPN будет виден на фоне почти пустого счётчика.

**Решения.**

1. **AmneziaWG вместо ванильного WireGuard, с самого начала.** Тот же
   протокол WG, но с обфускацией заголовков хендшейка (случайный паддинг,
   маскировка сигнатуры Ijk/Ijc и т.д.) — под DPI выглядит не как
   распознаваемый WG-трафик, а как непонятный UDP-шум. Это форк userspace
   (`amneziawg-linux-kernel-module` есть и как модуль ядра, но проще и
   надёжнее ставить userspace-реализацию `awg`/`amneziawg-go` через их
   репозиторий — в Debian 12 официального пакета нет). Инструменты те же
   (`awg`, `awg-quick`), конфиг отличается несколькими доп. параметрами
   обфускации (`Jc`, `Jmin`, `Jmax`, `S1`, `S2`, `H1`–`H4`) в секции
   `[Interface]`/`[Peer]` — их подбирает сама служба при выдаче пира, а не
   человек руками. Плата — не входит в стандартные клиенты: людям нужен
   клиент Amnezia (есть под все платформы, включая iOS/Android) вместо
   штатного WireGuard-приложения; это стоит явно проговорить с
   приглашёнными при выдаче доступа.
   Резерв на будущее, если DPI научится палить и AmneziaWG (гонка идёт
   постоянно): держать в голове Xray/VLESS+Reality как запасной транспорт
   на той же ноде — не делать сейчас, это отдельный этап поверх готовой
   инфраструктуры `vpn`, а не альтернатива ей.
2. **Служба роя `vpn`**, назначенная jeeves, — обычный `ServiceHandler` с
   `describe`, а не отдельный демон. Действия: `peers` (список: человек,
   устройство, последний хендшейк, объём за месяц), `issue` (выдать доступ),
   `revoke`, `usage` (потребление и лимиты), `set_quota`. Права — по общему
   правилу `действие@служба` (`issue@vpn`, `peers@vpn`, …). Весь UI приходит
   из этапа 32 бесплатно, включая форму для `issue`.
3. **Root не отдаём ноде.** Нода на jeeves работает под `systemctl --user`,
   а туннель требует `CAP_NET_ADMIN`. Как с диагностикой на alfred
   (`/etc/sudoers.d/10-diag`) — узкий sudoers-хелпер ровно на `awg show` и
   `awg set awg0 peer …`. `awg-quick` целиком не разрешать: он исполняет
   произвольные `PostUp`, то есть равен root.
4. **Пир привязан к человеку, а не к устройству**: запись — `(chat_id,
   метка устройства)`, у человека их может быть несколько, квота считается
   суммарно по всем его пирам. Иначе «выдай ещё один конфиг на телефон»
   обнуляет любой лимит.
5. **Учёт трафика — сэмплер с накоплением.** `awg show awg0 transfer` отдаёт
   счётчики с момента поднятия интерфейса: они обнуляются при рестарте и при
   удалении пира. Служба опрашивает их раз в несколько минут и копит дельты
   в своей SQLite; отрицательная дельта означает переподнятый интерфейс —
   считать заново от нуля, а не уходить в минус. Месячный ролловер — по
   календарю, с сохранением истории.
6. **Два уровня лимитов.** На человека: мягкий порог (предупреждение в личку
   на 80%) и жёсткий (на 100% ключ снимается с интерфейса, `awg set awg0
   peer <pub> remove`) — запись в БД при этом остаётся, доступ
   восстанавливается первого числа или руками админа. На ноду: общий лимит
   канала VDS — при приближении событие админам. Точное значение лимита
   провайдера у нас нет, его надо узнать и вписать в конфиг.
7. **Секрет уходит в личку один раз.** Приватный ключ генерируется на jeeves
   (у собеседника в Telegram нет способа сгенерировать свой) и отдаётся
   текстом конфига плюс QR-картинкой; в БД хранится только публичный. Это
   осознанный компромисс против канона «приватный ключ не покидает клиента».
   Отправка — только в личку, никогда в группу, и бот удаляет своё сообщение
   с конфигом через несколько минут.
8. **Приватность как явное правило:** служба пишет только объёмы и время
   последнего хендшейка. Ни адресов назначения, ни DNS-запросов, ни логов
   соединений — тем более что доступ выдаётся гостям, а не только себе.
9. **События роя** `vpn_peer_issued`, `vpn_quota_warning`,
   `vpn_quota_exceeded`, `vpn_peer_blocked` идут обычным путём алертов — в
   бот, по подпискам.

**Тесты:** сэмплер (обычная дельта, переподнятый интерфейс, ролловер
месяца), пороги 80/100 % и восстановление, `issue`/`revoke` поверх
подменяемого backend'а (`awg` в тестах не вызываем), права по подписке,
выдача секрета только в личный чат.

**Открытые вопросы к заказчику:** вопросы (а) и (б) из предыдущей версии
плана сняты 2026-08-01 (выходной узел, обфускация нужна — см. выше).
Осталось одно: **(в) какой лимит трафика у VDS по тарифу** — без этого
числа лимит на ноду (решение 6) не настроить, пока держим только
предупреждение «канал растёт» без порога.

### Этап 34. Потоковый вывод и Rich Messages в ответах Альфреда

Разбор находки 2026-08-01 (веб-поиск, т.к. обе фичи новее среза знаний
модели). Вопрос не «вызвать новый метод API», а полноценный этап —
меняется кусок конвейера от Ollama до Telegram, а не только последний шаг.

**Фаза 2 реализована (2026-08-09), Фаза 1 сознательно пропущена** —
решение пользователя: rich сразу как основной режим ответа
(`LlmConfig.response_mode`, дефолт `"rich"`), без промежуточного шага с
голым `sendMessageDraft`; `"typing_plain"` (прежнее поведение) — резервный
режим на случай проблем с рендером у конкретного клиента. Код + юнит-тесты
готовы (`llm/ollama.py::chat_stream`, `llm/service.py` буфер +
`chat_progress`, `llm_chat.py::run_chat_loop(on_partial=...)`,
`bot/rich_stream.py::RichStreamSession`, ветвление в
`bot/handlers/ai.py`), полный набор (1643 теста) зелёный. **НЕ
задеплоено** ни на одну ноду и не проверено вживую ни на одном реальном
Telegram-клиенте — см. раздел «Тесты и проверка» ниже, рендер по своей
природе не покрывается юнит-тестами.

**Что реально появилось.**

- **Bot API 9.3:** `sendMessageDraft` — эфемерный черновик (как «печатает…»
  в ChatGPT), не сохраняется в истории чата сам по себе; после окончания
  генерации всё равно нужен настоящий `sendMessage`/`editMessageText` с
  финальным текстом.
- **Bot API 10.1 (2026-06-11): «Rich Messages».** `InputRichMessage`,
  `sendRichMessage`, `sendRichMessageDraft` (потоковый черновик уже
  форматированного контента — таблицы, заголовки, вложенные списки,
  сворачиваемые блоки, код, LaTeX, коллажи), `editMessageText` получил
  параметр `rich_message`. Лимит длины сообщения поднят до 32 768 символов
  (у нас сейчас захардкожен старый лимit 4096 в трёх местах:
  `bot/notifier.py::MAX_LEN`, `bot/handlers/ai.py`, `bot/tool_debug.py`) —
  при переходе на Rich Messages это упрощение можно забрать бесплатно.
- **`RichBlockThinking`** — отдельный блок именно под рассуждения модели
  (`<tg-thinking>` в `InputRichMessage`). У нас модель уже генерирует
  «невидимый» thinking, который `ai_flow.py` вынужденно вычищает (живая
  находка — 1400+ токенов размышления ломали вывод непредсказуемо). Это
  открывает продуктовый вопрос **отдельно от инженерной задачи**: показывать
  рассуждение свёрнутым блоком (прозрачность) вместо нынешнего полного
  скрытия (сейчас часть образа Альфреда — не палить, что он модель) — не
  решаем сейчас, оставляем как развилку на потом.
- **aiogram** (`>=3.4,<4` в `pyproject.toml`) — в проекте стоит 3.29.1,
  типы/методы под всё это есть с 3.30.0: нужен бамп зависимости, дальше
  ограничения совместимости нет.

**Живые баги платформы (по чужим отчётам, июнь 2026, месяц с небольшим на
момент разбора) — проектировать вокруг них, а не игнорировать:**

1. **Смешение plain `editMessageText` и `sendRichMessage` при стриминге
   ломает форматирование** — если промежуточные чанки редактируются без
   rich-режима, а финализация идёт через rich, пользователь видит сырые
   `##`, `**`, `|` вместо разметки. Лечится дисциплиной: весь стрим —
   только через `sendRichMessageDraft`, ни одного plain-редактирования
   внутри одного потока.
2. **Telegram Desktop не рендерит стримы `sendRichMessageDraft`** (iOS/
   Android — нормально); Telegram Web вообще не рендерит `sendRichMessage`.
   Семья/гости сидят на разных клиентах — часть аудитории увидит либо не
   увидит поток корректно, и это не наш баг, чинить нечем.
3. Сообщалось об увеличенном кегле текста в Rich Message-теле относительно
   обычных сообщений и о зависании индикатора «печатает» в группах
   (финализация запаздывает ~10 с).

**Архитектурный разрыв, который не решается одним вызовом API.**
`PROTOCOL.md` — строгий запрос/ответ (`command` → один ответный конверт),
потоковых сообщений в протоколе роя нет вовсе. `llm/ollama.py::chat()`
сейчас жёстко зовёт Ollama с `"stream": False` — частичного вывода нет
нигде в конвейере, и служба `llm` может стоять на другой ноде (winpc), не
там, где бот. Два пути:
  a. Завести в протоколе честный потоковый примитив (несколько ответных
     конвертов на один `id`) — правка `proto/`, задевает все службы.
  b. **Переиспользовать уже существующий в проекте паттерн опроса**
     (`wake_core.py`: «опрашивать `get_state` удалённой службы, пока не
     ответит или не истечёт») — служба `llm` держит частично сгенерированный
     текст в памяти, отдаёт его отдельным действием/полем `get_state`, бот
     опрашивает раз в ~1 с, пока основной блокирующий `chat` не вернулся, и
     кормит нарастающим текстом черновик в Telegram. Не требует правки
     протокола, дешевле и вписывается в уже принятые решения — предпочтительный
     старт.

**Рекомендованный порядок (двумя фазами, не одним куском):**

1. **Фаза 1 — дёшево, без Rich Messages вовсе.** `send_chat_action(chat_id,
   "typing")` перед вызовом `llm.chat` (эта мелочь висит нереализованной
   ещё с LLM_INTEGRATION_PLAN.md §6.6) плюс простой текстовый стрим через
   `sendMessageDraft` (Bot API 9.3, обычный текст, без Rich) поверх опроса
   `get_state` по варианту (б). Полезно уже само по себе, платформенных
   багов Rich Messages не касается.
2. **Фаза 2 — настоящий Rich.** Переход на `sendRichMessageDraft`/
   `sendRichMessage` там, где формат реально нужен (таблицы в `/nodes`,
   код в ответах Альфреда, сворачиваемые блоки) — после того как баги п.
   1–3 выше устоятся или для них найдутся обходы; `RichBlockThinking` —
   отдельное решение, не автоматически вместе с этой фазой.

**Тесты.** Логика чанкинга/троттлинга/опроса — юнит-тестами как обычно.
Корректность РЕНДЕРА — по природе клиентская история, автоматизировать
нечем: перед тем как показывать это гостям, нужна ручная проверка минимум
на двух клиентах (например, Desktop и Android), учитывая задокументированный
баг п. 2 выше.

### Этап 35. Прямой потоковый канал между нодами — новая возможность ноды

Заявка пользователя 2026-08-01: обобщить проблему стриминга из этапа 34 до
уровня платформы. Нужна не «стриминг ответов Альфреда», а общая
возможность ноды передавать непрерывный поток байт другой ноде (или
устройству вне роя) — сам этап 34 становится первым потребителем, а не
единственным. Названные пользователем сценарии:

- **Интернет-радио** — нода ретранслирует/проксирует аудиопоток на
  устройства в сети, без привязки к Telegram.
- **«Коллективный кинотеатр»** — фильм, лежащий на диске одной ноды
  (`torrents`), стримится остальным участникам для совместного просмотра.

**Почему это НЕ вписывается в существующий протокол.** `PROTOCOL.md` —
конверты JSON поверх одного TCP-соединения на пир, строго запрос/ответ
(`describe`/`get_state`/`command`). Это подходит для контрольной плоскости
(редкие, маленькие сообщения), но не для потока медиабайт: большой объём,
непрерывность, нужен backpressure, и — важно для слабого железа alfred
(Celeron N3350, 2 ядра) — тяжёлый поток не должен подпирать управляющий
канал той же ноды (heartbeat, события) в одном TCP-сокете.

**Решение: не изобретать бинарный протокол поверх линка пира, а выдавать
обычный HTTP-тикет.** Контрольная плоскость (`describe`/`command`, права
`действие@служба` — переиспользуем как есть) выдаёт **только адрес и
разовый токен**: `{"url": "http://<адрес-ноды>:PORT/stream/<токен>",
"expires_at": …}`. Сами байты идут по чистому HTTP (chunked
transfer-encoding) — токен в пути вместо HMAC-схемы роя, потому что
потребитель байтов — не наш код, а обычный медиаплеер (mpv/VLC/браузер),
который не умеет в наш протокол. Это переиспользует то, для чего и так
существует HTTP-стриминг (интернет-радио и HLS/DASH и так поверх HTTP), а
не строит велосипед под каждый случай заново.

**Решения по месту.**

1. **Возможность живёт в `node/`-ядре, не в конкретной службе** (как в
   заявке — «новая возможность НОДЫ»): общий компонент, который любая
   служба (`llm`, `torrents`, будущая `radio`/`media`) может дёрнуть, чтобы
   получить тикет + слушатель. Аналогия — `describe`/`command` уже
   общие для всех служб, не переизобретаются каждой заново.
2. **Только relay/passthrough, без транскодирования.** Слабое железо
   alfred не тянет перекодирование видео на лету; источник должен уже
   быть в проигрываемом формате/битрейте. Явно ограничить конкурентные потоки —
   иначе даже пассивная раздача байт с двух ядер Celeron может забить CPU
   на I/O под нагрузкой нескольких зрителей разом.
3. **Слушатель — на tailscale/LAN, не `0.0.0.0`** — тот же принцип, что уже
   применяется для `endpoint_attr` служб и осознанно НЕ применяется как
   дефолт на jeeves (см. этап 26). Публичный доступ, если понадобится
   (гостю вне тейлнета), — отдельное решение, не дефолт.
4. **Токен разовый/короткоживущий, не HMAC-токен роя.** Обычный HTTP-клиент
   не умеет подписывать запросы токеном `[swarm].token` — поэтому токен в
   URL, с коротким TTL и логированием БЕЗ самого токена (тот же принцип,
   что и с инвайт-кодами и секретами VPN, этап 33 п. 7).
5. **Синхронный просмотр («смотрим вместе, старт по команде») — явно
   НЕ входит в эту возможность.** Это отдельная, более сложная задача
   (общий канал play/pause/seek между зрителями) поверх транспорта,
   который здесь появляется — не путать «доставить байты» с
   «синхронизировать воспроизведение».
6. **Пересечение с этапом 34.** Опрос `get_state` для стриминга LLM-ответа
   (этап 34, вариант «б») — временный обходной путь, пока этой возможности
   нет. Если этап 35 появится раньше, чем понадобится Rich Messages,
   стриминг LLM-ответа может переехать на HTTP-тикет вместо опроса — не
   блокирует этап 34, но стоит держать в голове при реализации.

**Тесты:** выдача/проверка тикета (валиден/просрочен/одноразовый),
привязка к правам `действие@служба`, отказ отдавать `0.0.0.0`, лимит
конкурентных потоков — сам HTTP-стриминг байт нагрузочно не тестируем
юнитами, только логику вокруг него.

**Открытый вопрос:** нужен ли доступ гостям вне тейлнета (публичный
слушатель на jeeves) или хватает LAN/tailscale — как и с VPN (этап 33),
это меняет модель угроз и решается отдельно, не по умолчанию.

### Этап 36. `tell` для всех гостей: владелец всегда доступен, «семья» — своя группа — ✅ v0.76.0 (2026-08-05)

Решение пользователя 2026-08-04 (после находки живого бага этапа 33 п. 7 —
секрет VPN уходил не тому получателю): `tell@llm` перестаёт быть
привилегией «выдано вручную нескольким», а выдаётся ВСЕМ гостям — но с
более узкими правами по умолчанию, чем раньше был весь тул целиком.

1. **Право `tell@llm` (как сейчас) — «могу писать ВЛАДЕЛЬЦУ».** У любого
   гостя с этим правом всегда получается написать владельцу (админу с полным
   `*`), даже если больше он никому не может, — сама причина заводить
   `tell` каждому: чтобы гость мог достучаться до Алексея, не будя его
   явным приглашением в разговор.
2. **Новое право `tell_guests@llm` — «могу писать ДРУГИМ гостям» (не
   владельцу).** Без него `tell` на кого-то, кроме владельца, отказывает
   («не умею», не «отказываю» — тот же принцип §3.4 LLM_INTEGRATION_PLAN.md).
   Выдаётся точечно, не по умолчанию.
3. **Группа «семья» — новый флаг `family` на подписке.** Члены семьи видят
   друг друга «своими» и могут `tell` друг друга без `tell_guests@llm` —
   это ОБХОД п. 2, а не альтернатива праву: гость без флага `family`
   по-прежнему не пишет другим гостям без отдельного права, даже если
   пишущий сам — семья.
4. **Реализация — не декларативные права, а проверка получателя внутри
   `tool_tell` (bot/tools.py), после резолва через `recipients.find_recipients`:**
   владелец определяется как `target_subscription.allows_command("*")`
   (существующий признак полного доступа, не новый флаг — второй
   владелец в конфиге автоматически подпадёт под тот же признак);
   `family` — новое поле на `Subscription`/`SubscriptionConfig`/
   `GuestSubscriptionConfig` (config.py, subscriptions/models.py,
   subscriptions/book.py), симметричная проверка (оба конца — семья).
   **Поле `family` уже заведено этапом 37** (`bot.family`, точнее
   `Subscription.family`) под доступ к `memory scope=family` — этот этап
   переиспользует его, ничего не переделывая в модели.
5. **Не влияет на видимость тула.** `requires=CommandRight(TELL_RIGHT)` в
   `TOOLS` (том же месте) остаётся — это по-прежнему «есть ли тул вообще»;
   п. 1–3 — это уже КОМУ внутри уже вызванного тула можно писать.
6. **Ручной шаг после реализации:** дописать `tell@llm` действующим гостям
   в `instances/telegram-bot.<нода>.guests.toml` (гостевой пакет,
   `subscriptions/guests.py`) и в дефолт `[invites].grant_commands`
   (config.py) для новых — но только ПОСЛЕ того, как код начнёт различать
   владельца/семью/остальных, иначе это то же самое «всем можно всё», что
   уже подвело на VPN.

**Реализовано ровно по п. 1–5.** `bot/tools.py::TELL_GUESTS_RIGHT =
"tell_guests@llm"` — новая константа рядом с `TELL_RIGHT`; проверка внутри
`tool_tell` — после резолва `target` через `find_recipients`, до
рейт-лимита: `is_owner = target_subscription.allows_command(WILDCARD)`,
`same_family` — оба конца `Subscription.family`, `has_tell_guests =
ctx.subscription.allows_command(TELL_GUESTS_RIGHT)`. Отдельного кода под
«владелец-отправитель» не понадобилось: `allows_command` возвращает `True`
на любую строку, если в `allowed_commands` есть голый `*` — тем самым
`has_tell_guests` уже истинен для владельца без специального случая.
`bot/guest_rights.py` — `tell@llm` переименован в каталоге на «Написать
владельцу», добавлена строка `tell_guests@llm` («Писать другим гостям») —
точечная выдача через `/guests` без правки кода бота (п. 2).

**Тесты (написаны и зелёные, `tests/unit/test_tell.py`):** владелец всегда
получает `tell` от гостя без `tell_guests@llm`
(`test_tell_guest_always_reaches_owner_without_tell_guests_right`); гость
без `family`/права не может написать другому гостю
(`test_tell_guest_cannot_reach_another_guest_without_right_or_family`);
`family` не альтернатива праву, а обход именно для пары семья↔семья

#### Фаза 0. Второй сервер + выбор локации (делаем сейчас)

**39.0.1. Подбор домена — для фазы 1, не блокирует фазу 0.** В модели B
клиентский `Endpoint` — сырой IP нужного сервера, домен не нужен. Домен
понадобится в фазе 1 (DNS-фейловер `vpn-nl`/`vpn-us`). Решение отложено
(пользователь 2026-09-04). Кандидаты: новый домен + Cloudflare DNS · DuckDNS
· существующий домен. Факторы к оценке:
- цена и автопродление; потеря домена = потеря VPN для всех клиентов;
- минимальный TTL (Cloudflare — 60 c);
- API для фазы 1: надёжность, токен с узкими правами (одна зона / запись);
- WHOIS-privacy — не светить инфраструктуру;
- скорость резолва из Алматы — рядом anycast-узел Cloudflare (`1.1.1.1`
  ~30 мс, см. память `alfred-network-dns-latency`), плюс в его пользу;
- задел под фазу 2: поддомены `vpn`, `vpn-nl`, `vpn-us`.
- MagicDNS Tailscale **не подходит** — клиенты-телефоны не в tailnet.

Разбор 2026-09-05 (рекомендация — **свой домен + Cloudflare DNS**):
- **DuckDNS отпадает** — сайт сервиса лёг в августе 2025, статус не
  восстановлен; критичную зависимость VPN на него не вешаем.
- **Cloudflare DNS free**: записи «DNS only» (proxy для UDP 51820 не годится)
  — минимальный TTL **60 c**, полноценный API, токен скоупится до одной
  зоны (`Zone.DNS:Edit` + `Zone.Zone:Read`) → в фазе 1 ключ с минимальными
  правами. Anycast-резолвер рядом с Алматы (`1.1.1.1` ~30 мс).
- **Регистрация**: Cloudflare Registrar по себестоимости (`.com` ~$10–11/год,
  WHOIS-privacy включена), но требует держать DNS на Cloudflare — совпадает
  с выбором. Альтернатива — Porkbun (~$11/год продление) с делегированием NS
  на Cloudflare.
- Брать `.com`/`.net` (реже блокируются в жёстких сетях), домен отдельный
  под инфраструктуру, не связанный публично с владельцем.
- Остаточный риск (KZ): локальные резолверы могут ломать ответ до подъёма
  туннеля → держать доступным конфиг с сырым IP как fallback; позже —

**40.1. `conntrack_pct` — заполнение таблицы отслеживания соединений**
`/proc/sys/net/netfilter/nf_conntrack_count` ÷ `nf_conntrack_max` × 100.
Для NAT/VPN-бокса критично: таблица переполнилась → ядро молча дропает новые
соединения, туннель «поднят», клиенты не ходят. `DIR_ABOVE`, дефолт warn 80 /
crit 95, hint «таблица conntrack почти полна — новые соединения дропаются».
Модуль `nf_conntrack` не загружен (нода без NAT) → файлов нет → метрику не
эмитим (как PSI). Одно чтение, дельта не нужна.

**40.2. `net_err_rate` — ошибки и дропы на интерфейсах**
Два снимка `/proc/net/dev` с паузой `sample_window_s` (как у `steal_pct`), сумма
дельт `rx_errs + rx_drop + tx_errs + tx_drop` по всем не-`lo` интерфейсам,
нормировать в **событий/мин**. `DIR_ABOVE`, дефолт warn 1 / crit 10, hysteresis 1,
hint «интерфейс теряет пакеты — `ip -s link`, проверь линк/драйвер virtio».
Ловит тихую деградацию линка (класс «downshift до 100 Mbps / check cabling» из
CLAUDE.md, но для VM). v1 — агрегат по всем интерфейсам (теряем, какой именно;
hint отправляет смотреть руками). Возможная доработка: per-interface
`component_id = "host:net_err:<iface>"` — но это ломает плоский `METRICS` (ключ =
фиксированное имя), поэтому за пределами v1.

**40.3. `kernel_stall_events` — залипания ядра/гипервизора за окно**
Счётчик строк kernel-журнала с прошлого прогона, подходящих под паттерны стойл:
`hung_task`, `rcu_(sched|preempt).*stall`, `clocksource.*(unstable|Marking)`,
`soft lockup`, `BUG: soft`, `NETDEV WATCHDOG`, `TX timeout`,
`blocked for more than \d+ seconds`. Это **ровно** документированный сценарий
падения jeeves (`jeeves-vpn-hypervisor-stalls` — фризы VM гипервизором, которые
`steal` ловит не всегда, а в dmesg они есть). Форма как у `oom_kills`: дельта,
warn 1 / crit 1 (любое событие — повод), hint «ядро логировало стойла — вероятны
фризы VM гипервизором».
- **Источник:** `journalctl -k -S <last_scan> -U <now> -o cat` + grep паттернов.
  `sensors/power.py` уже ходит в `journalctl` и регистрирует `JOURNALCTL_REQUIREMENT`
  — переиспользовать. Для не-root доступа к kernel-журналу нужен `sevboa` в группе
  `systemd-journal` (или `adm`); нет прав → метрику помечаем недоступной через
  `requirements_registry` (как smartctl в этапе 38), в карточке ⚠️-подсказка
  `usermod -aG systemd-journal sevboa && перелогин` либо строка в
  `/etc/sudoers.d/10-diag`.
- **Состояние «последний скан»:** ключ `app_state` (`Store.get_state/set_state`),
  напр. `kernel_scan_at`; первый прогон — окно `now - sample_window_s` (не с
  начала времён). `dmesg` не берём: `kernel.dmesg_restrict=1` по умолчанию на
  Debian → нужен root/`CAP_SYSLOG`.
