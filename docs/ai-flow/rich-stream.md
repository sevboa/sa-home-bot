# Rich-ответы и щадящий стрим (`bot/rich_stream.py`, Этап 34)

`RichStreamSession` — Telegram Bot API 10.1/10.2 Rich Messages для ответов Альфреда. Rich — основной режим (`LlmConfig.response_mode`), без смешивания с plain `editMessageText` внутри одного ответа: `sendRichMessageDraft` пока идёт генерация и `sendRichMessage` для окончательного текста (единственная точка, реально персистящая сообщение). Текст ответа — готовый markdown (модель и так генерирует его); статусы (шаги/тул/пробуждение) — блок `InputRichBlockThinking` (допустим ТОЛЬКО в draft, в сообщениях нельзя — поэтому `finalize` шлёт обычный markdown).

- `sendRichMessageDraft` платформенно ограничен приватным чатом (Bot API, не наш выбор). В группах сессия работает без `on_partial`, в конце один `finalize()`: то же форматирование (таблицы, код, списки), без анимации. Сессия заводится ВСЕГДА (нужна для finalize в любом чате), стрим-черновики подключаются только для приватных.
- `draft_id` случаен на сессию, не константа на чат: `ActiveAiChats` хранит task только для отмены, не гарантирует единственность /ai в чате (два быстрых сообщения — две задачи aiogram); общий `draft_id` анимировал бы один черновик поверх другого.
- Сигнатура последнего показанного — пара `("md", текст)`/`("think", текст)`: пейлоады структурно разные, совпадение сырого текста между ними не должно гасить обновление.
- Черновик эфемерен (докстринг aiogram: «temporary 30-second preview», находка 2026-08-11), а ожидание пробуждения/прогрева на порядок длиннее — отсюда keep-alive. Защитный потолок фоновой задачи `_KEEPALIVE_MAX_IDLE_S` = 30 мин тишины (самое долгое легитимное ожидание — `wake_core.WARMUP_TIMEOUT_S` = 360 с) страхует брошенную сессию; штатно сессия обязана дойти до `finalize`/`finalize_status`/`aclose`.
- **Этап 34.3 (2026-09-30), щадящий стрим.** Живая находка: частая смена черновика в личке вешает клиент Telegram (особенно Android), а у `sendRichMessageDraft` недокументированный лимит строже `editMessageText` (при ~1.3 с между черновиками — 429 с retry_after 3–10 с). Раньше черновик шёл на каждый тик опроса (раз в секунду), на каждый статус тула, плюс безусловный keep-alive раз в 20 с и typing раз в 4 с, а 429 глотались в `log.debug`. Теперь все отправки через один ограничитель `RichDraftPolicy`: не чаще `min_interval_s` (общий лимит на текст, статус и keep-alive), текст — только при приросте `min_growth_chars` (первый кусок — без условия; текст короче показанного — новый раунд после тула — тоже), статусы сворачиваются (последний побеждает), keep-alive только в простое, `retry_after` выдерживается для всех черновиков сессии, typing при черновике не горит (решение 2026-08-11) — только при `streaming=False`. Отложенное досылает фоновая `_pump`, спит до следующего момента (`_next_due`), будится на новый push.
- Гонка финала: раньше keep-alive и typing гасились ПОСЛЕ `sendRichMessage`, тик keep-alive мог всплыть устаревшим черновиком после реплики. Теперь `_send_persisted` сначала останавливает фоновую задачу (дождавшись отменённой — она могла быть посреди отправки) и typing, и под тем же замком, что черновики, шлёт реплику. Реальное сообщение вытесняет черновик той же сессии (семантика платформы), поэтому состояние черновика сбрасывается.
- Живая находка 2026-08-29: ловили только `TelegramAPIError`, а реальный сбой (зависший SOCKS-прокси) приходит как `aiohttp_socks.ProxyTimeoutError` — обычный `Exception`; он рушил весь /ai-ответ ещё до модели. Черновик — превью, один тик потерять не страшно (в отличие от `finalize`). `CancelledError` не `Exception`, отмена проходит. Warning на первые три сбоя каждого вида за сессию, дальше debug (прокси может лежать минутами); итог — одна INFO-строка при `aclose`.
- Живой баг 2026-08-10: статусные фразы сами называют Альфреда в третьем лице («Альфред сёрфит…»); с `ALFRED_PREFIX_MD` получалось «Альфред: Альфред сёрфит…» — статусы идут через thinking-блок (не markdown), префикс нужен только настоящему ответу (`on_partial`).
- `finalize_status` — реплика ДРУГОГО персонажа (Агнольд, Альбегт) без префикса Альфреда. Живая находка 2026-08-10 (третий заход): через `message.answer()` (обычный sendMessage) активный черновик «шаги» не менялся, а истекал сам, и реплика всплывала отдельным сообщением с разрывом. `sendRichMessage` вытесняет черновик той же сессии напрямую, без зазора, а реплика остаётся в истории. `reply_to_message_id` — для «Альбегта» провала отложенной задачи (`bot/node_events.py`): реплай-стрелка — единственная подсказка, к какой давней просьбе реплика относится.
- Доставка финала: `finalize` с ретраями 429 (`send_with_retry`); `None` — не вышло. Тогда `handlers/ai.py` откатывается на plain-HTML `send_direct` (Этап A, 2026-08-30: терять готовый ответ молча нельзя).
