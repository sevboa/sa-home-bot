# Окно контекста и сжатие истории (Этап 50, 2026-09-30)

## Живая поломка

История треда уходила в модель целиком (`ai_turns` без LIMIT, семь копий сборки в хендлерах). Промпт дорастал до ~31.8k из 32768 токенов окна, модель уходила в thinking, окно кончалось посреди генерации (`done_reason=length`) — «Альбегт» (пустой ответ) или ответ, молча обрезанный на полуслове; Ollama при переполнении сама выкидывает начало истории. База промпта ~12k (персонаж, декларации тулов, роутер), 83% роста — длинные ответы Альфреда.

## Как устроено (`bot/dialogue_context.py`)

- **Сборка** `load_history` — одна функция на все пути хендлера: [краткое содержание начала разговора отдельным system-сообщением] + ходы после `upto_message_id` этого содержания. Старые (не из последних `context_keep_recent_turns`) ответы Альфреда укорачиваются до `context_old_reply_max_chars` с явной меткой `SHORTENED_MARK` (не «…», чтобы модель не приняла обрыв за манеру и не подражала). `ai_turns` не меняется никогда. `DialogueHistory` — подкласс списка (проходит через хендлеры и request_alfred как обычный список), `compress_after` — выход: ставит request_alfred, хендлер после доставки запускает фоновое сжатие.
- **Оценка до генерации** `estimate_prompt_tokens`: по последнему замеру `prompt_eval_count` треда плюс прирост в символах и по чистым символам (база + текст / `context_chars_per_token`); берётся бо́льшая — prefix-кэш Ollama может занижать `prompt_eval_count`, а оценка по символам не знает точной базы: ошибаемся в запас.
- **Порог превышен** — в ЭТОТ ЖЕ ответ добавляется `STEP_AWAY_INSTRUCTION` (решение 2026-09-30): ответить как обычно и в конце, в образе, своим поводом, без технических слов, сказать, что нужно ненадолго отлучиться. Примеры поводов — только примеры. После доставки ответа запускается фоновое сжатие. Если окно неизвестно/слишком мало для базы промпта (порог ≤ `context_base_tokens`), «отлучаемся» не на каждом ходе — от реального переполнения страхует `_rescue`.
- **Сжатие** — отдельный LLM-запрос службы llm с ролью `summarizer` (свой system без персонажа, think off, temperature 0): прежнее содержание + старые ходы → новое ~1–1.5k токенов, в `ai_dialogue_summaries`. Сжимается только история. Новая версия пишется одной строкой только после успешного пересказа, поэтому ход, не дождавшийся сжатия, видит целостную картину. Защита от двойного запуска двумя слоями: `schedule` не заводит вторую задачу, само сжатие под замком треда. Дословный хвост начинается с реплики собеседника. Одна часть — не больше ~55% окна вместе с прежним содержанием.
- **Дословный возврат** `recall_verbatim` — перед генерацией FTS5-поиск (trigram, `ai_turns_fts`) по ходам треда, которых нет в истории дословно (сжатые/укороченные), под текущую реплику; блок «Из начала разговора (дословно)» парами «реплика + ответ» в пределах `context_recall_budget_chars`. Так «медведь с зелёными глазами», потерявший цвет глаз в пересказе, возвращается исходными сообщениями. «ё» → «е», как в индексе (`schema.sql::ai_turns_fts_insert`). Стоп-слова и обращения тянут случайные ходы — отфильтрованы.
- **Страховка** (`request_alfred::_rescue`): ответ вернулся с `done_reason=length`/пустым из-за переполнения — синхронное сжатие, заготовленная реплика (`STEP_AWAY_LINES`) и перегенерация без повторных побочных эффектов тулов (`_tools_done_note`, `allow_tools=False`); не помогло — `trim_to_budget` отрезает самые старые ходы. Заготовки написаны БЕЗ буквы «р»: Логопед (картавость) обрабатывает только вывод модели, а эти строки идут мимо — без «р» они верны и для картавого Альфреда, и для «чистой речи» гостя (Этап 47); проверяется тестом.
- Окно `num_ctx`: что служба сказала в последнем ответе этому процессу (`_seen_num_ctx`) → последний замер из БД → `[llm].num_ctx` бота (грубый фолбэк). `describe` здесь намеренно не зовётся: оценка идёт ДО пробуждения, неудачный describe спящей ноды закэшировал бы «профиля нет» на 5 минут и сбил бы выбор router-прохода.
- Тулы, чей след виден в истории (`HISTORY_TOOLS`): вызов и результат после хода собеседника. Находка 2026-10-03: в истории были только тексты («покажи кабинет» → «Вот, прошу…»), и на следующую такую просьбу модель отвечала тем же текстом без `take_photo` — образец говорил, что снимок это слова. Только тулы, присылающие что-то в чат. Находка 2026-10-09: id из `find_person` жил один ход, на «да, хочу связь» модель звала `request_acquaintance` с выдуманным 123456789 — тулы людей остаются в истории длиннее (600 знаков, id кандидатов не обрезать).

## Цикл тулов (`llm_chat.py`)

- Вынесен из ai_flow (находка 2026-07-24): им пользуется и служба tasks (отложенные «спросить нейронку», в т.ч. от тула `remind`); модуль зависит от `bot.tools` (чистый Python без aiogram) и намеренно не импортирует `llm/service.py` (константы `ACTION_CHAT`, `ACTION_CHAT_PROGRESS` продублированы: у tasks нет тяжёлых зависимостей LLM-службы). Модуль БД не трогает: `on_tool_call` передаёт вызывающий.
- `MAX_TOOL_ROUNDS = 5` (было 4, решение 2026-07-27): с `web_search` модель делает несколько поисков подряд; на вопросе про Нидерланды три раунда ушли только на поиск. Лимит исчерпан — НЕ падаем: последний запрос без деклараций тулов, модель формулирует из собранного (раньше был `ProtoError` → «Альбегт» после нескольких минут ожидания при том, что результаты уже лежали в messages). Пустой ответ и там — настоящий сбой (`ERR_INTERNAL`).
- Живая находка 2026-09-04: несколько результатов `web_search` в одном ходе добивали контекст до предела — модель возвращала пустую строку без ошибки. Результаты длиннее `_TOOL_RESULT_INLINE_LIMIT` (1000) в `messages` кладём превью (600) с id; полный текст — в `tool_ctx.tool_result_cache`, модель при нужде зовёт `recall_tool_result(id)`. В `ai_tool_calls` пишется полный текст.
- Повторы раунда `chat` при кратковременном обрыве связи (решение 2026-09-25, `CHAT_RETRY_DELAYS_S` 3 и 6 с): линк alfred→mycraft переподключился посреди хода (~5 с без связи), раунд после тула упал в unavailable — гость вместо готового ответа получил «Альфреда нет на месте». Паузы покрывают переподключение PeerLink/ServiceLink (RECONNECT_DELAY_S = 5 с). Повторяем ТОЛЬКО «нет связи» (`_is_link_gap`: без `ServiceTimeoutError` — модель уже думала весь бюджет — и без `ERR_UNKNOWN_DST`); раунд идемпотентен: служба только генерирует, тулы исполняются здесь.
- Стрим (Этап 34, Фаза 2): с `on_partial` каждый раунд идёт со своим `request_id` и параллельным опросом `chat_progress` раз в ~1 с (`_POLL_INTERVAL_S`, короткий `_POLL_TIMEOUT_S` на round-trip). Параметров `get_state` не принимает (PROTOCOL.md), а Альфред ведёт несколько диалогов одновременно, поэтому частичный текст держится по `request_id`. Финальный текст всё равно берётся из результата основного `command`, сбой опроса не критичен; какой раунд станет настоящим ответом, решает вызывающий.
- Серийные тулы (Этап 59.7): действия идут по одному, следующее модель назначит, увидев итог предыдущего (`SERIAL_DEFERRED`).
- `speech_clear` может быть функцией — флаг перечитывается перед каждым раундом: гость мог сменить передатчик кнопкой посреди хода (живой баг 2026-09-28). `photo_key` едет на каждый раунд, служба использует его, только если последний элемент `messages` несёт `raw_image`.
- `ChatStats.first_prompt_tokens` — промпт ПЕРВОГО раунда (история + заметка, без результатов тулов) — по нему оценивается место под историю; `max_prompt_tokens` — для лога и страховки; `done_reason=length` — окно кончилось посреди генерации.
