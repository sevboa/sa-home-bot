# Службы памяти и карточки людей

## memory (`memory/`)

У модели нет памяти между разговорами: персонажный промпт — статика на каждом вызове, текущий тред — всё остальное. «Качаем в /mnt/data/pr», «смотрим в озвучке LostFilm» хранить было негде.

- **Память — по чату** (решение 2026-07-29): сказанное в личке не всплывает в группе. `chat_id` проставляет бот, не модель (модель параметра не видит и до чужой памяти не дотянется).
- `scope=common` — общее знание дома (кто такой Альфред, как выглядит), видно из любого чата; позволяет вынести справочную часть из персонажного промпта. Заводит человек руками (`nodectl call memory remember scope=common …`). `scope=family` (2026-08-03) — только чаты из `[memory].family_chat_ids`; живая находка 2026-08-02: день рождения, рассказанный в личном чате, спросили из ЧУЖОГО семейного — `chat` его не показывает, а `common` показал бы случайному гостю по инвайту. Границу держит запрос к БД, не обещание модели молчать. Гостевой флаг «семья» (`guest_family`) убран 2026-09-27 — присланный старым ботом, игнорируется. `family` в обе стороны: чат не из семьи не может записать семейный факт.
- `sensitive=true` — личное, никогда не `common` (отказ, а не «предупредим и запишем»), в контекст уходит с оговоркой «не пересказывать вслух». Жёсткая здесь только видимость; «не произноси» — просьба к модели.
- Забыть можно только факт своего чата со `scope=chat` (без `chat_id` в условии один чат стирал бы чужую память, зная номер; общее знание заводит человек — пусть руками и убирает).
- Поиск — FTS5 системного sqlite, токенайзер `trigram` (ищет по подстроке), без эмбеддингов: единственная машина с моделями штатно спит, а память должна отвечать. Живая находка 2026-07-29 (первый же прогон): записали «смотрим в озвучкЕ», спросили «какая у нас озвучкА» — ноль находок; хвост «-ка» в «озвучке» не встречается. Отрезание окончания (`utils.text.stem`) превращает поиск в поиск по началу слова. Это не морфология («качаю» не найдёт «качаем»). Слова объединяются через OR (bm25 поднимет запись с большим числом совпадений), каждое в кавычках (пунктуация и `AND`/`NOT`/`*` из живого текста ломали бы разбор).
- `MAX_FACT_CHARS` = 400: факт — одна мысль, длинные подойдут под любой запрос и не влезут в контекст. Больше трёх фактов в контекст не влезает, запас — для `nodectl`.
- **Этап 42.1 (2026-09-23):** служба перенесена с alfred на mycraft. Прежний инвариант «доступна ВСЕГДА» не подтвердился: `recall_facts` и `tool_memory` дёргаются только внутри /ai-разговора, а он и так не ответит, пока mycraft спит. Недоступность — предусмотренная деградация (`recall_facts` → `[]`, тул → «недоступно»). `NODE_ID` должен совпадать с `[node].id` ноды, где `memory` в assignments.
- `memory/protocol.py` намеренно без импортов внутри проекта (бот-тулы импортируют константы, не утягивая службу). Значения `NODE_ID`/`SERVICE_NAME` не менять.

## graph_memory (`graph_memory/`, Этап 41)

Neo4j + Graphiti. Зачем отдельно: `memory` не отвечает на реляционные вопросы («кто жена Алексея», если записано «Наташа — жена Алексея»); граф сущностей/рёбер, экстракция через LLM (Ollama на mycraft), гибридный поиск (вектор + текст + граф).

- ОСЛАБЛЕННЫЙ инвариант: пинуется на mycraft (там Neo4j и Ollama), которая штатно уходит в suspend. Недоступность во сне — деградация («деградация при недоступности пира», ARCHITECTURE.md §11), `recall_graph_facts` молча отдаёт `[]`.
- Партиционирование по `chat_id` (`group_id` Graphiti = `str(chat_id)`) — граница приватности, как у memory.
- Асинхронная запись: экстракция — секунды. `add_episode` сразу пишет строку в `graph_episodes` (pending) и отвечает; `_ingest_loop` обрабатывает очередь последовательно (pending → processing → done/failed, `MAX_ATTEMPTS` = 3). При старте `processing`-хвост сбрасывается в pending — иначе рестарт терял бы эпизод. Пауза опроса пустой очереди 5 с (реже, чем poll tasks), `RETRY_BACKOFF_S` = 15 с — не долбить Neo4j/Ollama.
- Клиент Graphiti строится лениво под замком (Neo4j/Ollama могут быть не готовы при старте `sa-home-node`; два одновременных первых запроса иначе построили бы клиента дважды); любая ошибка → `ERR_UNAVAILABLE`. Импорты graphiti — внутри метода (extras только на mycraft).
- Параметры экстракции (замер 2026-09-25, gemma через `/v1`): без них эпизод шёл 30–110 с и держал общую очередь Ollama, в которой стоит живой чат. Через OpenAI-совместимый `/v1` Ollama по умолчанию ВКЛЮЧАЕТ thinking у gemma (нативный `/api/chat` бота — нет): ~60% токенов уходило в рассуждение; `reasoning_effort="none"`. `max_tokens` 4096 (дефолт Graphiti 16384, `extract_edges` передаёт свой лимит в обход `LLMConfig`; ответы убегали до 3–4 тыс. токенов и обрывались таймаутом — 500 от Ollama, эпизод failed). `temperature=0`: нужна детерминированность.
- Модель экстракции — та же, что в VRAM для живого чата (`extraction_model` пусто → `settings.llm.model`): без вытеснения из VRAM и очереди позади медленной CPU-генерации. Reranker не вызывается (`EDGE_HYBRID_SEARCH_RRF` — чистый RRF по BM25+cosine), клиент держим, чтобы Graphiti не завёл дефолтный без api_key («Missing credentials»).
- Источники эпизодов (`EPISODE_SOURCE_*`) — раздельные константы, чтобы piggyback-пути не путали эпизоды и будущий фильтр различал: memory_fact, dialogue_turn (42.2), look_at_photo (42.2), link (42.2), web_search (42.3 — ради чего и затевалась графовая память), image (Этап 48).
- Лимит эпизода 400 знаков (одна мысль), канон — `protocol.MAX_EPISODE_CHARS`; клиентская сторона — `graph_memory/client.py::add_episode` (обрезает с «…», таймаут 2 с, проглатывает недоступность).

## Карточки людей (Этапы 54, 58)

Утверждение — «by_id сказал, что у subject_id поле field = value». Правило веса (решение владельца 2026-10-08, этап 54): сказанное о себе — сильное, из сильных действует последнее; сказанное знакомым — слабое и работает, пока сам человек не сказал иначе; у владельца особого веса нет. Источник сохраняется, чтобы Альфред мог ответить «откуда знаешь»; в хранилище только id, имя подставляет бот.

- Этап 54: утверждения — узлы `(:PersonClaim)` в общем разделе графа `PEOPLE_GROUP_ID` (не `str(chat_id)`: пол, сказанный в одном чате, обязан быть известен во всех), прямой Cypher без LLM-экстракции (это утверждение, а не текст для разбора); повтор того же освежает `at`. Знакомство by_id с subject_id проверяет бот, служба выводит вес из равенства id.
- Этап 58: карточки переехали в таблицу `person_claims` на alfred (`people/claims.py` — чистая логика, `people/book.py::PeopleBook` — снимок на ход: имя карточка → Telegram → подписка; метки для `find_person`; подпись подписки владельца «me» в метки не идёт — технический ключ). Прозвищ на карточке не больше `MAX_ALIASES` (8), свежие вперёд: справка перед каждым ходом не должна разрастаться от болтливого знакомого.
- Перенос (`people/seed.py`, один раз, метки в `app_state`): `[[people]]` конфига — слово владельца (слабое утверждение с by_id = владелец, о себе — сильное); профили Telegram; карточки из графа этапа 54 — метка ставится только после ответа службы, иначе повтор (первая попытка через минуту после старта, дальше раз в 10 минут: связь поднимается не сразу, mycraft может спать).
- Граф-версия (`graph_memory/people.py`) остаётся на ограниченном наборе полей gender/name/alias и отвечает по протоколу службы; общие части (выбор победителя, публичный вид, таблица слов пола, вес) — из `people/claims.py`.
