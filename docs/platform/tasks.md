# Служба tasks (отложенные задачи роя)

Замена старого тула remind (писал готовый текст прямо в БД бота). Живая находка 2026-07-24: пользователь явно попросил отдельный сервис роя; задачи может ставить любой узел по протоколу.

Задача = `due_at` + протокольная команда (`dst_node`/`dst_service`/`action`/`args`) + `timeout_s` + непрозрачные `meta`. Служба `meta` не читает, только хранит и возвращает целиком в событиях `task_result`/`task_prewake` тому, кто создал задачу (обычно бот, `bot/node_events.py`: доставка в Telegram и запись в ai_turns остаются у него — у службы нет доступа ни к Telegram, ни к БД бота). Процесс обычно на той же ноде, что бот. Протокольные константы (`tasks/protocol.py`) живут отдельно и без импортов проекта, чтобы `bot/tools.py` мог их брать, не утягивая службу (цикл импортов service ↔ tools).

## Протокол

- `ACTION_CREATE` — создать задачу; поле `await_event` ждёт событие роя вместо времени.
- `ACTION_CHAT_LOOP` — не форвардится как обычная команда: служба прогоняет messages/tools/think через полный цикл tool-calling поверх llm.chat (`llm_chat.run_chat_loop`). Единственный «богатый» тип задачи, ради которого сервис и выделен: модель ставит такую задачу сама себе тулом remind. `meta.dialogue_id` обычно есть (задача продолжает свой тред); его отсутствие — проактивное первое сообщение чужому собеседнику (`bot/tools.py::schedule_agent_dialogue`, Этап 44.1, задел под агента установки связи 42.6); рождение нового dialogue_id — забота получателя `task_result` (`bot/node_events.py::_handle_task_result`, Этап 44.2).
- `ACTION_TIMER` — чистый будильник (Этап 45): исполнять нечего, на сроке сразу `task_result {ok: true, result: {}}` с meta заказчика. Нужен экспирации форм подтверждения (`bot/pending_actions.py`): срок живёт в персистентной очереди (переживает рестарт бота), решение «истекло ли на самом деле» бот принимает идемпотентно по своей БД. `dst_node`/`dst_service` формальность. `meta.kind` будильника — экспирация формы, `meta.pending_action_id` — id записи pending_actions.
- `ACTION_FIRE_NOW` — разбудить задачу раньше `due_at` по её id. Внутренний примитив, используется `match_event`, имя публичное (протокол). Идемпотентно: защита от двойного срабатывания — `fired_at IS NULL` в `get_pending_task`.
- `match_event` — ждать событие роя `(node, event_type)`: `remind(after_event=…)`. Матчинг живёт в службе, а не в боте (решение пользователя 2026-08-05, живой баг): задача-продолжение сама зовёт node_manage/remind из уже сработавшего хода (внутри службы, БД бота там нет), а именно оттуда чаще всего ставится следующее ожидание (обновил ноду → перезапустил → жду подтверждения → следующая). `due_at` остаётся страховкой по таймауту. Пара lookup + fire_now в одном RPC; waiter снимается при срабатывании (и по таймауту, и при ручном fire_now), чтобы строка не осталась мёртвой.
- События: `task_prewake {task_id, meta, status: waking|ready|failed, reason?}` — прогресс прогрева; `task_result {task_id, meta, ok, result?, error?}` — итог на `due_at`; `tool_call {name, args, result}` — факт вызова инструмента моделью внутри сработавшей chat_loop-задачи (для дебаг-уведомлений `bot/lifecycle.py::notify_tool_call`; живой баг 2026-08-05: раньше уходило только имя, кнопке «развернуть» нечего было показывать); `deliver_message {chat_id, html, plain, message_thread_id?}` — тулы tell/notify_guest внутри chat_loop-задачи (живой запрос 2026-08-06 «напомни мне как граф, что пора спать»). `html` уходит в Telegram, `plain` — для ai_turns получателя. Доставка fire-and-forget: round-trip в протокол не заведён (тот же компромисс, что у task_result), тул отвечает модели «передано» оптимистично.
- `meta.kind` — единственный вид, распознаваемый потребителями: результат нужно доставить в Telegram как ответ Альфреда, продолжающий диалог `meta.dialogue_id`.

## Прогрев и срабатывание

- Прогрев (`prewake_loop`) за `PREWAKE_LEAD_S` до `due_at`: если dst не отвечает или спит, будим его заранее (WoL-путь как `/wake`, `wake_core.py`).
- Живая находка 2026-07-27 (инцидент 19:34–19:39, напоминание не доставлено): прежняя схема (единственный прогрев + мгновенный отказ на сроке) на практике дала худшее из двух — WoL из службы не уходил вовсе (пустой кэш wake-реквизитов, `wake_core.resolve_wake_info`), 5 минут форы пропали, на сроке задача сдалась за 6 секунд. Решение пользователя 2026-07-27: фора 10 минут (холодный старт winpc + загрузка 35B-модели укладываются), на сроке служба сама будит цель и повторяет попытки до `FIRE_GRACE_S` после `due_at`. Напоминание, опоздавшее на десятки минут, вреднее молчания — тогда честное «пропущено». Решение 2026-07-24 «холодный старт не должен растягивать момент срабатывания» заменено этим.
- Прогрев помечается сразу (следующий тик через 30 с иначе повторит попытку, пока предыдущая идёт); на сроке `fire_loop` дожидается прогрева СВОЕЙ задачи, а не читает presence посреди него (находка 2026-07-27: задача со сроком меньше `PREWAKE_LEAD_S` падала при идущем прогреве). Не выходить за общий бюджет задачи ради одного ожидания WoL; потолок прогрева 360 с рассчитан на prewake.
- Если до срока ещё `PREWAKE_LEAD_S`, прогрев ждём целиком; при неудаче `failed` НЕ эмитится — на сроке будет ещё серия попыток.
- «Шаги» (`task_prewake waking`) показываем один раз на задачу (`_announce_waking`).
- Списание задачи сразу при старте исполнения: исполнение небыстрое (запрос к модели до `timeout_s`) и не должно попасть под повторный тик. Дефолт `timeout_s` — бюджет запроса к модели: chat_loop не укладывается в прежние 60 с.

## Права заказчика

Читаются из того же конфига, что у бота (подписки — часть Settings): БД бота службе недоступна. Резолв — в момент срабатывания по `meta["chat_id"]`, а не снимком при создании: если право отобрали, пока задача ждала, отложенный ответ им не воспользуется. Не оптимизировать в снимок. Живой баг 2026-08-06: без guest_subscriptions книга видела только владельца/семью — `guests_list` честно врал «гостей нет»; поэтому `app.py` строит книгу бота с двумя аргументами (конфиг + гостевой пакет). `emit` — мост для реальной отправки (`ai_tools.ToolContext.emit`): своего notifier у процесса нет, бот доставит по `EVENT_DELIVER_MESSAGE`.

Живой инцидент 2026-08-05: модель, разбуженная по событию, заново ставила remind на тот же `(node, event_type)` — `tool_remind` сверяет с `woken_by` и жёстко отказывает. Второй заход того же дня: без восстановления `message_thread_id` из meta цепочка теряла тред после первого self-scheduled прыжка.

Уровень рассуждения передаётся строкой `off|low|medium|high`; в службе llm его переводит профиль модели (`llm/model_profiles.py`). Старые задачи в БД могли хранить булев `think` (до v0.97.0) — маппится для совместимости.

## Недоступность

`_is_retryable_unavailable` (то же правило, что `bot/ai_flow.py`): решение пользователя 2026-08-05 — сбой «модель недоступна в моменте» не повод сразу сдаваться честным «не удалось найти Альфреда»; повторяем в рамках `due_at + FIRE_GRACE_S`, как прогрев/побудка (`_fire_chat_loop`). Детерминированные ошибки (плохой запрос, внутренний сбой модели) не повторяются — повтор их не лечит.

Сборка (`tasks/app.py`): `server` создаётся после `service`, `emit` замыкается на переменную и реально вызывается после `server.start()` (как в `node/app.py::run_node`, `llm/app.py::run_llm`); обработчики сигналов — до `start()`.
