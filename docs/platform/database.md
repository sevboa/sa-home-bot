# База данных (db/)

`Store` — единственный слой доступа к SQLite, голый SQL без ORM, поверх aiosqlite (`db/connection.py`: WAL, внешние ключи, транзакция — commit при успехе, rollback при исключении). Один класс `Store` обслуживает три БД: бота, tasks и monitor (у каждой службы своя БД и свои таблицы схемы; общая `schema.sql`).

## Миграции (db/migrations.py)

`CREATE TABLE IF NOT EXISTS` не подхватывает новые колонки уже существующей таблицы (прод-БД не пересоздаётся), поэтому довески оформляются через `ALTER TABLE` с проверкой наличия колонки (`_add_column_if_missing` возвращает True, когда колонка только что добавлена — можно бэкфиллить).

## Идемпотентность уведомлений

Флаги `notified_alert_at` / `notified_cleared_at` выставляются только после успешной отправки. Цикл перегрева: переход в alerting сбрасывает оба флага; отправка «перегрев» выставляет `notified_alert_at`; переход в ok сбрасывает `notified_cleared_at`; отправка «остыл» выставляет его. Реализация: `db/state_tables.StateTable` — одна логика для `health_states` и `host_metric_states` (INSERT при новом компоненте; UPDATE со сбросом флагов на переходе; без перехода флаги не трогаются). Различия таблиц заданы параметрами: у health при старте alerting `alerting_since` ставится в `now` (у host — берётся из состояния), чистка «призраков» у health ограничена видами, реально участвовавшими в скане (вид датчика, отключённый в конфиге, истории не лишается), у host чистится всё, чего нет в срезе (метрика пропала — ядро без PSI после апгрейда — не держим призрака в карточке ноды). Компонент, пропавший из среза, иначе висел бы в /status «призраком» навсегда.

## Прочее

- `ACTION_TICKS_PREFIX` — префикс ключей `app_state` с метками принятых ручных действий (лимитер), ключ — «служба:действие».
- `DISK_SUMMARIES_KEY` — кэш `DiskSummary` в `app_state`: пишет `SensorScanJob` раз в `scan_cron`, читает `MonitorService.get_state()` вместо живого опроса.
- Outbox (Этап 52, `bot/outbox.py`): виды `alert` (6 ч), `task` и `deliver_message` (24 ч), `interactive` (15 мин). Протухшее не доставляется («сервер упал 7 часов назад» уже не новость); неизвестный вид — как интерактивный (самый короткий TTL). Запись с тем же `(chat_id, dedup_key)` заменяется свежей. Время хранится ISO UTC с микросекундами, строки сравниваются как время.
- `update_state` — атомарное read-modify-write записи `app_state` через compare-and-set: `alfred_away` правят два процесса (бот и CLI). Поэтому `fn` — чистая функция, повторяется на свежем значении (до 8 попыток). Явный `BEGIN IMMEDIATE` не годится: соединение общее с остальными задачами бота, чужая незавершённая транзакция сломала бы его.
- `redeem_invite` — проверка и погашение одним UPDATE с условием: два сообщения с одним кодом приходят одновременно, «проверил, потом записал» дало бы двух гостей на один одноразовый код. `find_invite` возвращает код в любом состоянии (отличить код от случайной строки из восьми символов).
- `transition_pending_action` — атомарный переход статуса; None — строка не в ожидаемом статусе (уже решено, двойное нажатие, гонка с экспирацией): вызывающий ничего не публикует. `pending_actions_needing_delivery` — что должно было уйти в чат, но не ушло из-за рестарта (стадии определяет `bot/pending_actions.py::_undelivered_stages`; отмена самим инициатором оповещения не требует, истёкший черновик — требует).
- `get_pending_task` + `fired_at IS NULL` — защита `fire_now` от двойного срабатывания (см. tasks.md). `pop_event_waiter_for` удаляет строку, чтобы одно событие не разбудило задачу дважды.
- `set_ai_turn_content` правит и `ai_turns_fts` (триггер ловит только вставку; замена «ё» → «е» та же). FTS-поиск картинок (`search_images`): стемминга у FTS5 нет — у слова длиннее 4 букв отрезаются две последние и ищется префикс («драконом» → «драко*»), слова через OR, порядок bm25 (то же правило `utils.text.stem`). `get_image` отдаёт только картинки этого чата и из разговора — чужую и отладочную (/draw) по номеру не достать.
- `record_event` пишет уже отрендеренный текст события; подрезка — отдельным `prune_swarm_events` из housekeeping (как job_runs/invites).
- `host_trend`: бакет — час + десятка минут; `taken_at` хранится как `datetime.isoformat()` (с `T`), порог тоже считается в Python в том же формате — строковое сравнение корректно.
- `chat_participants` не включает старые записи без `user_id` (до миграции) — участники «подтянутся» новыми обращениями.
- `consume_item` (Этап 59.3): предмет исчезает из описи и мест, запись и журнал остаются.
