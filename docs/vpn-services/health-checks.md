# Проверки доступности (vpn_check)

## Идея
Pull/push (решение 2026-08-17): служба `vpn` только РАССЫЛАЕТ «проверь» через generic fan-out node-сервиса (`ACTION_TRIGGER_PEERS`) и не ждёт ответа; каждая `vpn_check` на своей ноде сама пушит результат (`report_check`) обратно — фанаутом на ВСЕ живые vpn-инстансы (иначе результат оседал бы в БД одной ноды). С 39.0.7 (2026-09-18) каждый инстанс vpn просит проверить ТОЛЬКО себя (`server=self._node`): не дублируется диспетчеризация N раз, и бесплатный heartbeat — упавший инстанс не рассылает «проверьте меня». Смерть хоста видна отдельно через `live_vpn_nodes()`/monitor, vpn_check отвечает на более узкий вопрос: «идёт ли реально трафик именно этого транспорта оттуда».
Каждый инстанс гоняет `reconcile_vpn_check` по своей копии данных, без координации: гистерезис-счётчики могут разойтись на 1–2 тика, событие `vpn_check_failed/recovered` иногда задвоится — принято осознанно (дешевле, чем «кто один вправе эмитить»). На чтение (`check_status`) не фанаутим: запись уже разлита по всем инстансам.
Отчёт по виду (упал/поднялся) — одно событие со списком сайтов, а не по событию на сайт (общий сбой туннеля раньше сыпал сообщение на сайт).

## Гистерезис
`domain/vpn_check.py::reconcile_vpn_check` — булевый ok/fail поверх общего `domain/hysteresis.py::reconcile_band` (неудача = полоса OVER, успех = UNDER): переход в alerting после `fail_threshold` подряд неудач, обратно после `clear_threshold` подряд успехов. Ключ строки: (node-наблюдатель, server, transport, target). `rollup_status` сводит статусы наблюдателей одной пары: все OK → OK, все ALERTING → ALERTING, иначе PARTIAL («доступно частично», оранжевый индикатор, решение 2026-09-18). Цвет считается по ВСЕМ строкам пары (недостижимая цель у одного наблюдателя уже делает картину неоднородной), а наблюдатели считаются по узлам, не по строкам («observers: 4» при двух наблюдателях — находка деплоя 0.109.0).
Устаревание (`CHECK_STALE_FACTOR` = 3 интервала): наблюдатель может замолчать, не сказав ни слова (нода умерла/ушла из роя/потеряла интернет), а запись останется навсегда; зелёный от мертвеца хуже отсутствия индикатора. Три интервала, а не один — пропущенный тик это джиттер (пробник поднимает тоннель на время цикла). Для telegram_egress строка не прячется, а помечается `stale`.

## Слоты и туннели
Слот = пара (сервер, транспорт), настроенная на ЭТОЙ ноде (`node/vpn_probe_state.py`, пишет `node/fixups.py::make_vpn_probe_state_fixup` при `nodectl fix`; пусто — служба ничего не проверяет). Диспетчер шлёт одно имя сервера; если у ноды к нему настроено несколько транспортов, проверяются все, в один `report_check` — по строке на (сервер, транспорт, цель). Слоты одного сервера идут последовательно (эфемерный подъём — всплеск нагрузки; решение 2026-09-18 «не грузить машины»). Self-check исключён (сервер не проверяет сам себя — нет сигнала о видимости извне).
netns + veth + NAT заводит `node/fixups.py` и они переживают ребут (без физического интерфейса handshake/xray некуда выйти — находка 2026-08-17). САМ туннель (awg-quick / xray-клиент) эфемерный: поднимается перед пачкой слота и гасится в `finally`.
- awg: `awg-quick up`; гейт: маршрут `ip route get <литерал>` идёт через туннель (с ретраями — хендшейк не мгновенен; общее ожидание укладывается в `check_timeout_s`) + внешний IP из netns отличается от IP хоста (кроме самой VPN-ноды, где совпадение неизбежно).
- reality: xray-клиент — долгоживущий, запускается фоном под `timeout <окно>` (страховка, если sudo не пробросит SIGTERM; окно = `check_timeout_s` + 10 с), пауза после спавна даёт SOCKS слушать порт (значение 0.5 с не проверено по живым данным). Маршрут не переписан — гейт только по exit-IP через SOCKS. curl идёт с `--socks5-hostname` (имя резолвит сервер, как у настоящих клиентов): с голым `--socks5` DNS шёл через хост мимо туннеля, и сбой DNS/интернета у провайдера alfred (2026-10-06 04:50–06:20) выглядел как падение reality на всех VPN.
Гейт нужен, чтобы проверка не зеленела тихо мимо VPN (инцидент 2026-08-31): провал гейта помечает все цели одной внятной ошибкой. Одна строка журнала на прогон туннеля (иначе сбой не разобрать задним числом). Ошибки останова только логируются. Не удалось узнать exit-IP хоста — не тема проверки, реальные цели покажут сбой. `ip` резолвится при каждом вызове (чтобы `nodectl fix` после старта подхватился), `curl` внутри `netns exec` остаётся литералом — как в sudoers-правиле.

## HEAD вместо GET
Проверке нужен только код ответа; GET заставляет curl принять тело целиком. С добавлением google/youtube/instagram/discord (2026-09-20) каждый слот тянул ~1.5 МБ за цикл; замер youtube через туннель: 1247 мс / 870 КБ на GET против 657 мс / 0 КБ на HEAD; ×8 слотов ×12 циклов/час — порядка 100 ГБ в месяц трафика по VPN-серверам, прямо в лимит `node_limit_gb`. 405/501 — «метод не поддержан»: цель жива, повторяем GET. `http_code` внутренний, в отчёт не уходит.
Права: «a password is required»/локализованное «sudo:» → подсказка `nodectl fix` (`looks_like_sudo_denied` / `looks_like_sudo_message` из `utils/requirements.py`: вторая не зависит от локали ноды).
