# Проверки доступности (vpn_check)

## Идея
Pull/push (решение 2026-08-17): служба `vpn` только РАССЫЛАЕТ «проверь» через generic fan-out node-сервиса (`ACTION_TRIGGER_PEERS`) и не ждёт ответа; каждая `vpn_check` на своей ноде сама пушит результат (`report_check`) обратно — фанаутом на ВСЕ живые vpn-инстансы (иначе результат оседал бы в БД одной ноды). С 39.0.7 (2026-09-18) каждый инстанс vpn просит проверить ТОЛЬКО себя (`server=self._node`): не дублируется диспетчеризация N раз, и бесплатный heartbeat — упавший инстанс не рассылает «проверьте меня». Смерть хоста видна отдельно через `live_vpn_nodes()`/monitor, vpn_check отвечает на более узкий вопрос: «идёт ли реально трафик именно этого транспорта оттуда».
Каждый инстанс гоняет `reconcile_vpn_check` по своей копии данных, без координации: гистерезис-счётчики могут разойтись на 1–2 тика, поэтому `vpn_check_failed/recovered` приходит от каждого инстанса. Находка 2026-11-07: задвоение было не «иногда», а почти всегда (за 5 дней 46 из 46 оповещений zakhar и 19 из 32 alfred). Бот показывает и записывает одно и то же событие проверок и серий один раз за `VPN_EVENT_DEDUP_S` (120 с, `bot/node_events.py`, ключ без поля `active`). Эмитят по-прежнему все инстансы: иначе упавший сервер оставил бы админов без оповещений. Если счётчики инстансов разошлись на тик и больше, дубль остаётся: окно короче интервала проверок намеренно. Событие `vpn_check_recovered` несёт `active`: всё, что сейчас в alerting у этого инстанса, без устаревших наблюдателей, сгруппировано по (наблюдатель, сервер, транспорт); `whole` значит, что в группе не работает ничего. Бот выводит это блоком «Ещё не работает» или строкой «Других проблем нет» (решение владельца 2026-11-07: «восстановилось» не должно выглядеть как «всё хорошо»); от старой ноды без `active` текст прежний. На чтение (`check_status`) не фанаутим: запись уже разлита по всем инстансам.
Отчёт по виду (упал/поднялся) — одно событие со списком сайтов, а не по событию на сайт (общий сбой туннеля раньше сыпал сообщение на сайт).

## Гистерезис
`domain/vpn_check.py::reconcile_vpn_check` — булевый ok/fail поверх общего `domain/hysteresis.py::reconcile_band` (неудача = полоса OVER, успех = UNDER): переход в alerting после `fail_threshold` подряд неудач, обратно после `clear_threshold` подряд успехов. Ключ строки: (node-наблюдатель, server, transport, target). `rollup_status` сводит статусы наблюдателей одной пары: все OK → OK, все ALERTING → ALERTING, иначе PARTIAL («доступно частично», оранжевый индикатор, решение 2026-09-18). Цвет считается по ВСЕМ строкам пары (недостижимая цель у одного наблюдателя уже делает картину неоднородной), а наблюдатели считаются по узлам, не по строкам («observers: 4» при двух наблюдателях — находка деплоя 0.109.0).
Устаревание (`CHECK_STALE_FACTOR` = 3 интервала, длина интервала зависит от способа, см. «Проверки без роботного ритма»): наблюдатель может замолчать, не сказав ни слова (нода умерла/ушла из роя/потеряла интернет), а запись останется навсегда; зелёный от мертвеца хуже отсутствия индикатора. Три интервала, а не один — пропущенный тик это джиттер (пробник поднимает тоннель на время цикла). Для telegram_egress строка не прячется, а помечается `stale`.

## Слоты и туннели
Слот = пара (сервер, транспорт), настроенная на ЭТОЙ ноде (`node/vpn_probe_state.py`, пишет `node/fixups.py::make_vpn_probe_state_fixup` при `nodectl fix`; пусто — служба ничего не проверяет). Диспетчер шлёт одно имя сервера; если у ноды к нему настроено несколько транспортов, проверяются все, в один `report_check` — по строке на (сервер, транспорт, цель). Слоты одного сервера идут последовательно (эфемерный подъём — всплеск нагрузки; решение 2026-09-18 «не грузить машины»). Self-check исключён (сервер не проверяет сам себя — нет сигнала о видимости извне).
netns + veth + NAT заводит `node/fixups.py` и они переживают ребут (без физического интерфейса handshake/xray некуда выйти — находка 2026-08-17). САМ туннель (awg-quick / xray-клиент) эфемерный: поднимается перед пачкой слота и гасится в `finally`.
- awg: `awg-quick up`; гейт: маршрут `ip route get <литерал>` идёт через туннель (с ретраями — хендшейк не мгновенен; общее ожидание укладывается в `check_timeout_s`) + внешний IP из netns отличается от IP хоста (кроме самой VPN-ноды, где совпадение неизбежно).
- reality: xray-клиент — долгоживущий, запускается фоном под `timeout <окно>` (страховка, если sudo не пробросит SIGTERM; окно = `check_timeout_s` + 10 с), пауза после спавна даёт SOCKS слушать порт (значение 0.5 с не проверено по живым данным). Маршрут не переписан — гейт только по exit-IP через SOCKS. curl идёт с `--socks5-hostname` (имя резолвит сервер, как у настоящих клиентов): с голым `--socks5` DNS шёл через хост мимо туннеля, и сбой DNS/интернета у провайдера alfred (2026-10-06 04:50–06:20) выглядел как падение reality на всех VPN.
Гейт нужен, чтобы проверка не зеленела тихо мимо VPN (инцидент 2026-08-31): провал гейта помечает все цели одной внятной ошибкой. Одна строка журнала на прогон туннеля (иначе сбой не разобрать задним числом). Ошибки останова только логируются. Не удалось узнать exit-IP хоста — не тема проверки, реальные цели покажут сбой. `ip` резолвится при каждом вызове (чтобы `nodectl fix` после старта подхватился), `curl` внутри `netns exec` остаётся литералом — как в sudoers-правиле.

## HEAD вместо GET
Проверке нужен только код ответа; GET заставляет curl принять тело целиком. С добавлением google/youtube/instagram/discord (2026-09-20) каждый слот тянул ~1.5 МБ за цикл; замер youtube через туннель: 1247 мс / 870 КБ на GET против 657 мс / 0 КБ на HEAD; ×8 слотов ×12 циклов/час — порядка 100 ГБ в месяц трафика по VPN-серверам, прямо в лимит `node_limit_gb`. 405/501 — «метод не поддержан»: цель жива, повторяем GET. `http_code` внутренний, в отчёт не уходит.
Права: «a password is required»/локализованное «sudo:» → подсказка `nodectl fix` (`looks_like_sudo_denied` / `looks_like_sudo_message` из `utils/requirements.py`: вторая не зависит от локали ноды).

## Серийная проверка: ядро замера (Этап 63.1.1, 2026-11-03)
`vpn_series/measure.py::classify` — чистая функция над рядом samples `(t, bytes)` скачивания через туннель слота; `vpn_check` не затронут. Результат `SeriesResult`: `bytes_total`, `duration_s`, `stalled_at_bytes`, `max_idle_s`, `kbps`, `verdict`. Вердикты: `cut` — curl exit 18/56 при 10–30 КБ полученных (обрыв TCP после 15–20 КБ, признак ТСПУ); `error` — нет ни байта или иной ненулевой exit (0 и 28 терпимы: 28 — таймаут `--max-time` при заморозке); `freeze` — после первых байт поток стоял ≥ `freeze_idle_s`; `slow` — скорость ниже `min_kbps` (кбит/с); иначе `ok`. Простой считается от последнего прироста байт, до первого байта не учитывается.

## Серийная проверка: раннер (Этап 63.1.2, 2026-11-03)
`vpn_series/runner.py` — сборка `curl` argv (netns exec, socks5 для reality), стриминг stdout с тиками `tick_s` и дедлайном `duration_s + 5`, агрегация в `classify`. `run_single` — одиночный прогон; `run_burst` — `burst_connections` параллельных прогонов через `asyncio.gather`. Конфиг `[vpn_series]`: `url` (файл 200 МБ), `duration_s`, `burst_connections`, `freeze_idle_s`, `min_kbps`, `tick_s`. Дефолты подобраны под 2–3 минуты замера и 6 параллельных соединений.

## mtg_probe (vpn_series)

`src/sa_home_bot/vpn_series/mtg_probe.py::mtg_probe` проверяет прокси mtg на сервере с ноды-пробника: доходит ли TCP до порта и проходит ли TLS-хендшейк с SNI маскировки (`www.microsoft.com`). Ключи mtg не нужны и не читаются. Вердикты: `ok` (TCP и TLS прошли), `tcp_blocked` (TCP не доходит), `tls_blocked` (TCP есть, но TLS-хендшейк упал/завис — признак реза fake-TLS ТСПУ).

## mtproto_probe (vpn_series)

`src/sa_home_bot/vpn_series/mtg_probe.py::mtproto_probe` — настоящая проверка MTProto через fake-TLS
прокси mtg (2026-11-20): полный путь клиента Telegram — fake-TLS рукопожатие с секретом mtg
(hex или urlsafe base64 без паддинга, первый байт 0xee), obfuscated2-инициализация и запрос
`req_pq_multi` к дата-центру (`dc`, по умолчанию 2) с проверкой ответа `resPQ` и тем же nonce. В
отличие от `mtg_probe`, отличает живой прокси от сайта-маски, который лишь отвечает на TLS.

Вердикты `MtprotoProbeResult`: `ok` (TCP, рукопожатие и resPQ с тем же nonce прошли), `tcp_blocked`
(TCP не доходит), `tls_failed` (нет ServerHello: тип записи не 0x16, EOF или таймаут — признак реза
fake-TLS ТСПУ), `mtproto_failed` (ответ не resPQ, nonce не совпал, EOF или таймаут после
рукопожатия). Замеры: `tls_ms` (рукопожатие), `total_ms` (весь прогон); ошибка в `error`.

Проверка детерминирована для тестов: случайность и время передаются параметрами в чистые функции
(`parse_faketls_secret`, `build_client_hello`, `obfuscated2_init`). Пока вызывается вручную;
подключение к `vpn_check` будет отдельной задачей.

## Серийная проверка: действие series (63.1.4, 2026-11-03)

Действие `series` живёт **внутри** службы `vpn_check` (не отдельная служба). Причина: тот же netns пробника, иначе `vpn_check` и серия гасят друг другу туннель. Существующее поведение `check` (формат, тексты, отчёт `report_check`, события) **не меняется** — только добавляется действие и замок на слот.

### Замок слота
`self._slot_locks: dict[str, asyncio.Lock]` (ключ — `slot.netns`). Метод `_check_slot` целиком выполняется под этим замком (единственная правка существующего пути — обернуть тело в `async with`). `_series_slot` тоже берёт тот же замок. Это гарантирует, что `check` и `series` по одному слоту не пересекаются.

### Лёгкий режим по умолчанию
- Серия 30 с, файл 20 МБ (`url = "https://speed.cloudflare.com/__down?bytes=20000000"`, `duration_s = 30.0`).
- По расписанию — одиночная серия раз в 3 ч (`interval_s = 10800.0`).
- Залп (`burst`) — только по команде.
- Расписание выключено по умолчанию (`enabled = false`), включается только в конфиге zakhar:
  ```toml
  [vpn_series]
  enabled = true
  ```

### Действия
- `series` — параметры `server`, `mode` = `single`|`burst`. Проверки `server` как у `check` (self-check и «нет слота» — `accepted` + `skipped`), неизвестный `mode` → `ProtoError(ERR_BAD_REQUEST, ...)`. Запускает фоновую задачу `_series_run(server, slots, mode)`, сразу возвращает `{"accepted": true, "server": ..., "mode": ...}`.
- `series_status` — без параметров, возвращает `{"results": self._series_last}` (последний результат по ключу `"<server>/<transport>"`).

### Процесс `_series_slot`
Под замком слота:
1. Для reality цель TCP — `reality_target(reality_conf_path(slot).read_text())`, ошибка чтения → `target=None`.
2. `raw_probe` с `do_handshake`, который поднимает туннель (`_tunnel_up`) и делает `_egress_gate`, **БЕЗ гашения**.
3. Если вердикт `ok` — `run_single` или `run_burst`; иначе серия не запускается.
4. `finally` — `_tunnel_down`.

Результат: `{"server","transport","mode","raw": RawProbeResult.model_dump(mode="json"), "series": [SeriesResult.model_dump(mode="json"), ...], "at": utc_now().isoformat()}`.

### Расписание
Метод `async def series_loop(self)` — бесконечно: `asyncio.sleep(interval_s)`, затем `_series_run` по каждому серверу слотов в режиме `single` (исключения логировать, цикл не падает). Запуск в `vpn_check/app.py`: `asyncio.create_task(service.series_loop())` только при `settings.vpn_series.enabled`, отмена задачи в `finally`.

### Отчёт в vpn (63.1.5, 2026-11-03)
После прохода по слотам `_series_run` одним вызовом шлёт `report_series {node, results}` во все живые
инстансы `vpn` (`vpn_nodes.fanout`, общий с `report_check` хелпер `_report_to_vpn`). Если ни один слот
не дал результата (все упали исключением), отчёт не шлётся.

Приём — `vpn/checks.py::_report_series`. Вердикт пары (сервер, транспорт) —
`domain/vpn_series.py::series_verdict`: не-`ok` вердикт TCP-части (`tcp_blocked`, `proto_blocked`)
важнее серии; иначе первый из `freeze`/`cut`/`error`; `slow` считается рабочим (медленно, но живо —
блокировкой не считаем). Гистерезис тот же `reconcile_band`, пороги отдельные от `check_*`:
`[vpn] series_fail_threshold = 2`, `series_clear_threshold = 1` — при расписании раз в 3 ч алерт
приходит не раньше чем через ~6 ч от начала поломки, зато одна случайная заморозка не будит.

Состояние — таблица `vpn_series_states` (ключ node, server, transport; `last_report` — JSON отчёта
целиком, для строки `/vpn` в 63.1.6). `vpn_check_states` не трогается. События:
`vpn_series_failed {node, server, transport, verdict, consecutive}` и
`vpn_series_recovered {node, server, transport}`; `at_bytes` — где встала первая сломанная серия
(`stalled_at_bytes`, иначе `bytes_total`).

### Показ (63.1.6, 2026-11-03)
Алерт админам — `bot/node_events.py::render_vpn_series`, отдельно от `render_vpn_check` (его тексты не
менялись). `check_status` у vpn теперь отдаёт ещё `series` — строки `vpn_series_states`; экран
«проверка доступности» `/vpn` рисует блок «🇷🇺 Из РФ» только если строки есть: 🔴 — в алерте
(гистерезис), 🟠 — последний замер плохой, но порог ещё не пройден, 🟢 — работает. Без данных серий
экран байт в байт прежний. В снапшот бэкапа
таблица не входит (оперативные данные, как `vpn_check_states`).

## Проверка SNI-кандидатов (63.2.2, 2026-11-03)

### Зачем
Reality маскируется под чужой домен (SNI). Если ТСПУ режет этот домен или он не отдаёт TLS 1.3 + h2,
маскировка выдаёт себя. Нужна проверка списка кандидатов прямо с zakhar (РФ), без VPN-туннеля.

### Вердикты
- `ok` — DNS резолвится, TCP соединяется, TLS 1.3, ALPN h2.
- `dns_fail` — `getaddrinfo` не нашёл домен.
- `tcp_fail` — TCP не дошёл (timeout, connection refused, др. OSError до TLS).
- `tls_fail` — TLS-хендшейк упал (`ssl.SSLError`) или нет `ssl_object`.
- `no_tls13` — хендшейк прошёл, но версия не TLSv1.3.
- `no_h2` — TLS 1.3 есть, но ALPN не `h2` (обычно `http/1.1`).

### Действие
`vpn_check.sni_probe` — параметр `domains` (строка через запятую или список, макс. 30 доменов).
Валидация: только `[a-z0-9.-]`, есть точка. Туннели и замки слотов **не трогает** — проверка идёт
с хоста напрямую.

### Пример
```bash
nodectl -n zakhar call vpn_check sni_probe domains=www.google.com,dl.google.com
```

### Ответ
```json
{
  "results": [
    {"domain": "www.google.com", "verdict": "ok", "ms": 42, "error": null},
    {"domain": "dl.google.com", "verdict": "no_h2", "ms": 38, "error": "ALPN: http/1.1"}
  ]
}
```

### Ограничение
Проверка отвечает «домен сам по себе жив из РФ и годится как маска (TLS 1.3 + h2)». Она не
доказывает, что ТСПУ пропустит Reality на НАШ IP с этим SNI — это видно только серией 63.1 после
выката нового SNI (63.2.3). Таймаут всего TLS-хендшейка считается `tcp_fail` (DPI часто именно
молча тянет время), DNS ограничен тем же таймаутом. Домены приводятся к нижнему регистру,
кириллические (IDN) не принимаются — передавайте punycode.

## Уровень связки и устойчивый переход (65.1, 2026-11-11)
Единица оповещения — связка (наблюдатель, сервер, транспорт), а не сайт: уровень считается по всем
целям связки сразу — `domain/vpn_link.py::link_level` (нет плохих → `ok`, плохи все → `down`, иначе
`partial`). Оповещаем только по устойчивому уровню: `reconcile_link` держит уровень-кандидат,
пока он не продержится `threshold` отчётов подряд; прерванный ряд обнуляет счётчик, поэтому дребезг
не даёт ни одного оповещения. Объявляется только достижение края `ok` или `down` — устойчивый
`partial` не объявляется, значит постепенное падение через `partial` даёт одно оповещение в конце.
Первый отчёт связки молчит: он лишь задаёт объявленный край.

Состояние связки — таблица `vpn_link_states` (ключ node, server, transport; level — устойчивый
уровень, candidate — уровень-кандидат, candidate_count — длина ряда, announced — объявленный край).
Ведёт её служба при приёме отчёта: `vpn/checks.py::_apply_link_report` — уровень по всем целям
связки, `reconcile_link`, запись строки и событие `vpn_link_changed {node, server, transport, from,
to, bad_targets, total}` только при устойчивом переходе края. Настройки `[vpn]`:
`link_stable_threshold` (3), `ignored_observers` (состояние пишется, события нет),
`check_target_events` (false выключает `vpn_check_failed/recovered`; оставлено выключателем, чтобы
вернуть старую схему одной строкой конфига).

### Охваты и авария (65.2, 2026-11-12)
Охват `russia` — наблюдатели из `[vpn] russia_observers`, `global` — все прочие, кроме
`ignored_observers`. Уровень охвата по серверу: `ok`, если жива хотя бы одна связка, `down`, если
все лежат, иначе `partial`; устаревшие строки связок (старше порога свежести) в охват не входят.
Событие `vpn_outage {scope, server, from, to, scopes}` — охват вошёл в `down` или вышел из него;
оно заменяет `vpn_link_changed` той же пары (охват, сервер) в том же отчёте. `vpn_link_changed`
несёт `scope` и `scopes`. Действие `check_scopes` → `{scopes, russia, ignored, links}` (`russia` и `ignored` — списки наблюдателей из конфига, по ним бот раскладывает историю по охватам).

### История замеров (65.5, 2026-11-12)
На каждый принятый отчёт служба пишет по строке истории на связку (наблюдатель, сервер,
транспорт) — таблица `vpn_check_samples`: `total` целей, `bad` плохих, `median_ms` — медиана
задержки здоровых целей (`domain/vpn_history.py::median_ms`). Строка пишется в
`vpn/checks.py::_record_sample` сразу после `_apply_link_report`. Старше
`[vpn] samples_keep_days` (14) история удаляется в цикле проверок (`_prune_samples`).

Действие `check_history {hours, bucket_min}` → `{hours, bucket_min, series}`: история за окно,
сжатая по интервалам времени (`domain/vpn_history.py::aggregate`, группировка по
(server, transport, node), точки по интервалам с `reports/down/partial/median_ms`). Точки
сжимаются, потому что сообщение роя ограничено 1 МиБ: 14 дней по 15-минутным интервалам на
каждую связку — десятки тысяч точек, в одно сообщение они не помещаются. `hours` и `bucket_min`
не целые → `ProtoError(ERR_BAD_REQUEST, ...)`; значения ограничиваются отрезками
1 … `samples_keep_days * 24` и 1 … 1440, чтобы окно не вышло за хранящуюся историю.

### Слои «сеть» и «нода» (65.8, 2026-11-12)

Луковица из трёх слоёв: сеть → нода → VPN. Оповещение называет самый внешний сломанный слой и глушит
всё, что под ним. Все три слоя идут одним событием `vpn_outage` с полем `layer` (`net`, `node`, `vpn`):
подписки менять не нужно. С 2026-11-22 подписка владельца исключает `vpn_outage`, `vpn_series_*` и
`vpn_check_*`, проверки VPN идут только в группу «КиберАльфред». Состояние слоёв — таблица
`vpn_layer_states`, устойчивость считает тот же `reconcile_link`, что у связок.

**Сеть.** Сервер кладёт в команду проверки свой адрес и порт Reality (`net_target`), наблюдатель
запоминает его в памяти и перед подъёмом туннелей пробует TCP до этого порта: `curl` в netns
Reality-пробника (маршрут там прямой, права sudo уже есть), ответ — `%{time_connect}` больше нуля.
Результат идёт в отчёте полем `net: {сервер: {ok, ms, error}}`. Служба `vpn` ведёт состояние на пару
(наблюдатель, сервер) и сводит его в охват так же, как связки: охват `down`, когда сервер не отвечает
всем наблюдателям охвата. Порог — `link_stable_threshold` отчётов. Пока в отчёте `net.ok = false`,
счётчики связок этого наблюдателя к серверу стоят (строка лишь освежается), замер в историю пишется.

Находка 2026-11-12: взять адрес из конфига пробника нельзя — файл принадлежит root, служба наблюдателя
его не читает (`_reality_raw_target` в проде возвращает `None`). Поэтому адрес передаёт сервер.
Наблюдатель без Reality-пробника к серверу или старой версии поле `net` не шлёт — слой для него
неизвестен и ничего не глушит.

**Нода.** Каждая служба `vpn` в цикле проверок смотрит, отвечают ли рою службы `vpn` других серверов
(серверы берутся из связок, обновлявшихся за последние сутки). Молчащему серверу она сама рассылает
проверки от его имени — иначе слои «сеть» и VPN по нему стало бы нечем мерить. Порог слоя «нода» на
один проход больше, чем у сети: если сервер лёг целиком, слой «сеть» успевает объявиться первым, и
«нода недоступна» не шлётся (флаг `notified`: восстановление сообщается только там, где сообщали
поломку). Пока слой «нода» объявлен сломанным, счётчики связок к этому серверу стоят. Служба, которая
сама не видит себя в рое, соседей не судит. При рассылке от чужого имени `net_target` не передаётся —
наблюдатель берёт запомненный; после перезапуска наблюдателя при лежащем сервере слой «сеть» неизвестен
и оповещение будет «нода недоступна».

**Сайт, недоступный отовсюду.** Цель, которая не открылась ни через одну рабочую связку (рабочих связок
не меньше двух, игнорируемые наблюдатели не в счёт), в уровень связки и в замер не входит. Такие цели
пишутся в `vpn_resource_states` и отдаются в `check_scopes` полем `resources` за последние сутки.

`check_scopes` отдаёт `scopes` уже с учётом внешних слоёв (сломанная сеть или нода делает сервер
`down`) и `layers` — три слоя на каждый сервер по каждому охвату.

### Домен ставит сервер (2026-11-22)

Конфиги пробников `/etc/sa-home-bot/vpn-probe/*.json` принадлежат root и имеют права 0600, служба
`vpn_check` их не читает: `PermissionError` (это `OSError`) молча даёт `sni=None`, и наблюдатель
присылал `Reality` / `XHTTP` без домена. Поэтому `vpn/checks.py::_report_check` для строк своего

`probe_entry_name`: `reality` берёт `[vpn.reality].sni`, `reality_alt` — `[vpn.reality.alt].sni`,
`reality_xhttp` — `[vpn.reality.xhttp].sni`. Серверное имя приоритетнее присланного; если секции
нет (или транспорт awg/awg_alt), остаётся присланное наблюдателем.

Второй путь, для строк соседних серверов (бот читает `check_status` с одной ноды, а там строки по
всем серверам): SNI лежит в слоте. `ProbeSlot.sni` (необязательное, `node/vpn_probe_state.py`)
пишется в `/etc/sa-home-bot/vpn-probe-state.json` (0644, служба читает), старый файл без поля
читается как раньше. Фикс-ап `vpn-check-probe-state` перед проверкой и записью берёт SNI из
root-конфига reality-слота через `sudo cat`, поэтому `nodectl fix` дописывает `sni` в state на
уже настроенных нодах без перевыпуска ключей. Наблюдатель сначала берёт `slot.sni`, потом, как
раньше, пробует прочитать конфиг слота. Серверная подстановка для своих строк остаётся.

Суффикс растёт, пока не найдётся имя, которого нет среди активных. Обычные цветы без суффикса,

### Почему копятся лишние пробники

Нужно 6 наблюдателей × 5 транспортов = 30 пиров chat 0 на сервер, активных больше. Причина:
`probe_tunnel._fetch_probe_config` вызывает `ACTION_ISSUE` с `chat_id=0` и транспортом, но без
`device_label`, поэтому каждый вызов создаёт новый пир со случайным именем. Прежний пир не
отзывается: у chat 0 нет привязки «наблюдатель + слот» к пиру, а перевыпуск (`_reissue`) идёт по
имени устройства, которого фикс-ап не передаёт. Новый ISSUE происходит каждый раз, когда
конфиг слота нужно получить заново:

- awg и awg_alt: конфиг устарел (`probe_conf_stale`: ключ сервера сменился или конфиг пуст);
- reality, reality_alt, reality_xhttp: файла `/etc/sa-home-bot/vpn-probe/*.json` нет (переезд
  слота на другой индекс, восстановление ноды, ручное удаление);
- каждый новый наблюдатель и каждый переустановленный наблюдатель.

Старые пиры остаются активными, так как ни один путь не знает, чей они. Лечение требует стабильной
идентичности пробника (например, `device_label = probe-<наблюдатель>-<транспорт>` с перевыпуском
по нему либо уборка неиспользуемых пиров chat 0 по сроку), это отдельная задача и в этом коммите не
делается.

### Правило
- Линия на каждую пару (транспорт, наблюдатель), `ChartPanel.lines` ключуется `(transport,
  observer)`. Цвет задаёт транспорт, стиль — наблюдатель: сплошная, пунктир, точки, штрих-точка
  (по кругу). Стиль берётся по позиции наблюдателя в отсортированном списке наблюдателей охвата
  (`ChartPanel.observers`), поэтому одинаков на всех панелях охвата. Провал (2 с и выше) считается
  по данным самого наблюдателя: все его отчёты отрезка плохие. Строки провала в верхней полосе
  сдвинуты по транспорту и чуть по наблюдателю.
- Легенда: цвета транспортов (с `entry`), затем отдельный блок «стиль → наблюдатель», если у охвата
  больше одного наблюдателя. Элементы переносятся на следующую строку по ширине холста.
- Плашка «частично»: наблюдатель «слепой» на сервере, если за окно по всем транспортам не прошло
  больше половины его отчётов (`BLIND_SHARE = 0.5`, `observer_verdicts`). Если в охвате есть и
  слепые, и зрячие наблюдатели, а служба дала `ok`, плашка — «частично». Если слепы все,
  остаётся уровень службы (`down`). Только бот, логика службы `vpn`/`vpn_check` и алерты не менялись.
- Подпись: для сервера, где наблюдатели охвата расходятся, добавляется строка
  `🇷🇺 🇳🇱 jeeves: vanka — недоступен 24 ч, osip — работает` (время — отрезки, где все отчёты
  наблюдателя плохие). Идёт перед строками эпизодов; когда наблюдатели согласны, подпись прежняя.
- Эпизоды «нет связи» и «лучшее подключение» считаются как раньше (слитые наблюдатели охвата).

## Проверки без роботного ритма (решение владельца 2026-11-23)

Зачем. Российские наблюдатели (osip, vanka, zakhar) раньше каждые ровно 300 с пачкой ходили ко всем серверам всеми способами. Такой метроном и пачка одинаковых соединений к одним и тем же адресам с одних и тех же адресов хорошо видны ТСПУ/СОРМ и выдают нас как робота. Владелец согласился проверять реже и вразнобой.

Что изменилось.
- Интервал раунда: `check_interval_s + random.uniform(0, check_jitter_s)`, по умолчанию 900 + до 300 с, то есть раунд раз в 15–20 минут (было 300 с). Считает сервер `vpn` в `ChecksMixin.check_loop`; у каждого инстанса vpn (каждый просит проверить только себя) разброс свой, поэтому раунды разных серверов не синхронны.
- Порядок вразнобой. Диспетчер шлёт наблюдателям одно задание на сервер (фанаут `trigger_peers`), список слотов у наблюдателя свой, поэтому перемешивание и паузы сделаны на наблюдателе (`VpnCheckService._run_and_report`): слоты (способы) идут в случайном порядке (`random.sample`), цели каждого слота тоже в случайном; перед каждым слотом пауза `uniform(0, spread_s / число_слотов)`, в сумме не больше `spread_s` = `CHECK_SPREAD_RATIO` (0,5) от `check_interval_s`, то есть первая половина интервала. Пауза на сервере не годится: он не знает слотов наблюдателей и не может разнести их по одному, а задержка доставки заданий размазала бы только момент старта, но не пачку внутри наблюдателя. Параметры расписания сервер кладёт в аргумент `schedule` (`spread_s`, `awg_min_s`, `awg_max_s`) только в плановом раунде; ручной `check_now` и внеплановая проверка упавшей ноды идут без него: все слоты, без пауз, сразу. Старый наблюдатель аргумент игнорирует и проверяет всё как раньше.
- AWG редко. Способы из `AWG_PROBE_TRANSPORTS` (`awg`, `awg_alt`) проверяются не каждый раунд: для каждой пары (наблюдатель, сервер, способ) наблюдатель помнит в памяти момент следующей проверки и после проверки назначает его через `uniform(awg_check_min_s, awg_check_max_s)` (1–3 ч). Слот, которому ещё не пора, пропускается целиком: в отчёт не попадает, состояния (`vpn_check_states`, `vpn_link_states`, выборки) не трогаются, `recovered`/`failed` не шлются, провалом это не считается. Если из слотов задания пора только AWG-слотам нет, ответ `skipped`. После рестарта наблюдателя первая проверка AWG идёт в ближайший раунд.
- Устаревание считает одна функция `vpn/service_common.py::stale_after_s(cfg, transport)`: для AWG `awg_check_max_s * CHECK_STALE_FACTOR`, для остальных `(check_interval_s + check_jitter_s) * CHECK_STALE_FACTOR`. Строки с транспортом (`vpn_check_states`, `vpn_link_states`) фильтруются по ней поштучно через `_fresh_clause`; слои сети и ноды и telegram_egress считаются как не-AWG.
- Суточный отчёт (`bot/vpn_daily.py`): порогов по числу проб в нём нет, редкие точки AWG дают пустые корзины (`None`), а не провалы. Но при раунде 15–20 минут и корзине 15 минут одна пустая корзина стала обычным делом, и `_runs` рвал бы затянувшийся сбой на куски; теперь одна пустая корзина внутри сбоя «мостится» (`MAX_BRIDGED_EMPTY_SLOTS` = 1), две и больше пустых подряд сбой заканчивают, как раньше.

Цена. Аварии замечаются позже: гистерезис `check_fail_threshold = 2` считается по раундам, то есть оповещение о сбое приходит через 30–40 минут вместо 10, а сбой только AWG виден через 1–3 часа (и подтверждается ещё на одной проверке, то есть до нескольких часов). `link_stable_threshold` и серии (`vpn_series`) не менялись.

Поля `[vpn]`: `check_interval_s = 900`, `check_jitter_s = 300` (>= 0), `awg_check_min_s = 3600`, `awg_check_max_s = 10800` (min не больше max). Подробно в `docs/platform/config-reference.md`.

## Цикл проверок не зависит от AWG (2026-11-23)

Сервер сам раз в раунд рассылает наблюдателям задание проверить себя (`check_loop` службы vpn). До v0.220.1
цикл запускался только при `awg` в `[vpn].transports` (остаток времён, когда reality был вторым транспортом).
На ion AWG выключили 2026-11-22, служба vpn перезапустилась с новым конфигом 2026-11-22 в 22:45 UTC, и с этого
момента ion не проверял никто: ни матрицы в Grafana, ни оповещений о его сбоях. Теперь цикл идёт при любом наборе
транспортов.

## Нет TCP до сервера — VPN-проверки не делаются (2026-11-23)

Наблюдатель сначала делает слой «сеть» (TCP-проба curl до IP:порт Reality сервера, `net_target`). Если TCP нет
(`net.ok = false`), тоннели не поднимаются и curl через них не идёт: на каждый слот и цель в отчёт кладётся
`ok = false` с ошибкой «пропущено: нет TCP до host:port», разброс `spread_s` не выжидается, в лог уходит одно
предупреждение. Отчёт и протокол прежние (с `net`), сервер по `net.ok = false` по-прежнему замораживает связку
(`_report_check`, `frozen`).

Зачем: если IP уже заблокирован, рукопожатия Reality/xray на нём бесполезны и только светят VPN перед ТСПУ.
Серии `vpn_series` так уже делали через `raw_probe` (`TCP_BLOCKED`). Если `net_target` не передан, нет sudo или TCP
есть, поведение прежнее.
