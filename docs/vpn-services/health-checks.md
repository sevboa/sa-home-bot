# Проверки доступности (vpn_check)

## Идея
Pull/push (решение 2026-08-17): служба `vpn` только РАССЫЛАЕТ «проверь» через generic fan-out node-сервиса (`ACTION_TRIGGER_PEERS`) и не ждёт ответа; каждая `vpn_check` на своей ноде сама пушит результат (`report_check`) обратно — фанаутом на ВСЕ живые vpn-инстансы (иначе результат оседал бы в БД одной ноды). С 39.0.7 (2026-09-18) каждый инстанс vpn просит проверить ТОЛЬКО себя (`server=self._node`): не дублируется диспетчеризация N раз, и бесплатный heartbeat — упавший инстанс не рассылает «проверьте меня». Смерть хоста видна отдельно через `live_vpn_nodes()`/monitor, vpn_check отвечает на более узкий вопрос: «идёт ли реально трафик именно этого транспорта оттуда».
Каждый инстанс гоняет `reconcile_vpn_check` по своей копии данных, без координации: гистерезис-счётчики могут разойтись на 1–2 тика, поэтому `vpn_check_failed/recovered` приходит от каждого инстанса. Находка 2026-11-07: задвоение было не «иногда», а почти всегда (за 5 дней 46 из 46 оповещений zakhar и 19 из 32 alfred). Бот показывает и записывает одно и то же событие проверок и серий один раз за `VPN_EVENT_DEDUP_S` (120 с, `bot/node_events.py`, ключ без поля `active`). Эмитят по-прежнему все инстансы: иначе упавший сервер оставил бы админов без оповещений. Если счётчики инстансов разошлись на тик и больше, дубль остаётся: окно короче интервала проверок намеренно. Событие `vpn_check_recovered` несёт `active`: всё, что сейчас в alerting у этого инстанса, без устаревших наблюдателей, сгруппировано по (наблюдатель, сервер, транспорт); `whole` значит, что в группе не работает ничего. Бот выводит это блоком «Ещё не работает» или строкой «Других проблем нет» (решение владельца 2026-11-07: «восстановилось» не должно выглядеть как «всё хорошо»); от старой ноды без `active` текст прежний. На чтение (`check_status`) не фанаутим: запись уже разлита по всем инстансам.
Отчёт по виду (упал/поднялся) — одно событие со списком сайтов, а не по событию на сайт (общий сбой туннеля раньше сыпал сообщение на сайт).

## Гистерезис
`domain/vpn_check.py::reconcile_vpn_check` — булевый ok/fail поверх общего `domain/hysteresis.py::reconcile_band` (неудача = полоса OVER, успех = UNDER): переход в alerting после `fail_threshold` подряд неудач, обратно после `clear_threshold` подряд успехов. Ключ строки: (node-наблюдатель, server, transport, target). `rollup_status` сводит статусы наблюдателей одной пары: все OK → OK, все ALERTING → ALERTING, иначе PARTIAL («доступно частично», оранжевый индикатор, решение 2026-09-18). Цвет считается по ВСЕМ строкам пары (недостижимая цель у одного наблюдателя уже делает картину неоднородной), а наблюдатели считаются по узлам, не по строкам («observers: 4» при двух наблюдателях — находка деплоя 0.109.0).
Устаревание (`CHECK_STALE_FACTOR` = 3 интервала): наблюдатель может замолчать, не сказав ни слова (нода умерла/ушла из роя/потеряла интернет), а запись останется навсегда; зелёный от мертвеца хуже отсутствия индикатора. Три интервала, а не один — пропущенный тик это джиттер (пробник поднимает тоннель на время цикла). Для telegram_egress строка не прячется, а помечается `stale`.

## Слоты и туннели
Слот = пара (сервер, транспорт), настроенная на ЭТОЙ ноде (`node/vpn_probe_state.py`, пишет `node/fixups.py::make_vpn_probe_state_fixup` при `nodectl fix`; пусто — служба ничего не проверяет). Диспетчер шлёт одно имя сервера; если у ноды к нему настроено несколько транспортов, проверяются все, в один `report_check` — по строке на (сервер, транспорт, цель). Слоты одного сервера идут последовательно (эфемерный подъём — всплеск нагрузки; решение 2026-09-18 «не грузить машины»). Self-check исключён (сервер не проверяет сам себя — нет сигнала о видимости извне).
netns + veth + NAT заводит `node/fixups.py` и они переживают ребут (без физического интерфейса handshake/xray некуда выйти — находка 2026-08-17). САМ туннель (awg-quick / xray-клиент) эфемерный: поднимается перед пачкой слота и гасится в `finally`.
- awg: `awg-quick up`; гейт: маршрут `ip route get <литерал>` идёт через туннель (с ретраями — хендшейк не мгновенен; общее ожидание укладывается в `check_timeout_s`) + внешний IP из netns отличается от IP хоста (кроме самой VPN-ноды, где совпадение неизбежно).
- reality: xray-клиент — долгоживущий, запускается фоном под `timeout <окно>` (страховка, если sudo не пробросит SIGTERM; окно = `check_timeout_s` + 10 с), пауза после спавна даёт SOCKS слушать порт (значение 0.5 с не проверено по живым данным). Маршрут не переписан — гейт только по exit-IP через SOCKS. curl идёт с `--socks5-hostname` (имя резолвит сервер, как у настоящих клиентов): с голым `--socks5` DNS шёл через хост мимо туннеля, и сбой DNS/интернета у провайдера alfred (2026-10-06 04:50–06:20) выглядел как падение reality на всех VPN.
Гейт нужен, чтобы проверка не зеленела тихо мимо VPN (инцидент 2026-08-31): провал гейта помечает все цели одной внятной ошибкой. Одна строка журнала на прогон туннеля (иначе сбой не разобрать задним числом). Ошибки останова только логируются. Не удалось узнать exit-IP хоста — не тема проверки, реальные цели покажут сбой. `ip` резолвится при каждом вызове (чтобы `nodectl fix` после старта подхватился), `curl` внутри `netns exec` остаётся литералом — как в sudoers-правиле.

## HEAD вместо GET
Проверке нужен только код ответа; GET заставляет curl принять тело целиком. С добавлением google/youtube/instagram/discord (2026-09-20) каждый слот тянул ~1.5 МБ за цикл; замер youtube через туннель: 1247 мс / 870 КБ на GET против 657 мс / 0 КБ на HEAD; ×8 слотов ×12 циклов/час — порядка 100 ГБ в месяц трафика по VPN-серверам, прямо в лимит `node_limit_gb`. 405/501 — «метод не поддержан»: цель жива, повторяем GET. `http_code` внутренний, в отчёт не уходит.
Права: «a password is required»/локализованное «sudo:» → подсказка `nodectl fix` (`looks_like_sudo_denied` / `looks_like_sudo_message` из `utils/requirements.py`: вторая не зависит от локали ноды).

## Серийная проверка: ядро замера (Этап 63.1.1, 2026-11-03)
`vpn_series/measure.py::classify` — чистая функция над рядом samples `(t, bytes)` скачивания через туннель слота; `vpn_check` не затронут. Результат `SeriesResult`: `bytes_total`, `duration_s`, `stalled_at_bytes`, `max_idle_s`, `kbps`, `verdict`. Вердикты: `cut` — curl exit 18/56 при 10–30 КБ полученных (обрыв TCP после 15–20 КБ, признак ТСПУ); `error` — нет ни байта или иной ненулевой exit (0 и 28 терпимы: 28 — таймаут `--max-time` при заморозке); `freeze` — после первых байт поток стоял ≥ `freeze_idle_s`; `slow` — скорость ниже `min_kbps` (кбит/с); иначе `ok`. Простой считается от последнего прироста байт, до первого байта не учитывается.

## Серийная проверка: раннер (Этап 63.1.2, 2026-11-03)
`vpn_series/runner.py` — сборка `curl` argv (netns exec, socks5 для reality), стриминг stdout с тиками `tick_s` и дедлайном `duration_s + 5`, агрегация в `classify`. `run_single` — одиночный прогон; `run_burst` — `burst_connections` параллельных прогонов через `asyncio.gather`. Конфиг `[vpn_series]`: `url` (файл 200 МБ), `duration_s`, `burst_connections`, `freeze_idle_s`, `min_kbps`, `tick_s`. Дефолты подобраны под 2–3 минуты замера и 6 параллельных соединений.

## mtg_probe (vpn_series)

`src/sa_home_bot/vpn_series/mtg_probe.py::mtg_probe` проверяет прокси mtg на сервере с ноды-пробника: доходит ли TCP до порта и проходит ли TLS-хендшейк с SNI маскировки (`www.microsoft.com`). Ключи mtg не нужны и не читаются. Вердикты: `ok` (TCP и TLS прошли), `tcp_blocked` (TCP не доходит), `tls_blocked` (TCP есть, но TLS-хендшейк упал/завис — признак реза fake-TLS ТСПУ).

## Серийная проверка: действие series (63.1.4, 2026-11-03)

Действие `series` живёт **внутри** службы `vpn_check` (не отдельная служба). Причина: тот же netns пробника, иначе `vpn_check` и серия гасят друг другу туннель. Существующее поведение `check` (формат, тексты, отчёт `report_check`, события) **не меняется** — только добавляется действие и замок на слот.

### Замок слота
`self._slot_locks: dict[str, asyncio.Lock]` (ключ — `slot.netns`). Метод `_check_slot` целиком выполняется под этим замком (единственная правка существующего пути — обернуть тело в `async with`). `_series_slot` тоже берёт тот же замок. Это гарантирует, что `check` и `series` по одному слоту не пересекаются.

### Лёгкий режим по умолчанию
- Серия 30 с, файл 20 МБ (`url = "https://speed.cloudflare.com/__down?bytes=20000000"`, `duration_s = 30.0`).
- По расписанию — одиночная серия раз в 3 ч (`interval_s = 10800.0`).
- Залп (`burst`) — только по команде.
- Расписание выключено по умолчанию (`enabled = false`), включается только в конфиге zakhar:
  ```toml
  [vpn_series]
  enabled = true
  ```

### Действия
- `series` — параметры `server`, `mode` = `single`|`burst`. Проверки `server` как у `check` (self-check и «нет слота» — `accepted` + `skipped`), неизвестный `mode` → `ProtoError(ERR_BAD_REQUEST, ...)`. Запускает фоновую задачу `_series_run(server, slots, mode)`, сразу возвращает `{"accepted": true, "server": ..., "mode": ...}`.
- `series_status` — без параметров, возвращает `{"results": self._series_last}` (последний результат по ключу `"<server>/<transport>"`).

### Процесс `_series_slot`
Под замком слота:
1. Для reality цель TCP — `reality_target(reality_conf_path(slot).read_text())`, ошибка чтения → `target=None`.
2. `raw_probe` с `do_handshake`, который поднимает туннель (`_tunnel_up`) и делает `_egress_gate`, **БЕЗ гашения**.
3. Если вердикт `ok` — `run_single` или `run_burst`; иначе серия не запускается.
4. `finally` — `_tunnel_down`.

Результат: `{"server","transport","mode","raw": RawProbeResult.model_dump(mode="json"), "series": [SeriesResult.model_dump(mode="json"), ...], "at": utc_now().isoformat()}`.

### Расписание
Метод `async def series_loop(self)` — бесконечно: `asyncio.sleep(interval_s)`, затем `_series_run` по каждому серверу слотов в режиме `single` (исключения логировать, цикл не падает). Запуск в `vpn_check/app.py`: `asyncio.create_task(service.series_loop())` только при `settings.vpn_series.enabled`, отмена задачи в `finally`.

### Отчёт в vpn (63.1.5, 2026-11-03)
После прохода по слотам `_series_run` одним вызовом шлёт `report_series {node, results}` во все живые
инстансы `vpn` (`vpn_nodes.fanout`, общий с `report_check` хелпер `_report_to_vpn`). Если ни один слот
не дал результата (все упали исключением), отчёт не шлётся.

Приём — `vpn/checks.py::_report_series`. Вердикт пары (сервер, транспорт) —
`domain/vpn_series.py::series_verdict`: не-`ok` вердикт TCP-части (`tcp_blocked`, `proto_blocked`)
важнее серии; иначе первый из `freeze`/`cut`/`error`; `slow` считается рабочим (медленно, но живо —
блокировкой не считаем). Гистерезис тот же `reconcile_band`, пороги отдельные от `check_*`:
`[vpn] series_fail_threshold = 2`, `series_clear_threshold = 1` — при расписании раз в 3 ч алерт
приходит не раньше чем через ~6 ч от начала поломки, зато одна случайная заморозка не будит.

Состояние — таблица `vpn_series_states` (ключ node, server, transport; `last_report` — JSON отчёта
целиком, для строки `/vpn` в 63.1.6). `vpn_check_states` не трогается. События:
`vpn_series_failed {node, server, transport, verdict, consecutive}` и
`vpn_series_recovered {node, server, transport}`; `at_bytes` — где встала первая сломанная серия
(`stalled_at_bytes`, иначе `bytes_total`).

### Показ (63.1.6, 2026-11-03)
Алерт админам — `bot/node_events.py::render_vpn_series`, отдельно от `render_vpn_check` (его тексты не
менялись). `check_status` у vpn теперь отдаёт ещё `series` — строки `vpn_series_states`; экран
«проверка доступности» `/vpn` рисует блок «🇷🇺 Из РФ» только если строки есть: 🔴 — в алерте
(гистерезис), 🟠 — последний замер плохой, но порог ещё не пройден, 🟢 — работает. Без данных серий
экран байт в байт прежний. В снапшот бэкапа
таблица не входит (оперативные данные, как `vpn_check_states`).

## Проверка SNI-кандидатов (63.2.2, 2026-11-03)

### Зачем
Reality маскируется под чужой домен (SNI). Если ТСПУ режет этот домен или он не отдаёт TLS 1.3 + h2,
маскировка выдаёт себя. Нужна проверка списка кандидатов прямо с zakhar (РФ), без VPN-туннеля.

### Вердикты
- `ok` — DNS резолвится, TCP соединяется, TLS 1.3, ALPN h2.
- `dns_fail` — `getaddrinfo` не нашёл домен.
- `tcp_fail` — TCP не дошёл (timeout, connection refused, др. OSError до TLS).
- `tls_fail` — TLS-хендшейк упал (`ssl.SSLError`) или нет `ssl_object`.
- `no_tls13` — хендшейк прошёл, но версия не TLSv1.3.
- `no_h2` — TLS 1.3 есть, но ALPN не `h2` (обычно `http/1.1`).

### Действие
`vpn_check.sni_probe` — параметр `domains` (строка через запятую или список, макс. 30 доменов).
Валидация: только `[a-z0-9.-]`, есть точка. Туннели и замки слотов **не трогает** — проверка идёт
с хоста напрямую.

### Пример
```bash
nodectl -n zakhar call vpn_check sni_probe domains=www.google.com,dl.google.com
```

### Ответ
```json
{
  "results": [
    {"domain": "www.google.com", "verdict": "ok", "ms": 42, "error": null},
    {"domain": "dl.google.com", "verdict": "no_h2", "ms": 38, "error": "ALPN: http/1.1"}
  ]
}
```

### Ограничение
Проверка отвечает «домен сам по себе жив из РФ и годится как маска (TLS 1.3 + h2)». Она не
доказывает, что ТСПУ пропустит Reality на НАШ IP с этим SNI — это видно только серией 63.1 после
выката нового SNI (63.2.3). Таймаут всего TLS-хендшейка считается `tcp_fail` (DPI часто именно
молча тянет время), DNS ограничен тем же таймаутом. Домены приводятся к нижнему регистру,
кириллические (IDN) не принимаются — передавайте punycode.
