# Архитектура службы vpn

## Транспорты и общая квота
У пира один из двух транспортов (`vpn_peers.transport`, значения `awg` и `reality` менять нельзя).
Учёт трафика и месячная квота ОБЩИЕ: одна квота на гостя на сервер независимо от транспорта (решение владельца 2026-09-10).

- `awg` — AmneziaWG (UDP + обфускация), исходный (этап 33). Пир = ключ WireGuard + адрес в подсети; учёт из `awg show <iface> transfer`. Бэкенд `vpn/awg.py`.
- `reality` — VLESS+Reality через xray-core (TCP/443), единственный транспорт, проходящий ТСПУ из РФ. Пир = UUID клиента xray; колонки переиспользованы: `public_key` = UUID, `address` = email `c<chat_id>-<устройство>` (`_reality_email`). Учёт из `xray api statsquery`, бэкенд `reality/xray.py`. `server_pubkey` у reality-пира — публичный ключ Reality-сервера на момент выдачи (57.1); у старых reality-пиров NULL, их по ключу не судим.

Какие транспорты держит нода — `[vpn].transports` (+ секция `[vpn.reality]`). jeeves: `["awg"]`; wooster: `["reality"]`; можно оба. Reality доступен только если собран бэкенд xray; awg доступен всегда (бэкенд создаётся без побочных эффектов). Если транспорт у ноды один, `transport` в запросе необязателен; если оба — бот/модель указывают, какой (`_resolve_transport`, иначе ошибка «уточните transport»). У старых строк `transport` мог быть NULL до миграции — трактуется как awg.

## Реконсайлер
Не разрозненные add/remove, а `reconcile` (решение плана этапа 33): желаемое состояние сервера (активные пиры допущенных и не исчерпавших квоту чатов — БД источник истины) сверяется с фактическим по каждому транспорту отдельно; лишние снимаются, недостающие добавляются. Вызывается на старте (после рестарта сервера пиров/юзеров нет, БД помнит всех) и на каждом тике сэмплера — тем же ходом закрываются месячная разблокировка 1-го числа, снятие при блокировке по квоте и самовосстановление после ручных правок. Строки БД реконсайлер не трогает: пир остаётся `active`, поэтому возврат допуска не требует перевыпуска конфига — поднимется тот же ключ. Для reality ключ сверки — email (как в `list_clients`/`statsquery`), значение — UUID.
`xray api adu` меняет только живой инстанс, не `config.json`: после рестарта xray список юзеров пуст, возвращает его reconcile при старте.

В `app.py` порядок важен: допуск (`backfill_access`) обязан выполниться строго до первого reconcile, иначе тот снял бы пиры всех, кому допуск ещё не проставлен. Обработчики сигналов ставятся до `start()` (он ждёт появления своего адреса, см. proto/server.py). Неудача первого reconcile (sudoers ещё не поставлен через `nodectl fix`) не мешает службе подняться: `ERR_NEEDS_PRIVILEGE` потом объяснит, что делать. Подписка и https-страница (57.10) не поднялись — служба живёт без них (`get_subscription` вернёт понятную ошибку). Проверки доступности рассылаются только на awg-нодах (у reality-only нет netns-пробника AmneziaWG), но приём отчётов `report_check` работает на любой ноде с службой vpn (раньше висел на awg-гейте, и reality-only нода не принимала отчёт собственного пробника).

## Сентинель chat_id = 0
`vpn/protocol.py::PROBE_CHAT_ID` = 0 — это НЕ гость, а пробник ноды (vpn_check выпускается тем же `issue`, `node/fixups.py::VPN_PROBE_CHAT_ID` держит копию значения). Тот же 0 (`NODE_SENTINEL_CHAT_ID`) используется как «весь канал ноды» в таблицах квот (`vpn_quota_state`): реальный Telegram chat_id никогда не 0.
Следствия: допуск (`_access`) для сентинеля всегда «разрешён» — закрывать собственную диагностику незачем, а на ноде без пробника бэкфилл строки не создаст и `nodectl fix` не смог бы его выпустить; реконсайлер не снимает пробника; `check_restore` исключает его из «задетых»; любое правило «чат должен быть X» обязано исключать сентинель, иначе ломается vpn_check. Перед выкатом правок службы vpn снимать снимок пиров по обеим нодам.

## Приватность
Служба хранит только объёмы и время последнего хендшейка. Ни адресов назначения, ни DNS-запросов, ни логов соединений. IP посетителей веб-страницы подписки не пишутся.

## Устройства и имена
Число устройств на гостя намеренно не ограничено (решение 2026-08-03) — потолок стоимости задаёт трафик. Проверки допуска/квоты идут ДО генерации ключа и выделения адреса: у отказа не должно быть следов. Имя устройства больше никто не вводит (2026-08-04) — служба берёт случайный цветок из `FLOWER_NAMES` (только латиница, до 8 символов; имя `.conf` ≤ 15 символов — предел имени тоннеля wireguard-android; вернули 2026-10-11, мастер /vpn использует их же для новых устройств). Бот может задать имя явно (57.1, `MAX_DEVICE_LABEL_LEN` = 64, без управляющих символов), повтор активной пары (label, transport) — ошибка, а не дубль. Уникальность активной пары держится кодом (на старых базах с дублями индекс не создать), поэтому проверка и INSERT идут одним критическим участком. Число устройств чата ДО выдачи (`prior_device_count`) возвращается, чтобы бот решил, что показать первым: 0 — вероятно, настраивается с этого же телефона, удобнее файл; иначе — QR. Перевыпуск снимает старый пир ДО выдачи нового, поэтому допуск проверяется и в нём. Перевыпуск сохраняет транспорт устройства. Адреса awg выделяются из подсети: `.1` под сервер, reality-пиры в пул адресов не входят.
Трафик устройства считается по всем транспортам имени, включая перевыпущенные (expired) и отозванные в этом месяце — иначе перевыпуск обнулял бы цифру.

## Прочее
- Приватный ключ awg-сервера (`server_private_key`) нужен только `backup/identity.py`; укладывается в sudoers `awg show *`.
- Публичный ключ awg-сервера отдаётся в `get_state` для пробников (`node/fixups.py::_probe_conf_stale`). Живой случай 2026-09-20: jeeves переустановили 18.09, конфиг пробника на wooster остался с 01.09 со старым ключом — фикс считал «файл на месте» и не перевыпускал, awg wooster→jeeves молча не поднимался месяц. Ошибка чтения ключа не должна валить весь `get_state` (его дёргает бот на каждый экран).
- `get_state` несёт: транспорты ноды (бот решает, предлагать ли выбор), индикатор по транспортам, флаг «умею допуск» (старая нода поля не шлёт — бот читает отсутствие как «допуск не ведёт, пущены все»; это код совместимости, его удаляют только с подтверждения владельца).
- `proto`-сервер валидирует action по `describe`, поэтому неизвестное действие в диспетчер не доходит.
- Локальные копии констант сервиса node (`NODE_SERVICE`, `ACTION_TRIGGER_PEERS`) в `vpn/service.py` — чтобы не тянуть в лёгкую службу тяжёлые зависимости node/service.py.

## Раскладка модулей службы vpn

`vpn/service.py` держит класс `VpnService` (конструктор, `describe`, `get_state`, диспетчер `run_command`) и собирает его из миксинов: `peers.py` (выдача, перевыпуск, отзыв, список пиров), `reconcile.py` (бэкфилл, реконсайл, сверка после восстановления), `quota.py` (квоты, допуск, гранты, пороги), `client_configs.py` (vless и подписка по запросу), `subscription_links.py` (поколения, ссылки подписки, опрос соседних нод), `usage.py` (учёт трафика и сэмплер), `proxy.py` (прокси Telegram), `checks.py` (результаты `vpn_check`), `apk_service.py` (кэш APK). Общие константы и хелперы — в `service_common.py`; `month_key` читается только оттуда (тесты подменяют `service_common.month_key`). Старые имена `CHECK_STALE_FACTOR`, `GB`, `PROBE_CHAT_ID`, `_random_device_label` остаются доступны из `vpn.service`.
