# Пробуждение (WoL) и готовность служб

Модули: `wake_core.py`, `wol.py`.

`wake_core` — общее ядро без aiogram (раньше жило в `bot/swarm_view.py` и `bot/handlers/wake.py`;
служба tasks без Telegram тоже должна будить цель перед сроком, находка 2026-07-24). Литералы
`node`/`monitor` и т.п. — не импорт из bot/*, который тянет aiogram.

## Сценарий `ensure_service_ready`
presence -> (различить сон и аварию) -> WoL и ожидание подъёма -> прогрев, заземлённый на реальный
ответ Ollama, а не самоотчёт службы. Исходы: `READY`; `UNREACHABLE` (машину/службу не удалось
поднять за `wake_timeout_s`); `CRASHED` (нода ответила на presence, а именно эта служба нет — WoL
бесполезен; аудит 2026-08-26, раньше смешивалось с UNREACHABLE и слался лишний magic packet с ожиданием
до таймаута); `WARMUP_FAILED`. Фазы `PHASE_WAKING/WOKEN/WARMING` передаются в `on_phase_change` ДО
начала ожидания. На «уже тёплом» пути фаза не вызывается.
Самоотчёт `self._asleep` службы llm инициализируется True при старте, поэтому первый запрос после
рестарта проходит через настоящий прогрев. Внешнее выгружение модели самой Ollama не заземлено —
известный задокументированный пробел (не платим сетевым вызовом за каждый запрос).

## Таймауты (значения не менять без причины)
- `PEER_TIMEOUT_S` (3 с) — обзорные опросы (/swarm, поиск LAN-waker); `PRESENCE_TIMEOUT_S` (6 с) —
  presence перед запросом к модели, цена ложного «недоступна» выше (лишний WoL посреди диалога).
  Находка 2026-07-23: без укороченного таймаута get_state ждёт весь дефолт ProtoClient (10 с) на каждый хоп,
  а TCP-keepalive замечает пропажу лишь за ~50 с. Находка 2026-07-25: 3 с ловило ложные «недоступна»
  на подтормаживании winpc (WSL2/Ollama). Таймаут читается внутри функции, а не дефолтом аргумента
  (дефолт вычисляется при импорте, и подмена в тестах не доходила бы).
- Ожидание после magic packet `WAKE_POLL_TIMEOUT_S`: находка 2026-07-27 — 90 с было меньше
  `_WARMUP_TIMEOUT_S` llm (150 с) и реального холодного старта winpc.
- `WARMUP_TIMEOUT_S` = 360 с: находка 2026-07-30 — 180 с меньше реального холодного старта
  (Qwen3.6-35B-A3B с диска 201 с по `load_duration`); согласовано с `[llm].request_timeout_s`.
  Служба без `ACTION_WARMUP` (`ERR_UNKNOWN_ACTION`) — не ошибка. Причина неудачи прогрева уходит в лог
  (сбой 2026-07-30: на winpc разбор требовал хода за логами другой машины).
- Правка 3 -> 6 с (`2b8fae7`) пришлось делать в двух копиях (ai_flow и tasks) — константы теперь одни.

## Реквизиты WoL
`resolve_wake_info`: свой кэш, при промахе — спросить локальную ноду (она помнит WoL соседей с их
hello, `PeerLink.wake_info`, даже после сна) и сразу положить в кэш. Инцидент 2026-07-27 19:34: кэш
наполнялся только в `find_lan_waker`, куда `wake_swarm_node_core` доходит лишь после успешного
чтения кэша — курица-яйцо; у tasks WoL не уходил ни разу. `find_lan_waker`: живая нода в том же
сегменте LAN (совпал объявленный broadcast); будит она, а не вызывающий (бот или tasks могут быть
вне локалки). `wake_swarm_node_core` возвращает `WakeOutcome` с готовым HTML для чата (tasks
использует только `ok`).
`collect_reports(with_monitor=...)`: слито из `bot/swarm_view.py` когда за данными пришёл тул
swarm_status (`bot/tools.py` не может импортировать `swarm_view` — тянет aiogram).
`check_updates_summary`: версия репозитория одна на рой (решение владельца 2026-08-04); своя нода
спрашивается через `check_update`, остальные берутся из `get_state` (тот же веерный опрос, что у
/swarm). На последней версии файлы могли уже лежать без `restart_node` — отражается в сводке.

## wol.py
Magic packet: 6 x 0xFF + MAC x 16 (102 байта), UDP-broadcast, несколько копий (безвредно),
`bind_ip` — нода многодомная (LAN + tailscale), без привязки broadcast может уйти не в тот сегмент.
`ping_host` — один ICMP с таймаутом 1 с (iputils разрешает всем). Умение WoL объявляется только при
проводном интерфейсе по умолчанию (этап 19 п.6, Wi-Fi ненадёжен): Linux — sysfs, Windows —
эвристика по имени. Интерфейс по умолчанию определяется UDP-`connect()` трюком (пакет не уходит,
сеть не нужна). Виртуальные/туннельные интерфейсы (docker, tailscale, wg, tun, vmware и т.п.) не годятся
ни целью, ни отправителем — шире, чем `proto/endpoints.is_virtual_iface`.
