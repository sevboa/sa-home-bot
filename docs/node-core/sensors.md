# Датчики, задания монитора, воркер

Модули: `sensors/*`, `jobs/*`, `worker/*`, `scheduler/setup.py`, `monitor/*`.

## Общее
Парсеры вынесены в чистые функции (тесты на фикстурах без железа), блокирующие вызовы идут через
executor (ARCHITECTURE §9.6). `SensorSource` — изоляция доменного `SensorReading` от источников;
порядок отображения в /status: CPU -> GPU -> диски. Отсутствие программы/прав объясняется через
`requirements_registry`, а не каждым сканом в логе.

## CPU / GPU
psutil, fallback `sensors -j`. На Windows температур нет ни в psutil, ни в WMI — LibreHardwareMonitor
(решение этапа 19, 2026-07-10). GPU: с проприетарным NVIDIA-драйвером hwmon температуру не публикует,
единственный источник `nvidia-smi` (находка при установке Tesla V100 SXM2 на mycraft); один вызов
опрашивает все карты; `[N/A]` — строка пропускается.

## Диски (`sensors/disks.py`)
- У USB-мостов (JMicron `sntjmicron`) без `-d` температура `null`: тип берётся из
  `smartctl --scan -j` либо задаётся как `/dev/sda:тип`. Тип отделяется последним двоеточием.
- Не SMART-устройства (eMMC, optical, loop, RAID, device-mapper, zram) не опрашиваем (иначе спам
  в лог каждый скан). Таймаут одного вызова защищает скан от зависшего USB-моста.
- smartctl возвращает ненулевой код при некритичных предупреждениях, но JSON валиден — парсим stdout.
- NVMe: `lsblk` отдаёт namespace (`/dev/nvme0n1`), SMART работает с контроллером (`/dev/nvme0`) —
  пересчёт обязателен, иначе температура/health NVMe всегда пустые.
- Метки: HDD1/HDD2, SSD, NVMe, eMMC; номер только если дисков вида больше одного; eMMC первой (нет
  температуры, SMART недоступен). SIZE=0 — пустой картридер, пропускаем. Отсутствие колонок ROTA/SIZE
  в старом lsblk — деградация к прежнему поведению.
- Иконка здоровья в /status берётся из последних снимков БД (`health_overrides`), чтобы совпадать с
  алертами `SmartScanJob`; на холодном старте — живой опрос.
- SMART raw: `raw.value` у части дисков упаковывает несколько полей (Hitachi: string `'31 (0 9)'` при
  value `589855`) — берём первый токен `raw.string`.
- Health: FAILED — диск при смерти; PASSED, но pending/uncorrectable — предупреждение.
  `SmartScanJob` read-only (`-H -A`, self-test'ы не запускаются).

## Windows: LHM (`sensors/lhm.py`, логику не трогать)
Единый `Computer` и DLL на процесс (инициализация дорогая), на срез только `Update()`.
- Автозагрузка pythonnet (2026-07-17) поднимала runtime не полностью — явный `netfx`;
  `PYTHONNET_RUNTIME` уважается. Баг 2026-07-17 (второй заход): `lhm_problem()` (event loop) и
  чтение датчиков (executor) вызывали `_ensure_runtime()` одновременно, гонка ломала `clr` —
  инициализация один раз за процесс под локом, повтор не делаем даже после неудачи.
- Пороговые сенсоры типа Temperature (у NVMe 80 C) не показания: `max()`-fallback принимал их за самое
  горячее (баг 2026-07-17: 55 -> 80 C). Значения None и <= 0 C — мусор (без админа драйвер не грузится).
- Находка 2026-07-20: конкурентный `hw.Update()` ронял LHM IndexOutOfRange, но общий лок стал строго
  хуже — зависший Update() (похоже, съёмный картридер без носителя) держал лок вечно, сбор датчиков
  стоял без ошибок в логе до рестарта. Решение: `Update()` в отдельном пуле с `HW_UPDATE_TIMEOUT_S`,
  зависший Identifier банится (утечёт один поток один раз), пул отдельный от дефолтного executor.
  Одно проблемное устройство не гасит остальных (`_safe_hardware_node`).
- NVMe: приоритет "Temperature"/"Composite Temperature", иначе максимум остальных. Вид носителя —
  эвристика (NVMe по identifier, SATA SSD по модели, остальное HDD). Здоровье и свободное место на
  Windows пока пусты (health придёт со SmartScanJob, сопоставление дисков с томами требует WMI).

## Питание / история отключений (`sensors/power.py`)
`last -xR --time-format iso reboot` классифицирует сессии: `crash` — не было штатного shutdown;
время конца — штатный. Для внезапного обрыва точный момент в wtmp отсутствует — оценка по
`last_entry` сессии из `journalctl --list-boots`; сессии сопоставляются по START с допуском. `still
running` — текущая сессия, не отключение, но её START — момент возврата после краха. Страница
запрашивается на одно событие больше (признак следующей). На Windows истории нет.

## Host-метрики VPS (`sensors/host.py`)
/proc и statvfs. Два снимка с паузой (дельты steal/iowait/oom/ошибок NIC) — в executor. Только
errs, не drop: на виртуальном NIC `rx_drop` — шум гипервизорного свитча, `tx_drop` — qdisc/туннели,
ложная тревога. `guest/guest_nice` не включаются в сумму (двойной счёт). Стойла ядра:
`journalctl -k` (доступ нужен root либо группа systemd-journal/adm, иначе пусто без ошибки —
членство проверяется заранее; сценарий jeeves-vpn-hypervisor-stalls); курсор окна в app_state
(`jobs/scan` сдвигает после успешного среза). Нет PSI/conntrack — метрика не эмитится.

## Задания (`jobs/*`, `worker/*`, `scheduler/setup.py`)
- `SensorScanJob`: состояние коммитится одной транзакцией (`apply_diff`), отправка отдельным шагом;
  `notified_*` выставляется, только когда диспетчер принял событие (`handled`) — падение между
  записью и отправкой не теряет и не дублирует. Статистика по ПРОШЛЫМ показаниям. Telegram-диспетчер
  всегда `handled=True` (повтор дал бы дубли чатам), proto-диспетчер `handled=False` при отсутствии
  клиентов — событие повторится.
- `SmartScanJob`: baseline сдвигается только после доставки хотя бы одному (или когда слать некому);
  доставка целиком провалилась — деградацию повторим.
- Диски в состоянии монитора — кэш `SensorScanJob` (живой баг 2026-07-18: smartctl на каждый запрос
  делал /status и веерный /swarm медленными). На vps дисков со SMART нет, кэш затирается.
- `HousekeepingJob`: потолки истории показаний на компонент, host-истории (~10 суток при `*/1`,
  чтобы поймать «steal подрос за неделю»), журнала событий роя (`swarm_events`).
- Планировщик кладёт в `DedupQueue` (ключ освобождается на `get()`); все cron-job'ы `coalesce=True`,
  `max_instances=1` (инвариант §9.4). `JobWorker` строго последовательный (один job зараз), падение
  job'а не валит worker, запись `job_runs` до/после.
- Монитор: `downtime` — команда-представление (с params, кнопкой не рисуется); окна тренда и
  страницы истории ограничены от абсурдных запросов; программы `smartctl`/`nvidia-smi` — только если
  соответствующий датчик включён; kernel-журнал — только при включённом host-датчике.
