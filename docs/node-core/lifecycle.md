# Жизненный цикл ноды: запуск, супервизор, останов, обновление, питание

Модули: `node/app.py`, `node/supervisor.py`, `node/service.py`, `node/state.py`, `node/update.py`, `cli.py`, `app.py`.

## Состояние ноды (`node/state.py`)
Не TOML и не БД: `assignments` и пиры из рантайма (`assign`/`unassign` — этап 17, `join` — этап 18)
переживают рестарт. TOML — стартовый источник, не единственный. Персистентный справочник пиров:
id + последний удачный адрес + все известные пути (этап 24); тип соседа при перезаписи адресов
сохраняется (его пишет PresenceWatcher из hello, нужен когда соседа не спросить).
`last_known_version` — версия прошлого старта: по ней `restart_applied` (см. swarm-links).
Сохранение атомарно (tmp в том же каталоге + `os.replace`).

## Запуск (`node/app.py::run_node`)
- Сигналы перехватываются ДО первого долгого шага (находка 2026-07-28): `server.start()` может ждать
  адрес до трёх минут, и всё это время остановка убивала бы процесс, не погасив уже запущенные
  дочерние службы.
- Нода слушает unix-сокет (фронтенды) и все адреса `listen` (TCP для пиров); недостающий адрес старт
  не задерживает. Умения `join`/`swarm_join` объявляются по настроенному адресу (статичен), рою
  нода называет реально слушаемые (список растёт).
- Порядок: сервер создаётся до супервизора (emit замыкается на broadcast); аренда — ниже супервизора
  (нужен router), колбэки смотрят на переменные, а не захватывают объекты; пакеты настроек
  применяются ДО запуска служб (правка при выключенной ноде вступает сразу); синглтоны стартует
  аренда, а не `start_all` (даже активная роль сначала убеждается, что службу не держит другая
  нода); маячок собирается последним (нужны join сервиса и реальные адреса сервера).
- Первый запуск с `swarm.join` и пустым списком пиров: разовый bootstrap через тот же
  `NodeService.join()`, что и `nodectl join`; рой разъезжается сам (замыкание сетки).
- Пакеты настроек лежат рядом с `config.toml`; без файлового конфига репликации нет.
- `llm` на Windows-ноде не спавнится супервизором (WSL из Session-0/LocalSystem не запускается,
  находка 2026-07-23): процесс поднимает задача планировщика (`deploy/llm-runner.ps1`), но llm
  остаётся в assignments — маршрутизация независима от супервизии.

## Останов
Бюджет `SHUTDOWN_BUDGET_S` (20 с) сверх `[node].stop_timeout_s` на прощание, фоновые задачи, линки и
сокеты; каждый шаг под потолком, вся последовательность под общим бюджетом (этап 29: на jeeves
останов не заканчивался никогда и по логу нельзя было понять, где встал). Сторож `arm_hard_exit`
даётся с запасом поверх бюджета — сначала свои потолки и честная запись в лог, потом принудительный
выход (процесс может застрять в уборке задач внутри `asyncio.run()`). Прощание `node_leaving`
ПЕРВЫМ делом, пока соединения живы (этап 23): иначе «корректно остановилась» и «выдернули из
розетки» неотличимы. Детям бюджет отдельный (`stop_timeout_s`).

## Супервизор (`node/supervisor.py`)
Одна `SupervisedService` = одно назначение: запуск -> ожидание выхода -> если не останавливали сами,
`service_failed`, пауза, перезапуск. Стоп: SIGTERM, по таймауту SIGKILL. Останов служб в обратном
порядке назначений (бот раньше монитора). Порядок в реестре задаёт и порядок кнопок.
- Весь цикл наблюдения обёрнут в try/except (инцидент 2026-08-08: необработанное исключение из
  `_emit` — broadcast упавшему клиенту при нестабильной сети — тихо убило fire-and-forget задачу,
  `telegram-bot@alfred` провисел без перезапуска ~20 минут; `start()` после этого no-op). Плюс
  диагностическая страховка в done-callback. Ветка «кто-то снял desired_running» стала громкой
  (инцидент 2026-08-12 разбирался по отсутствию лога).
- `FENCED_EXIT_CODE` = 11: служба вытеснена другим экземпляром (409 Telegram) — не перезапускать,
  решение за арендой (`note_fenced`).
- Инстансная служба читает свой пакет настроек (иначе поднялась бы на общем конфиге).
- Windows: отдельная process group и `CTRL_BREAK_EVENT` для мягкой остановки (в группе родителя
  он прилетел бы и самой ноде); `proc.terminate()` там = TerminateProcess. Ветки не трогать.
- `process_alive` — реальный признак жизни процесса, не `status` (см. leases-and-replication).

## Бот (`app.py`)
С этапа 13 бот — фронтенд: датчиками, порогами и планировщиком владеет служба monitor. В БД бота
остаются app_state, message_id для reply-цепочек, лимит форс-сканов. 409 Conflict при polling —
не сбой, а сообщение извне: возвращаем `True` из `run`, `cli.main` превращает в `FENCED_EXIT_CODE`
(два поллера отбирают апдейты друг у друга, спорить бессмысленно). Первый `get_me()` — в bounded
retry (инциденты 2026-08-08 и 2026-08-12: после ребута сеть поднята частично — DNS резолвится,
HTTP до Telegram ещё нет); если сеть не ожила и после ретраев, процесс падает намеренно, а
восстановление — restart-loop супервизора вместе с фиксом гонки в аренде. Успешный `get_me()` —
лучшее доказательство готовности; отчёт `report_ready` — best-effort и повторяется при каждом
переподключении `node_link`. Этап 52: маршрут до Bot API, outbox, перебор известных маршрутов на
старте. Останов: СНАЧАЛА известить чаты с идущим /ai (`RESTART_TEXT`) и отменить их задачи, пока
`node_link` и сессия бота живы (находка 2026-07-24: осиротевшая задача падала на разорванном
`node_link` и слала голое «что-то пошло не так»), затем остановка связей, polling, прощание,
флаг чистого завершения до закрытия БД. `stop_polling` бросает RuntimeError, если polling не успел
стартовать (быстрый SIGINT, бэд-токен).
Замыкания `node_link`/`node_service` читаются геттером: callback передаётся в конструктор раньше,
чем переменной присвоено значение.

## CLI (`cli.py`)
`--check-config` не тянет тяжёлые зависимости (импорт служб ленивый). Само-рестарт: `os.execv`, тот
же PID, работает под systemd и в терминале. Windows: `os.execv` не заменяет образ (новый PID,
обёртка сочтёт ноду умершей), поэтому само-рестарт там — выход с `RESTART_EXIT_CODE`, перезапуск
делает WinSW (`onfailure restart`) или человек.

## NodeService (`node/service.py`)
- Публичный протокол: порядок и содержимое `describe()` не менять (боты старых версий в рое).
- Power-действия и `restart_node` — умения без параметров, выполняются с задержкой, чтобы ответ ушёл.
- `get_state`: внешне управляемые службы (llm на Windows) берутся из роутера, а не супервизора —
  иначе рабочая llm не показывалась (баг 2026-07-28). `wake` — Ethernet-реквизиты для кэша бота.
- `report_ready`, `trigger_peers` (fan-out без ожидания результата), `send_wol` (будит нода из той
  же LAN, этап 19 п.6), `get_instance_config`/`instance_revision` (служебные, без choices, не для UI),
  `swarm_join` (граф всех известных пиров за один round-trip; без своего TCP-адреса не объявляется).
- Автовыключение по простою Alfred (`[node].idle_poweroff`): открытая SSH-сессия или живая tmux
  (переживает разрыв SSH, находка 2026-08-03) откладывает выключение и шлёт `idle_power_blocked`;
  Занятая локальная служба (`ServiceInfo.busy` в hello, первая — исполнитель devlab, 2026-11-01)
  откладывает выключение молча, без `idle_power_blocked`: `NodeRouter.busy_services()`.
  `close_ssh_sessions` = выгнать всех и выключить одним действием (решение владельца 2026-08-03).
  История режима сна: poweroff -> hybrid-sleep (2026-09-22: 5/5 раз роняло Tesla V100 с шины, даже
  при успешной записи образа — ломает переход через ACPI S4, откатили) -> suspend s2idle (2/2) ->
  снова poweroff (решение владельца 2026-09-23: простаивающая машина именно гаснет; будится по WoL).
  Ни один режим не переживает потерю питания во сне — poweroff единственный честный.
- Обновление: `check_update` только смотрит; `update` подтягивает последний тег БЕЗ рестарта
  (на Linux) — `update.restart_required` честно скажет. Тег `vX.Y.Z` против установленной `X.Y.Z`:
  lstrip префикса (баг 2026-07-17: update считал себя устаревшим всегда). Баг 2026-08-04:
  `up_to_date` сравнивал только диск с целью, и Альфред пропускал `restart_node` на ноде, где файлы
  уже лежат, а исполняется старый код — теперь отдельное `running`. Win32: задача планировщика
  (`deploy/win-auto-update.ps1`), фиксируем только неудачу запуска (процесс скоро умрёт).

## Обновление (`node/update.py`)
pipx не требует root, переустановка идёт из процесса ноды; загруженный код она не трогает, нужен
рестарт. `PIPX_HOME` вычисляется от реально работающего интерпретатора (четвёртый родитель
`sys.executable`): Windows-служба от LocalSystem имеет свой `%LOCALAPPDATA%`, и без явного PIPX_HOME
`pipx install --force` молча ставил в чужой venv (находка 2026-07-17). Экстры (tts/stt/graph_memory)
сохраняются из `pipx_metadata.json` (находка 2026-09-24: голый `git+<repo>` терял пины, `numpy<2.5`
у tts, и `--force-reinstall` притащил numpy 2.5.3). Win32: `pipx install --force` из процесса
структурно не работает (WinError 5/32, находки 2026-07-17/19, venv-DLL держит этот же процесс) —
только внешняя задача от SYSTEM, имя задачи — из `install-node.ps1`. `git ls-remote` синхронный и
короткий (таймаут заметно меньше `DEFAULT_TIMEOUT` протокола, иначе клиент сдаётся раньше); pipx
install — фоновая задача, таймаут большой.

## Фоновые задачи и мелочи
- `NodeService` хранит ссылки на фоновые `asyncio.Task` (иначе соберёт GC).
- `vpn_probe_state.py`: файл пишет `nodectl fix` (root), читает `vpn_check` (обычный пользователь).
  0644 (не секрет: имена netns/veth/iface и порт), каталог xray-конфигов пробников reality — 0600
  (несут UUID). Нет файла — служба ничего не проверяет (молчание лучше кривых данных).
