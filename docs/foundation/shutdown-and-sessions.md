# Останов, сессии, служебные утилиты

## Останов с потолком (`utils/shutdown.py`, `utils/lifespan.py`)

Повод — этап 29, живой сбой на jeeves 2026-07-30: нода приняла `restart_node`, написала
«Останов ноды...» и осталась работать; следующей строки в логе не было ни через минуту, ни через три,
процесс дожил до `TimeoutStopSec` и был добит SIGKILL. Класс проблемы: последовательность останова
состояла из голых `await`, каждый полагался на добрую волю собеседника. Одного полумёртвого сокета
(данные в Send-Q не уходят, FIN не подтверждается) хватает, чтобы останов не закончился никогда, а по
логу не видно, на каком шаге.

Правила модуля:
- у каждого шага останова есть потолок (`ShutdownBudget.step`, по умолчанию `STEP_TIMEOUT_S` = 5 с —
  заведомо больше нужного исправному пути и меньше терпения человека); просроченный шаг бросается с
  записью в лог, останов идёт дальше, имя шага попадает в `overdue`. Нижняя граница бюджета шага —
  0,1 с: даже за дедлайном готовый шаг успевает завершиться, зависший честно попадает в `overdue`.
  Сбойный (исключение) шаг логируется и не отменяет остальные;
- у общего останова есть дедлайн (`total_s`), чтобы десяток честных, но небыстрых шагов (пиров в рое
  много, 5 с на каждого — уже минуты) не складывались бесконечно;
- у процесса есть жёсткий предел `arm_hard_exit(delay_s)`: демонский сторожевой поток вызывает
  `os._exit(HARD_EXIT_CODE)`. Это последний рубеж за нашим кодом — `asyncio.run()` в конце сам
  отменяет оставшиеся задачи и ждёт их без потолка. Код выхода ненулевой намеренно (10): systemd
  (`Restart=on-failure`) и WinSW (`<onfailure action="restart"/>`) поднимут ноду заново — нода,
  которая не может выключиться, хуже упавшей: её не обновить и не перезапустить штатно;
- `dump_pending_tasks` пишет в лог имена незавершённых задач (они осмысленные: `peer-link-alfred`,
  `lease-manager`, …) — один дамп на останов, без DEBUG. Именно его не хватало при разборе jeeves.

`Lifespan` только ждёт сигнал остановки и ничего не гасит сам: порядок остановки задаёт `app.py` (`ShutdownBudget` на шаг). Сигналы: SIGINT/SIGTERM и, только на Windows, SIGBREAK (супервизор шлёт дочерней службе
`CTRL_BREAK_EVENT`, см. `node/supervisor.py`); там, где `add_signal_handler` не поддержан
(Windows), используется `signal.signal`.

## SSH-сессии и tmux (`utils/ssh_sessions.py`)

Нужны автовыключению по простою (`node/service.py::maybe_auto_poweroff_idle`, `_close_ssh_sessions`):
Alfred не должен молча обрывать чужую работу на mycraft.

- `loginctl` уже обязателен в проекте (polkit-правила питания в `node/fixups.py` завязаны на
  systemd-logind). Сессия считается SSH, если у неё `Remote=yes` — так PAM помечает вход по сети.
  Проверено вживую 2026-08-03 на mycraft: обычная `systemd --user` linger-сессия даёт `Remote=no`,
  интерактивный `ssh mycraft` — `Remote=yes`.
- Разбор — построчный `Key=Value`, не `--value`: при нескольких `-p` подряд `show-session --value`
  отдаёт значения в собственном порядке свойств, а не в порядке аргументов, и позиционный разбор тихо
  путает поля.
- tmux — отдельный независимый сигнал простоя: сессия tmux переживает разрыв SSH (в этом её смысл),
  человек мог отсоединиться, а его процесс в панели ещё работает. `Remote=yes` её не видит. На
  2026-08-03 tmux на mycraft не установлен — `list_tmux_sessions` и `kill_tmux_server` глотают
  `FileNotFoundError` (нет бинарника = нет сессий), но общий `_run` — нет: для `loginctl`, единственного
  жёсткого источника правды о SSH, отсутствие бинарника должно падать, иначе поломка systemd-logind
  сделала бы автовыключение опасно «слепым». `list-sessions` у tmux возвращает ненулевой код и когда
  tmux нет, и когда сервер не поднят — для проверки разницы нет.
- `kill_tmux_server` гасит tmux целиком со всеми панелями: пользователь подтвердил кнопкой «выключить»,
  а не просто «отсоединить».

## Прочее
- `utils/version.py::version_key` — покомпонентное сравнение «0.21.0» → `(0, 21, 0)`; нечисловые
  компоненты считаются 0, чтобы неожиданный формат тега не ронял сравнение.
- `utils/system.py::system_uptime_seconds` — аптайм ОС: Windows через `GetTickCount64`, Linux из
  `/proc/uptime`; `None`, если определить не удалось.
- `utils/logging.py::configure_logging(level, fmt)` — `plain` или `json` (поля `ts`, `level`, `logger`,
  `msg`, `exc`), на stderr; `aiogram` и `apscheduler` приглушены до WARNING (шумят на INFO).

## stem

`utils/text.py::stem` — грубое «начало слова» для триграммного поиска (память `memory/service.py` и
восстановление реплик в `bot/dialogue_context.py`). Живая находка 2026-07-29 (первый настоящий прогон
памяти): записали «смотрим в озвучкЕ», спросили «какая у нас озвучкА» — ноль находок. Триграммный
индекс ищет подстроку целиком, и хвост «-ка» в «озвучке» не встречается. Отрезание окончания (6+ букв —
два символа, 4–5 — один) превращает поиск в поиск по началу слова: «озвуч» находит «озвучке»,
«озвучка», «озвучкой». Это не морфология, а грубое приближение без словарей и зависимостей.
