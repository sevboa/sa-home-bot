# Клиент Ollama (llm/ollama.py)

Тонкий клиент по loopback без HTTP-библиотек: `urllib` + `asyncio.to_thread` достаточно для одной локальной службы, отдельную зависимость проект не тянет. Плюс прогрев и усыпление контейнера в WSL2 (`container_backend="wsl-docker"`) или ожидание systemd-сервиса (`"native"`).

## Прогрев и холодный старт WSL (находки 2026-07-23)

- WSL на старой LTSC-инсталляции сама засыпает между вызовами `wsl.exe` и каждый раз стартует холодно; первый прогон занял ~95 с и не уложился в 90 с. Поэтому `_WARMUP_TIMEOUT_S = 150`. Это ожидаемый режим (требование владельца: модель не должна быть постоянно поднята, машина нужна и для другого), а не баг, который надо скрывать, держа WSL всегда тёплой.
- Даже когда `/api/version` уже отвечает, самый первый `/api/generate|chat` после холодного старта иногда обрывается («Remote end closed connection without response»): модельный бэкенд ещё не готов. Отсюда ретраи `_POST_RETRY_ATTEMPTS = 3` с паузой `_POST_RETRY_DELAY_S`.
- `ensure_running` вызывается на КАЖДУЮ попытку, а не один раз до цикла: иначе ретрай бился бы в ту же отвалившуюся WSL. Это быстрый no-op, если Ollama отвечает.
- Keepalive WSL здесь намеренно не заводится: `_post_with_retry` зовётся на каждый запрос, а VM нужна на весь тёплый idle-период (до 30 минут). Владелец — `LlmService` (`WslKeepalive.start/stop` вокруг простоя).
- `native`: своего «подъёма» нет, только ожидание ответа после рестарта systemd-юнита. `stop` для native не трогает процесс (always-on сервер под LLM), а просит Ollama выгрузить модель явным `keep_alive: 0`.

## Общий бюджет ретраев (находка 2026-07-27)

Раньше 3 попытки по (до 150 с прогрева + до `request_timeout_s` на POST) складывались в ~20 минут, а вызывающий ждёт ровно `request_timeout_s` (`Envelope.timeout_s`): клиент отваливался раньше, чем служба сдавалась, и вместо внятной ошибки приходил голый таймаут. Теперь дедлайн общий, новая попытка не начинается, если время вызывающего вышло.

Потоковый вариант (Этап 34, Фаза 2) отличается одним условием: не ретраить, если пришёл хотя бы один чанк. Накопленный текст уже ушёл в `on_chunk` (буфер частичной генерации виден пользователю в черновике), повтор с нуля задвоил бы его. Оба варианта — одна функция `_post_with_retry(..., on_chunk=None)`.

Ретраится только транзиентная ошибка соединения; `HTTPError` — реальный ответ сервера, повтор бессмыслен.

## Тело HTTP-ошибки (находка 2026-08-04)

`str(exc)` у `HTTPError` — голое «HTTP Error 400: Bad Request»; тело ответа Ollama с точной причиной валидации терялось, и разбор сбоя сводился к чтению логов трёх машин (`bot/node_events.py::ALBERT_TASK_MISSED`). `_append_error_body` дописывает тело (поле `error` из JSON или сырой текст) в `exc.msg`, оттуда оно идёт дальше в `ProtoError`. `utils/http` это сознательно не покрывает: POST живёт только здесь.

## keep_alive и num_ctx (находка 2026-07-24)

Без явного `keep_alive` Ollama выгружает модель через 5 минут после последнего ответа независимо от `idle_sleep_after_s` (тот управляет только жизнью WSL-VM/контейнера). Служба об этом не знала, пользователь видел «модель зачем-то выгружается» без единой реплики в образе. `_keep_alive_options` передаёт `idle_sleep_after_s` как `keep_alive` (секунды) и фиксирует `num_ctx` одинаково на каждый вызов: разный `num_ctx` у запросов к одной модели Ollama считает разной конфигурацией, не переиспользует KV-кэш и пересоздаёт раннер. Тот же эффект — Graphiti через `/v1` без `num_ctx` (лечится `OLLAMA_CONTEXT_LENGTH=32768`).

`options` вызова `chat` (Этап 50: сэмплинг служебного прохода, temperature 0 и потолок `num_predict`) смешиваются так, что `num_ctx` из `_keep_alive_options` не перезаписывается.

## preload (находка 2026-07-27)

`ensure_running` поднимает только контейнер и ждёт `/api/version` — модели в памяти при этом нет, первый реальный запрос платит десятки секунд за загрузку, и «прогрето» не значит «ответит в срок». Ollama на пустом `prompt` штатно загружает модель; `keep_alive` держит её до конца тёплого окна.

## think

`think` — `bool | str | None`. `None`: ключ не отправлять вовсе (не то же, что `False`: у gemma-4 явный `False` глушит скрытое рассуждение, отсутствие флага — нет). Строка (`low`/`medium`/`high`) — уровень для effort-моделей (gpt-oss). Готовое значение приходит из профиля модели (`llm/model_profiles.py`). В потоке (Этап 50) `thinking` копится только ради длины в логе (`_log_ollama_timings`), наружу боту не едет.

## Профили моделей (`model_profiles.py`)

Раньше «как у этой модели включается рассуждение» разносилось руками по четырём полям `[llm]` (`mode`, `think_style`, `single_call_think`, `think_chat`), хотя модель крутится на другой машине. Теперь служба по имени своей модели берёт профиль из `model-profiles.toml` (пакетный + локальный override рядом с `config.toml`; формат в шапке TOML) и сама переводит намерение-уровень (`off`/`low`/`medium`/`high`) в параметр Ollama `think`.

- Порядок `REASON_LEVELS` = индекс уровня, который выдаёт роутер.
- Контроль `off` — явный `False`; `on` — флаг не отправляется (уровень модель не понимает, а явный `think=true` отвергается с 400); `effort` — строка как есть; `flag` и любой нераспознанный — обычный булев тумблер.
- Локальные записи: с тем же `name` заменяют, новые идут перед `_default`. Если `_default` нет вовсе (битый override), есть жёсткий фоллбэк в коде.
- Боту в `describe()` едет урезанная сводка (`ModelProfileSummary`): нужен ли роутер-проход и уводит ли модель рассуждение в невидимый буфер. Перевод уровня остаётся на службе.
- Поле `LlmConfig.think_style` принимается и игнорируется (хранится в конфигах ради совместимости).
