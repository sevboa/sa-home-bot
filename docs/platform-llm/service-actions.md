# Действия службы llm

`LlmService` (`llm/service.py`) — `ServiceHandler` службы. Это единственный владелец состояния «тёплого окна»: активные чаты, флаги сна и прогрева, keepalive WSL, буферы стриминга и сессий.

## Действия

- `ask`, `chat` — диалог с Ollama по loopback; `chat` принимает `chat_id`, `request_id`, `reason`, `raw_image`, `user_id`, `speech_clear`, `mode`.
- `chat_progress` — чтение буфера частичной генерации по `request_id` (Этап 34, Фаза 2, Rich-стрим). `get_state()` параметров не принимает, а Альфред ведёт несколько диалогов разных чатов одновременно, поэтому частичный текст отдаётся не полем состояния, а обычной командой по `request_id`. Гонка первого опроса (бот спрашивает раньше, чем стрим завёл запись) — не ошибка, ответ `{"partial": "", "done": False}`.
- `warmup` — прогрев без генерации для службы tasks (`prewake_loop`, за `PREWAKE_LEAD_S` до `due_at`). Прогревает контейнер (`ollama.ensure_running`) и грузит модель (`ollama.preload`, находка 2026-07-27). Не вызывает `_touch(chat_id)`: прогрев не значит реального чата, ложный `chat_id` раздул бы список для `llm_idle_sleep`.
- `sleep` — ручной сон (`quiet=True` для штатного роспуска, когда бот уже попрощался).
- `look_at_photo` — повторный просмотр сохранённого фото по `photo_key` (`bot/tools.py::tool_look_at_photo`), без пересылки байт.
- `transcribe_voice`, `stt_upload_chunk` — распознавание голосовых (push-чанки, см. ниже).
- `synthesize_speech`, `tts_download_chunk` — синтез голосовых ответов (pull-чанки).
- `generate_image`, `item_portrait` — генерация картинок (см. [imagegen.md](imagegen.md)).
- `set_speech_clear` — переключение «чистой речи» гостя.

Отказы фото-путей возвращаются обычным `{"response": ...}`, а не полем-ошибкой: для `chat` это ложится в `ai_turns` как обычная реплика Альфреда (бот не знает про фото-специфику), для `look_at_photo` — как текст результата тула, который модель сама перескажет.

## Мультимодальный /ai (2026-08-10)

alfred присылает сырое фото ключом `raw_image` внутри ПОСЛЕДНЕГО элемента `messages` (это текущий ход пользователя; `history[-1]` в `bot/ai_flow.py::request_alfred`). Служба сама ресайзит и хранит (`llm/vision.py`) и возвращает `photo_key`. Известное ограничение v1: если роутер-проход на этом же ходу вызовет тул, `messages` вырастет и фото перестанет быть последним — картинка потеряется для финального ответа.

## Чанкование

- Голосовое на вход: короткое целиком base64 в `audio_b64`; длинное — сначала чанки `stt_upload_chunk` (push, `bot/voice_stt.py::_upload_chunked`, по образцу `vpn/service.py::ACTION_APK_CHUNK`, но в обратную сторону), затем `transcribe_voice` с `session_id` без `audio_b64`.
- Синтез на выход: готовое аудио инлайном, если base64 не превышает `_INLINE_TTS_B64_BYTES` (800 000, запас от `MAX_MESSAGE_BYTES`, base64 раздувает на треть), иначе сессия и pull-чанки `tts_download_chunk` (`bot/voice_tts.py`). Размер чанка — `proto.chunks.CHUNK_BYTES` (часть протокола, менять нельзя).
- Картинка генерации едет инлайном: даже PNG 512x512 укладывается в лимит. Хранит её бот (БД на alfred): mycraft штатно спит, повторный показ не должен её будить.

## TTL служебных словарей (`TtlStore`)

- Буфер стриминга `_streaming` — 120 с после завершения: чтобы отставший опрос бота успел забрать последний тик `done`; без подметания растёт без предела, если бот упал посреди опроса.
- Загрузка STT `_stt_uploads` — 300 с: недовершённую загрузку нечем продолжить (offset начался бы заново). Дольше стриминга, потому что причина сироты другая.
- Сессии синтеза `_tts_sessions` — 300 с: неполученный готовый результат.
- Подметает `idle_loop` раз в минуту (`_IDLE_CHECK_INTERVAL_S`).

## Сон, прогрев и presence

- Idle-таймер: после `idle_sleep_after_s` без запросов служба гасит контейнер (освобождает VRAM) и, если были чаты с реальными запросами, эмитит `llm_idle_sleep` со списком `chat_id`: бот шлёт закрывающее сообщение ровно один раз.
- `EVENT_WENT_IDLE` отдельно от `llm_idle_sleep`: тот адресован чатам и не эмитится без активных, а `node/app.py::on_local_event` нужен сигнал «простой дошёл до сна» без этого условия, иначе автовыключение (`node/service.py::maybe_auto_poweroff_idle`) никогда не сработало бы на машине, с которой не заговаривали (находка 2026-08-03). Эмитится только из `_maybe_sleep_idle`, не из ручного sleep.
- `notify_restart` перед остановом процесса (`llm/app.py`, блок finally) извещает активные чаты событием `llm_service_restart` (решение пользователя 2026-07-24); список чатов при тихом сне очищается и в `quiet`-режиме, иначе после роспуска это событие скажет «появились другие дела».
- `_warmup_confirmed` (находка 2026-08-26): после рестарта процесса `get_state()["asleep"]` равен `self._asleep or not self._warmup_confirmed`. Раньше presence-проверка (`wake_core.ensure_service_ready`) честно, но неверно докладывала «не сплю» у свежего процесса, а модель в VRAM не была загружена, и первый чат платил ~200 с холодной загрузки внутри своего таймаута. Флаг True только после реального обращения к Ollama и False после каждого сна. Отдельный флаг, а не изменение `_asleep`, потому что `_asleep` управляет idle-таймером и автовыключением.
- `WslKeepalive` (находка 2026-07-23) живёт здесь, на весь тёплый период, не вокруг одного запроса: короткие вызовы `wsl.exe` не держат VM, она гасла через секунды после каждого ответа. Актуален только для `container_backend="wsl-docker"`; на native Linux (mycraft) Ollama — systemd-сервис.
- `num_ctx` в `get_state` и ответах — действующее окно службы (явный `[llm].num_ctx` побеждает дефолт профиля), а не дефолт профиля: до 2026-09-30 боту уезжал дефолт gemma-4 (14336) при реальных 32768.

## Статистика и тайминги

- `_log_ollama_timings` (находка 2026-08-10): без неё разбор «почему Альфред отвечает 20 секунд» был гаданием. Выяснилось, что 222 токена скрытого рассуждения (`message.thinking`) уходили на ответ из пяти слов, а prefill шёл больше 1000 ток/с.
- `_usage_stats` (Этап 50, 2026-09-30) отдаёт боту `prompt_eval_count`, `eval_count`, `done_reason` и `num_ctx`: раньше бот не знал, что промпт дорос до ~31.8k из 32768, и пользователь получал пустой ответ или обрывок (`done_reason=length`). Отсутствующие поля не кладутся; нет ни одного счётчика — нет и `num_ctx`.

## Роли chat

- Ведущий интерактивов (`_director_chat`, Этап 47): system от бота, JSON-ответ, без тулов, рассуждения и Логопеда (картавость испортила бы и JSON, и текст рассказчика).
- Сжатие истории (`_summarizer_chat`, Этап 50): те же условия, ответ обычным текстом, temperature 0, потолок длины.
- Общий префикс обеих ролей (2026-08-10): `system[0]` всегда персонаж, служебная инструкция роутера уезжает последним system-сообщением в хвост. Иначе два непересекающихся префикса с нулевого токена не давали переиспользовать KV-кэш, а на SWA-моделях (gemma-4) ещё и сбрасывали его целиком («forcing full prompt re-processing ... SWA» в логах Ollama).
- Ответ с запросом инструментов не прогоняется через Логопеда: это служебные данные для цикла вызовов, не финальный текст.
- «Чистая речь» берётся на входе запроса, а не после генерации (живой баг 2026-09-28: генерация в очереди Ollama шла ~3 минуты, запрос, отправленный до смены передатчика, затирал состояние).
- `think`-намерение: `reason` (off|low|medium|high) -> голый `think` (устаревший bool: True=high, False=off) -> `off`. Перевод в параметр Ollama делает профиль модели.

## Персонаж из config.toml (находка 2026-07-25)

Текст персонажа убран из репозитория: берётся из локального `config.toml` (`settings.llm.persona_prompt`), при пустом — безликая заглушка, чтобы служба не падала на пустом system.
