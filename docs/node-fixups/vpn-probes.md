# netns-пробники `vpn_check`

Служба `vpn_check` (`vpn_check/service.py`) сама `awg-quick`/`xray` насовсем не поднимает и root
не получает (инвариант «долгоживущий процесс сам sudo не зовёт»). Готовую сеть заводит заранее
`nodectl fix`; сам процесс туннеля служба поднимает и гасит вокруг каждого чек-цикла (эфемерно,
компромисс ради слабого железа — решение владельца 2026-09-18).

## Решения владельца 2026-08-17/18
Проверка обязана быть ОДИНАКОВОЙ на любой ноде роя (никаких «эта нода особенная») и проверять
реальную работоспособность VPN глазами настоящего клиента, а не суррогат вроде чтения состояния
nftables/awg. Поэтому на каждой ноде с `vpn_check` интерфейс живёт изолированно в собственном
network namespace, а `vpn_check/service.py` всегда зовёт curl через `ip netns exec`.

С 39.0.7(d) цели — не хардкод «jeeves/awg» и не ручной `[vpn_check] probe_server`, а
автообнаружение: все живые vpn-серверы роя кроме себя (`bot/vpn_nodes.py::probe_targets`).
У каждой пары (сервер, транспорт) свои netns/veth/подсеть/интерфейс. Номер слота (индекс) привязан
к паре, а не к позиции в списке: он назначается один раз и хранится в `indices` файла
`vpn-probe-state.json` (ключ `сервер/транспорт`). Новая пара берёт первый свободный номер: обычные
транспорты с 0, `reality_alt` с 32, `awg_alt` с 48, `reality_xhttp` с 56 (`ALT_SLOT_INDEX_BASES`),
дальше по кругу до `SLOT_INDEX_LIMIT=128`. Транспорты, которые ещё не умеют провижинить
(`SUPPORTED_PROBE_TRANSPORTS`), попадают только в `vpn-check-probe-state`: слот зарезервирован.
Подсеть `10.200.200.0/24` нарезается на `/30` (индексы 0–63), индексы 64–127 уходят в
`10.200.201.0/24`; не пересекается с VPN `10.9.0.0/24`, домашним LAN `192.168.0.0/24` и CGNAT
Tailscale. Имя veth `vprobe<N>h0` и интерфейс `awg-probe<N>` с тремя цифрами укладываются в 15
символов. Старый state без `indices` принимается: номера берутся из `veth_host` его слотов.
Сетевой сбой обнаружения сводится к пустому списку с предупреждением: фиксы, не связанные с VPN,
не должны зависеть от доступности роя.

## Почему именно netns + veth + NAT (находки 2026-08-17/18/21)
1. Голый `ip netns add` без интерфейсов: внутри пустой `ip route`, хендшейку WireGuard некуда
   уйти, все проверки висят по таймауту (curl exit 28).
2. На ноде с самим VPN-сервером адрес пробника из подсети VPN (напр. `10.9.0.14`) совпадает с
   адресом, который машина обслуживает как сервер, то есть для root netns он «свой». Ядро
   безусловно отвергает пересылку с локальным source (`fib_validate_source`, martian source — не
   зависит от `rp_filter`, не лечится `accept_local`; подтверждено `nft monitor trace`). Единственный
   чистый путь — изолировать адрес пробника в другом netns.
Оба случая решает одно и то же: veth-пара между root netns и netns пробника плюс точечный
NAT/forward на хосте. Внутри netns `awg-quick` работает по умолчанию (без `Table=off`) — сам
заводит fwmark/ip rule и default route внутри netns. DNS отдельно не настраивается: Tailscale
MagicDNS `100.100.100.100` достижим через forward-правило veth (проверено на jeeves 2026-08-18).
3. `net.ipv4.ip_forward=0` (alfred, 2026-08-21): veth работал (ping до хоста проходил), до
   интернета пакеты не доходили, conntrack пуст — ядро дропает пересылку ДО netfilter. Фиксы
   включают его явно (`ensure_ip_forward`: sysctl.d + `sysctl -w`).
4. На alfred не был установлен nftables — любой `nft` тихо проваливался (rc≠0 трактуется как
   «пустой ruleset»), симптом неотличим от таймаута. `ensure_nft_installed`.

## Состав фиксов (порядок в `build_fixups`)
1. `vpn-probe-legacy-cleanup` — первым (см. ниже); сразу за ним `vpn-probe-stale-cleanup`.
2. `vpn-check-probe-forwarding` — точечные `nft insert rule` (НЕ `nft -f`, см.
   [network-and-proxy.md](network-and-proxy.md)): цепочки ищутся среди существующих базовых
   (`find_base_chain`); если нет — заводится собственная таблица `sa_vpn_probe` с политикой accept.
3. `vpn-check-probe-forwarding-persist` — юнит + скрипт, переигрывающие правила при каждом старте.
4. `vpn-probe-scaffold-*` — юнит `sa-home-vpn-probe-scaffold-<server>-<transport>.service`
   (`ExecStartPre` с ведущим `-` идемпотентно создаёт netns/veth/маршрут, а перед `link add`
   стоит `-ip link del <veth_host>`: хвост прошлого запуска не роняет старт; `RemainAfterExit` не
   сохраняет состояние ядра — netns пересоздаётся на каждом буте).
5. `vpn-probe-conf-*` — конфиг клиента.
6. `vpn-check-probe-sudoers` — `ip netns exec <ns> curl *`; для awg `ip route get *`,
   `awg-quick up|down <iface>`; для reality `timeout * xray run -c <conf>`. Не голый `ip`
   (равносилен root). Содержимое сверяется целиком: после смены состава серверов старый снипет не
   должен оставаться неполным. Без целей сниппет не пишется, а удаляется (находка 2026-11-11:
   нода osip не видела рой, visudo отверг пустой `NOPASSWD:`).
7. `vpn-check-probe-state` — `/etc/sa-home-bot/vpn-probe-state.json` (`node/vpn_probe_state.py`):
   что реально настроено; пишет root, читает `vpn_check` без sudo.
   С 2026-11-22 слот reality несёт `sni` (домен имени подключения): фикс-ап читает его из
   root-конфига слота (`sudo cat`), ничего не перевыпуская; `check()` по-прежнему «содержимое
   равно», поэтому старый state без `sni` перезаписывается один раз. Без конфига слота `sni`
   остаётся пустым.

## Конфиг пробника
Конфиг получают тем же путём, что обычный гость: действие `issue` службы vpn на конкретном сервере
`slot.server` с `chat_id=0` (`VPN_PROBE_CHAT_ID`, совпадает с `vpn/service.py::NODE_SENTINEL_CHAT_ID`;
службу целиком не импортируем ради константы). `transport` в аргументах ОБЯЗАТЕЛЕН: сервер с
несколькими транспортами (jeeves — awg+reality) иначе отвечает «укажите transport».
- **awg**: из конфига вырезаются строка `DNS =` (иначе `awg-quick` зовёт отсутствующий на Debian
  `resolvconf`, находка 2026-08-17) и любая `Table` (раньше писали `Table = off`, версии
  v0.92.2–v0.92.4; на развёрнутых нодах строка переживала апгрейд, и curl уходил мимо туннеля
  plaintext — инцидент 2026-08-31, находка 2026-08-21). `check()` ловит застрявшую `Table`.
- **reality**: сервер отдаёт sing-box-конфиг и `vless://`; из ссылки строится свой xray-конфиг с
  SOCKS5-inbound (`reality/probe_client_config.py`). Файл `0600`, один на слот.
- **Протухший конфиг** (2026-09-20): jeeves переустановили 18.09 — новый keypair и параметры
  обфускации, а `awg-probe0.conf` на wooster остался с 01.09; `nodectl fix` не чинил (файл на
  месте, `Table` нет). `probe_conf_stale` сверяет `[Peer] PublicKey` с `server_public_key` из
  `get_state` службы vpn. Осторожно в одну сторону: любая неясность (сервер недоступен, поля нет,
  ключ в файле не найден) — НЕ протух, иначе `fix` при лежащем сервере снёс бы рабочий конфиг.
  Конфиг, выданный этим же воплощением сервера, чинится на месте — без нового пира в БД vpn.
- Ручной приём: если на диске старый `awg-probe0.conf` и фикс его не перевыпускает — удалить файл и
  повторить `nodectl fix`.

## Forward/NAT переживает ребут (инцидент 2026-08-24, гонка 2026-09-23)
После потери питания alfred scaffold поднялся сам, а правила forward/NAT — нет: `nodectl fix` клал
nft-правила в живой ruleset и нигде не сохранял. Решение — systemd-юнит
`sa-home-vpn-probe-forward.service` со скриптом `/usr/local/lib/sa-home-bot/vpn-probe-forward-reapply.sh`
(идемпотентно через `grep -qF` по `nft list`; family/table/chain — те же, что выбрал живой apply).
Свою таблицу `sa_vpn_probe` скрипт досоздаёт (она тоже не переживает ребут); чужие таблицы
(firewall jeeves, `ip filter`/`ip nat` tailscaled) не создаёт, а ждёт (`wait_table`, до 60 с).
Гонка 2026-09-23: юнит стартовал раньше владельца таблицы, первый `insert` падал с «No such file
or directory», `set -e` прибивал остальное — forward/NAT не появились вовсе, проверки молча
таймаутили. Теперь `After=tailscaled.service` (для отсутствующего юнита systemd игнорирует),
`wait_table` в скрипте и `Restart=on-failure` / `RestartSec=30`. Содержимое юнита сверяется:
апгрейд 2026-08-17 (старый юнит гонял `awg-quick`) иначе застрял бы навсегда.

## Остатки прежней схемы (инцидент 2026-09-20)
До 39.0.7(d) был одиночный пробник: вечный awg-туннель в netns `vpn-probe` с veth `vprobe-veth0`
на `10.200.200.1/30`. Новая схема нарезает подсети с начала диапазона, и первый слот получает тот
же адрес — на хосте два интерфейса с одним адресом. Ядро выбирало старый (мёртвый) veth: хендшейк
уходил, сервер отвечал, ответ утекал в заброшенный netns — awg jeeves↔wooster «таймаутил» при
исправных сервере, конфиге и NAT, а reality-слот работал, что и сбивало с толку.
`vpn-probe-legacy-cleanup` выполняется первым: `disable --now` юнита (гасит туннель через
ExecStop), удаление файла, `daemon-reload`, потом `ip netns del` и `ip link del` (терпимо к
отсутствию цели) и проверка, что ничего не осталось.

## Сдвиг индексов слотов (находка 2026-11-22, osip и jeeves после появления ion)
Индекс слота считался по `enumerate` списка целей. Сервер ion сортируется первым, и индексы всех
слотов сдвинулись; то же при временной невидимости сервера на обнаружении. Фикс-ап переписывал
юниты сдвинувшихся слотов (имя юнита от индекса не зависит), но прежние veth/адреса оставались
в ядре (`vprobe0h0`, `10.200.200.1/30`). Новый старт падал: `RTNETLINK answers: File exists`,
`ipv4: Address already assigned`, `Cannot find device vprobe0n0`.

Ручной обход (до фикса): остановить все `sa-home-vpn-probe-scaffold-*`, снести `ip netns del`
для `vpn-probe-*` и `ip link del vprobe*h0`, затем `nodectl fix`.

Решение:
1. Стабильные индексы: сохранённое назначение в `indices` state. Выбрано вместо хэша имени:
   существующие ноды сохраняют свои номера (берутся из state), коллизии невозможны по построению,
   хэш пришлось бы разруливать сдвигами. Временно невидимый сервер остаётся в `indices`,
   поэтому его номер никому не отдаётся и слот не пересоздаётся при возвращении. При сбое
   обнаружения слоты пусты, а `indices` берётся из state целиком.
2. `vpn-probe-stale-cleanup`: юниты `sa-home-vpn-probe-scaffold-*`, netns `vpn-probe-*` и veth
   `vprobe<N>h0`, которых нет среди пар из `indices`, отключаются и удаляются (юнит, netns,
   veth). Пары из `indices` (включая невидимые) не трогаются. При пустом обнаружении фикс не
   срабатывает: сбой роя не должен сносить рабочее. `check()` — «лишнего нет».
   Не ловится: слот, у которого veth старого индекса в ядре совпал по имени с нынешним
   индексом другой пары; такой хвост снимает `ip link del` в начале скаффолда.
3. Скаффолд: добавлен `-ip link del <veth_host>` перед `link add`. Выбран минимально: удаление
   хост-конца сносит и пир, поэтому `link add` всегда проходит, а адреса и `link set up`
   ставятся на свежую пару. Правка `-` у `link set up` скрыла бы настоящие сбои.

## Порт reality-конфига после сдвига слота (находка 2026-11-22, osip)
`_reality_conf_check` сверяет `inbounds[0].port` файла `/etc/sa-home-bot/vpn-probe/<netns>.json`
с `slot.socks_port` (`REALITY_SOCKS_PORT_BASE + index`), а `_reality_conf_apply` при существующем
файле просто выходил. После сдвига номера слота фикс-ап вечно писал «команда прошла, но проверка
всё ещё отрицательна» и ничего не чинил. Удаление файла вручную выдавало бы нового пира chat 0
при живом старом, пробники копились бы.

Решение: если файл читается и это валидный JSON с `inbounds[0].port`, apply меняет только порт
на `slot.socks_port` и пишет файл обратно (`0600`), новый пир не выдаётся. Нечитаемый файл или
битый JSON ведут себя как отсутствие файла: конфиг запрашивается заново.

### Решение (2026-11-22): постоянная идентичность пробника

Наблюдатель передаёт `device_label = probe-<имя наблюдателя>-<транспорт слота>`
(`probe_tunnel.probe_device_label`). Имя берётся из `settings.node.id`, а если его нет, из
`socket.gethostname()`; транспорт слота полный: `awg`, `awg_alt`, `reality`, `reality_alt`,
`reality_xhttp`. Длина укладывается в `MAX_DEVICE_LABEL_LEN` (64): длинное имя наблюдателя
обрезается. Метка допускает любые символы кроме управляющих, а email xray становится
`c0-probe-osip-reality_alt`; xray и путь удаления клиента (`remove_client` по email во всех
трёх inbound) принимают его.

Сервер (`vpn/peers.py::_issue`): для `chat_id == PROBE_CHAT_ID` с явной меткой прежняя активная
строка с тем же `device_label` и транспортом строки отзывается (статус `revoked`, удаляются
awg-пир и xray-клиент), затем выдаётся новая. Ошибки «уже выдано» для пробника нет. Для обычных
чатов поведение прежнее. Слоты одного наблюдателя не отзывают друг друга: `reality`,
`reality_alt` и `reality_xhttp` ложатся в строки с `transport = reality`, `awg_alt` в строки с
`awg`, но метка у каждого слота своя. Без метки (старый наблюдатель) выдача идёт как раньше.

Порядок выката: сначала серверы (vpn), потом наблюдатели. Старый сервер принимает явную метку
как обычное имя и на повторную выдачу той же метки отвечает «уже выдано»; фикс-ап в этом случае
не получает конфиг.

Уборка сирот: пиры chat 0, чья метка не начинается с `probe-`. Только вручную, после того как
все наблюдатели перешли на новые имена и получили конфиги заново. Действие службы vpn
`prune_probe_peers` по умолчанию dry_run и ничего не снимает, возвращает список:

    nodectl -n <сервер> call vpn prune_probe_peers
    nodectl -n <сервер> call vpn prune_probe_peers dry_run=false

Аргументы `nodectl call` разбираются как `ключ=значение`, `true/false` распознаются по виду.
Гостевые пиры (`chat_id != 0`) действие не трогает.

### Миграция на постоянные имена и запись метки (2026-11-22)

Конфиги, выданные до перехода, принадлежат пирам со случайными именами; `nodectl fix` сам их не
перевыпускал (файл на месте и не протух). Поэтому фикс-ап `vpn-probe-conf-*` запоминает, под
какой меткой получен конфиг слота: рядом с конфигом reality лежит `<netns>.label`
(`/etc/sa-home-bot/vpn-probe/`, `vpn_probe_state.label_path`), в нём `probe_device_label`
на момент получения. Если записанной метки нет (старая нода) или она отличается от нынешней (сменилось
имя наблюдателя), `check` ложен, и `apply` один раз получает конфиг заново (awg и reality) и
записывает метку. Дальше `check` проходит и повторный `nodectl fix` ничего не делает.

Действие `prune_probe_peers` объявлено в `describe` службы vpn, иначе `proto/server.py` отвечает
«нет такого действия» и `nodectl call` его не вызовет (находка 2026-11-22, первая версия v0.201.2
убирала его из `describe`). В `capabilities` его нет, а бот не рисует действия службы vpn
кнопками (общие кнопки строятся только для node, apps и torrents), так что в меню оно не попадает.
Вызов только через `nodectl -n <сервер> call vpn prune_probe_peers`.

Порядок выката:
1. Обновить серверы (vpn), потом наблюдателей.
2. На каждом наблюдателе выполнить `nodectl fix`: слоты получают конфиги под `probe-<имя>-<транспорт>`.
3. `nodectl -n <сервер> call vpn prune_probe_peers`: по списку убедиться, что у всех наблюдателей
   `probe-*` уже есть (в списке должны остаться только сироты со случайными именами).
4. Только после этого `nodectl -n <сервер> call vpn prune_probe_peers dry_run=false`.
