# netns-пробники `vpn_check`

Служба `vpn_check` (`vpn_check/service.py`) сама `awg-quick`/`xray` насовсем не поднимает и root
не получает (инвариант «долгоживущий процесс сам sudo не зовёт»). Готовую сеть заводит заранее
`nodectl fix`; сам процесс туннеля служба поднимает и гасит вокруг каждого чек-цикла (эфемерно,
компромисс ради слабого железа — решение владельца 2026-09-18).

## Решения владельца 2026-08-17/18
Проверка обязана быть ОДИНАКОВОЙ на любой ноде роя (никаких «эта нода особенная») и проверять
реальную работоспособность VPN глазами настоящего клиента, а не суррогат вроде чтения состояния
nftables/awg. Поэтому на каждой ноде с `vpn_check` интерфейс живёт изолированно в собственном
network namespace, а `vpn_check/service.py` всегда зовёт curl через `ip netns exec`.

С 39.0.7(d) цели — не хардкод «jeeves/awg» и не ручной `[vpn_check] probe_server`, а
автообнаружение: все живые vpn-серверы роя кроме себя (`bot/vpn_nodes.py::probe_targets`).
У каждой пары (сервер, транспорт) свои netns/veth/подсеть/интерфейс; имена выводятся
детерминированно из позиции пары в отсортированном списке (`probe_slot_from_target`) и стабильны
между прогонами, пока состав целей не меняется. Транспорты, которые ещё не умеют провижинить
(`SUPPORTED_PROBE_TRANSPORTS`), попадают только в `vpn-check-probe-state`: слот зарезервирован,
номера у остальных не съезжают. Подсеть `10.200.200.0/24` нарезается на `/30` по числу целей — не
пересекается с VPN `10.9.0.0/24`, домашним LAN `192.168.0.0/24` и CGNAT Tailscale.
Сетевой сбой обнаружения сводится к пустому списку с предупреждением: фиксы, не связанные с VPN,
не должны зависеть от доступности роя.

## Почему именно netns + veth + NAT (находки 2026-08-17/18/21)
1. Голый `ip netns add` без интерфейсов: внутри пустой `ip route`, хендшейку WireGuard некуда
   уйти, все проверки висят по таймауту (curl exit 28).
2. На ноде с самим VPN-сервером адрес пробника из подсети VPN (напр. `10.9.0.14`) совпадает с
   адресом, который машина обслуживает как сервер, то есть для root netns он «свой». Ядро
   безусловно отвергает пересылку с локальным source (`fib_validate_source`, martian source — не
   зависит от `rp_filter`, не лечится `accept_local`; подтверждено `nft monitor trace`). Единственный
   чистый путь — изолировать адрес пробника в другом netns.
Оба случая решает одно и то же: veth-пара между root netns и netns пробника плюс точечный
NAT/forward на хосте. Внутри netns `awg-quick` работает по умолчанию (без `Table=off`) — сам
заводит fwmark/ip rule и default route внутри netns. DNS отдельно не настраивается: Tailscale
MagicDNS `100.100.100.100` достижим через forward-правило veth (проверено на jeeves 2026-08-18).
3. `net.ipv4.ip_forward=0` (alfred, 2026-08-21): veth работал (ping до хоста проходил), до
   интернета пакеты не доходили, conntrack пуст — ядро дропает пересылку ДО netfilter. Фиксы
   включают его явно (`ensure_ip_forward`: sysctl.d + `sysctl -w`).
4. На alfred не был установлен nftables — любой `nft` тихо проваливался (rc≠0 трактуется как
   «пустой ruleset»), симптом неотличим от таймаута. `ensure_nft_installed`.

## Состав фиксов (порядок в `build_fixups`)
1. `vpn-probe-legacy-cleanup` — первым (см. ниже).
2. `vpn-check-probe-forwarding` — точечные `nft insert rule` (НЕ `nft -f`, см.
   [network-and-proxy.md](network-and-proxy.md)): цепочки ищутся среди существующих базовых
   (`find_base_chain`); если нет — заводится собственная таблица `sa_vpn_probe` с политикой accept.
3. `vpn-check-probe-forwarding-persist` — юнит + скрипт, переигрывающие правила при каждом старте.
4. `vpn-probe-scaffold-*` — юнит `sa-home-vpn-probe-scaffold-<server>-<transport>.service`
   (`ExecStartPre` с ведущим `-` идемпотентно создаёт netns/veth/маршрут; `RemainAfterExit` не
   сохраняет состояние ядра — netns пересоздаётся на каждом буте).
5. `vpn-probe-conf-*` — конфиг клиента.
6. `vpn-check-probe-sudoers` — `ip netns exec <ns> curl *`; для awg `ip route get *`,
   `awg-quick up|down <iface>`; для reality `timeout * xray run -c <conf>`. Не голый `ip`
   (равносилен root). Содержимое сверяется целиком: после смены состава серверов старый снипет не
   должен оставаться неполным.
7. `vpn-check-probe-state` — `/etc/sa-home-bot/vpn-probe-state.json` (`node/vpn_probe_state.py`):
   что реально настроено; пишет root, читает `vpn_check` без sudo.

## Конфиг пробника
Конфиг получают тем же путём, что обычный гость: действие `issue` службы vpn на конкретном сервере
`slot.server` с `chat_id=0` (`VPN_PROBE_CHAT_ID`, совпадает с `vpn/service.py::NODE_SENTINEL_CHAT_ID`;
службу целиком не импортируем ради константы). `transport` в аргументах ОБЯЗАТЕЛЕН: сервер с
несколькими транспортами (jeeves — awg+reality) иначе отвечает «укажите transport».
- **awg**: из конфига вырезаются строка `DNS =` (иначе `awg-quick` зовёт отсутствующий на Debian
  `resolvconf`, находка 2026-08-17) и любая `Table` (раньше писали `Table = off`, версии
  v0.92.2–v0.92.4; на развёрнутых нодах строка переживала апгрейд, и curl уходил мимо туннеля
  plaintext — инцидент 2026-08-31, находка 2026-08-21). `check()` ловит застрявшую `Table`.
- **reality**: сервер отдаёт sing-box-конфиг и `vless://`; из ссылки строится свой xray-конфиг с
  SOCKS5-inbound (`reality/probe_client_config.py`). Файл `0600`, один на слот.
- **Протухший конфиг** (2026-09-20): jeeves переустановили 18.09 — новый keypair и параметры
  обфускации, а `awg-probe0.conf` на wooster остался с 01.09; `nodectl fix` не чинил (файл на
  месте, `Table` нет). `probe_conf_stale` сверяет `[Peer] PublicKey` с `server_public_key` из
  `get_state` службы vpn. Осторожно в одну сторону: любая неясность (сервер недоступен, поля нет,
  ключ в файле не найден) — НЕ протух, иначе `fix` при лежащем сервере снёс бы рабочий конфиг.
  Конфиг, выданный этим же воплощением сервера, чинится на месте — без нового пира в БД vpn.
- Ручной приём: если на диске старый `awg-probe0.conf` и фикс его не перевыпускает — удалить файл и
  повторить `nodectl fix`.

## Forward/NAT переживает ребут (инцидент 2026-08-24, гонка 2026-09-23)
После потери питания alfred scaffold поднялся сам, а правила forward/NAT — нет: `nodectl fix` клал
nft-правила в живой ruleset и нигде не сохранял. Решение — systemd-юнит
`sa-home-vpn-probe-forward.service` со скриптом `/usr/local/lib/sa-home-bot/vpn-probe-forward-reapply.sh`
(идемпотентно через `grep -qF` по `nft list`; family/table/chain — те же, что выбрал живой apply).
Свою таблицу `sa_vpn_probe` скрипт досоздаёт (она тоже не переживает ребут); чужие таблицы
(firewall jeeves, `ip filter`/`ip nat` tailscaled) не создаёт, а ждёт (`wait_table`, до 60 с).
Гонка 2026-09-23: юнит стартовал раньше владельца таблицы, первый `insert` падал с «No such file
or directory», `set -e` прибивал остальное — forward/NAT не появились вовсе, проверки молча
таймаутили. Теперь `After=tailscaled.service` (для отсутствующего юнита systemd игнорирует),
`wait_table` в скрипте и `Restart=on-failure` / `RestartSec=30`. Содержимое юнита сверяется:
апгрейд 2026-08-17 (старый юнит гонял `awg-quick`) иначе застрял бы навсегда.

## Остатки прежней схемы (инцидент 2026-09-20)
До 39.0.7(d) был одиночный пробник: вечный awg-туннель в netns `vpn-probe` с veth `vprobe-veth0`
на `10.200.200.1/30`. Новая схема нарезает подсети с начала диапазона, и первый слот получает тот
же адрес — на хосте два интерфейса с одним адресом. Ядро выбирало старый (мёртвый) veth: хендшейк
уходил, сервер отвечал, ответ утекал в заброшенный netns — awg jeeves↔wooster «таймаутил» при
исправных сервере, конфиге и NAT, а reality-слот работал, что и сбивало с толку.
`vpn-probe-legacy-cleanup` выполняется первым: `disable --now` юнита (гасит туннель через
ExecStop), удаление файла, `daemon-reload`, потом `ip netns del` и `ip link del` (терпимо к
отсутствию цели) и проверка, что ничего не осталось.
