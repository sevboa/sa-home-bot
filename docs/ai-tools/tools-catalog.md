# Каталог тулов

Права указаны как `requires` / `variants` в `ToolSpec`. Тексты описаний для модели лежат в `_DECL_*` соответствующего модуля.

## calc (`calc.py`)
Без сети и роя, `ast` с белым списком узлов (не `eval()`). Разрешены числа, `pi`, `e`, `+ - * / // % **`; степень не больше 1000 по модулю (защита памяти/CPU). Результат округляется до 6 знаков: «32.98672286269283» персонаж не произнёс бы. `pi`/`e` добавлены 2026-07-24 (площадь цилиндра): без констант модель подставляла «3.14159» сама или не звала тул. `^` заменяется на `**` текстом ДО парсинга: приоритет `^` в Python другой (ниже `+`), трактовка узла BitXor как степени ломала выражения сложнее одного `a^b`.

## get_weather (`weather.py`)
Тул «что сейчас в городе»: погода + местное время, время суток, солнце, луна (с 2026-10-09; всё считается локально по координатам и поясу из ответа Open-Meteo, `get_time.place_now`). Город из конфига (`[weather].city`) и город из вопроса резолвятся геокодером Open-Meteo, а не «памятью» модели: небольшая модель путает широту и долготу. Кэш `_GEOCODE_CACHE` на время жизни процесса. Геокодер плохо ищет кириллицу (2026-10-09: «Мурманск» → посёлок Мурманский, «Бран» → деревня во Франции, румынского Брана нет вовсе), поэтому ищем и как написано, и транслитом (`translit.CYRILLIC_TO_LATIN`) и выбираем сами: страна из «Город, Страна», точное совпадение имени, населённый пункт, ранг (`PPLC`>`PPLA`>`PPLA2`>`PPLA3`), население. Живой баг 2026-07-24: декларация не принимала город вообще — модель на вопрос про другой город честно отказывала. WMO-коды переведены таблицей: модель сама их не знает.

## convert_currency (`currency.py`)
Умножение делает сам тул (второй круг через `calc` — лишняя генерация без выгоды в точности). Курсы — open.er-api.com (рыночные, ~160 валют, включая RUB/KZT), кэш на час: источник обновляется раз в сутки.

## get_time (`get_time.py`)
Живой баг 2026-07-24: на «точное время по Москве/в Казахстане» модель пересчитывала пояса сама — неверно и непоследовательно; на «разницу между Москвой и Италией» тула не было вовсе. Теперь пояса и разницы по каждой паре мест считает тул (stdlib `zoneinfo`, сеть не нужна — важен только IANA-пояс, поэтому статическая таблица `_PLACE_TIMEZONES` вместо геокодинга). `places` — список для сравнения; `place` — одно место, плоский формат ответа не менялся. «По Гринвичу»/«GMT» в быту значит UTC (смещение 0 всегда), а не гражданское время Гринвичской обсерватории (Europe/London, летом BST) — поэтому `гринвич`, `гмт`, `gmt`, `utc` → `UTC`.

## remind (`remind.py`)
Единственный ПИШУЩИЙ тул, ходящий по протоколу роя мимо служб-адаптеров: создаёт в службе `tasks` отложенную задачу «спросить нейронку ещё раз в момент X» (§8.5; обобщено 2026-07-24 — раньше писал константный готовый текст прямо в БД бота, теперь доставка — новый живой ответ модели). Права: без `requires`, он появился до правил доступа и работает у живых пользователей; долг — завести право `create@tasks`, когда будет повод трогать подписки в проде.
- `when` — ISO 8601; наивное время считается локальным временем процесса (в нём модель видит «текущее время» из `ai_flow._build_context_note`).
- `after_event={node, event}` — проснуться по событию ноды (`restart_applied` | `update_finished`). Дедлайн-страховка `RESTART_EVENT_FALLBACK_S` (300 с) нужен, чтобы задача не ждала вечно; модель его не указывает — не знает, сколько займёт рестарт. Сама ожидание живёт в службе `tasks` (`ACTION_MATCH_EVENT`), не в БД бота (решение владельца 2026-08-05: remind, вызванный из уже сработавшего хода, исполняется внутри `tasks` и не имеет `ctx.store`).
- Директива после срабатывания по событию НЕ содержит конкретного времени дедлайна (решение владельца 2026-08-05): маленькая модель (Gemma) читала время как приглашение сверить часы и звала `get_time` по кругу. Срабатывание могло прийти и по событию, и по таймауту — модель сверяет состояние сама и не выдаёт желаемое за случившееся.
- `woken_by` — жёсткий отказ вместо словесного запрета повторно ждать то же событие (см. incidents.md, 2026-08-05).
- `_close_pending_tool_calls` — снимок `ctx.history` для remind делается ИЗ СЕРЕДИНЫ раунда: `run_chat_loop` дописывает единственное сообщение assistant с `tool_calls` на раунд, а ответные `tool` — только после возврата обработчика, поэтому вызов remind (и все после него) висят без ответа. Повторное проигрывание такой истории службой `tasks` даёт Ollama невалидную форму (assistant/tool_calls без ответа и сразу новый user): HTTP 400 на `/api/chat`, 2026-08-04. Недостающие `tool`-ответы дозаполняются в снимке, а не в живом `history`. Первому висящему вызову (всегда самому текущему) подставляется настоящий `_self_result`, остальным — «(результат не сохранён)».
- Уровень рассуждения на срабатывании: router-прохода тогда нет, берётся `config.reminder_reason` из legacy-полей; перевод в параметр Ollama делает профиль модели на стороне `llm` (`llm/model_profiles.py`) — отсюда исчезли баги с явным `think=true` → 400 на gemma (2026-08-05/08-10). `tools` в задачу не кладутся: комплект собирается заново при срабатывании по правам на тот момент.
- В `meta` задачи уезжает `message_thread_id` (2026-08-05: без него ответ `tasks` уходил в общий топик личного чата, а не туда, где шла переписка; `bot/node_events.py::_handle_task_result`/`_handle_task_prewake`). Для after_event туда же кладутся `awaited_node`/`awaited_event` — восстанавливаются в `ToolContext.woken_by` (`tasks/service.py::_fire_chat_loop`).
- `schedule_agent_dialogue` — НЕ ToolSpec, модель её вызвать не может: внутренняя функция для кода (речь Альфреда перед формой подтверждения и оповещением итога, Этап 45; `meta_extra` несёт `pending_action_id`/`stage`). Задача начинает НОВЫЙ тред у произвольного собеседника (`dialogue_id` рождает `bot/node_events.py::_handle_task_result`, Этап 44.2), `due_at` = сейчас — триггер уже наступил. Ошибки не проглатываются: вызывающий решает сам.

## Знакомства гостей (`acquaintance.py`, Этапы 42.6 → 45 → 46)
Решение владельца 2026-09-27: связь между гостями ОДНА — факт знакомства, взаимный и без степеней. Типы друг/знакомый/родство/супруг(а) (42.6.x) убраны: выбор типа сталкивал лбами людей, не определившихся между собой. Что бы собеседник ни сказал («мой друг», «моя жена»), Альфред предлагает знакомство. Групповой флаг «семья» (`Subscription.family`) убран тогда же. Подтверждённое знакомство открывает `tell` в обе стороны. Запрос живёт в `pending_actions` и решается кнопками форм; в `guest_relationships` пишется только итог. Отзыв знакомства не нужен (то же решение). Старые строки других типов миграция переписала в `acquaintance`, поэтому тип не сверяется.
- `request_acquaintance` НЕ отправляет предложение: создаёт черновик (срок 1 ч), форму с кнопками «Отправить»/«Отмена» бот присылает отдельным сообщением ПОСЛЕ ответа Альфреда (`bot/handlers/ai.py` → `PendingActions.flush_drafts`). Адресат — по id (Этап 54.5). Службе `tasks` формы показать некому — честный отказ. Без `requires`: открыто любому подписанному гостю. Инициатор в этом чате — всегда сам собеседник: в тексте, адресованном ему, его нельзя называть по имени в третьем лице (находка 2026-09-26; Gemma озвучивала такое слово в слово).
- `acquaintance_conflict` проверяется на открытии формы И повторно на «Отправить»/«Принять» (за час/трое суток ожидания могли познакомиться иначе или прийти встречное предложение). Находка 2026-10-09: ответ про Александра модель пересказала как «отправил Андрею» — id был взят не тот, поэтому в тексте отказа есть подсказка искать нужного `find_person`.
- `my_acquaintances` — только подтверждённые; про неотвеченные и отклонённые молчим намеренно (IMPLEMENTATION_PLAN.md §42.6.3). `acquaintance_roster` возвращает `(chat_id, имя)`: по id `tell` находит человека точно (баг 2026-09-28: «передай маме» ушло в «Наталья Вадимовна», хотя знакома была Милана).
- Падежи (`_guest_facing_name`, находка 2026-09-26): `Subscription.name` у владельца в проде технически «me» — ключ подписки, а не имя, и он утекал в чужие тексты («Гость «me» предложил…»). Имя берётся из карточки человека (Этап 58). Имя в карточке — в именительном: нельзя вставлять в предложение, где нужен другой падеж («у Наташа Сорокина»). Падеж держать на служебном слове («адресату (…)», «с адресатом (…)»), имя — именительным лейблом в скобках.

## Карточки людей (`people_tools.py`, Этапы 54.2, 54.4, 58)
- `note_person` — без `requires`: о себе может сказать любой, о другом — только его знакомый (проверяет обработчик). Вес утверждения решает бот, не модель: о себе — сильное, о знакомом — слабое, о постороннем — отказ. Находка 2026-10-09: «Я знаком с Андреем, это мой брат» — модель без `find_person` взяла id Александра (единственный id в семейных фактах памяти), а безымянный отказ ещё и подсказал открыть знакомство с ним же; поэтому отказ называет того, чей это id (`_note_person_stranger`).
- `find_person` — без `requires`: ищет только среди тех, к кому собеседнику вообще можно обратиться. `purpose="message"` (для `tell`/`notify_guest`): у гостя — подтверждённые знакомые и роль владельца; у владельца — все гости в личке. `purpose="acquaintance"`: все гости, но по точному имени/нику/прозвищу и без выдачи списка (гостю он не положен). Заходы от строгого к мягкому: как названо; та же основа (падеж, слово без последней буквы); начало слова по основе; последний — по отдельным словам без служебных и с транслитом ника (находка 2026-10-09: «Андрей который кейн» → ник kein). @ник в описании точнее любого имени рядом (там же: «Александр Сергеевич Севбо @ksytal_as» целиком не совпадал ни с одной меткой). Несколько кандидатов отдаются все с отличиями, выбирает собеседник.

## Интерактивные тулы (`interactive_tools.py`)
Тонкие обёртки над методами `Interactives`; службе `tasks` интерактивов нет — честный отказ. `swap_radio` (Этап 47) — один тул на обе стороны: до конца «Проклятого передатчика» запускает/продвигает сцену, после — переключатель старый/новый передатчик; решает кнопка формы, не модель. `manor_items` (49.3.6): опись модели, `show` — карточка вещи в чат; пока портрет рисуется, Альфред молчит до карточки (`end_turn`; «сейчас подготовлю описание» ломало четвёртую стену, 2026-10-15). `take_photo` (49.2): рисуется в фоне и приходит сам; до готовности снимка Альфред молчит — описание «до снимка» выходило выдуманным (2026-10-02). `item_action` (49.3.7) — форма. `search`/`act`/`walk`/`go` (59.1/59.7/59.4/59.5) — канарейка, исход решает код/Ведущий.

## Картинки (`pictures.py`)
- `generate_image` (Этап 48) — право `generate_image@llm`: генерация будит mycraft и ~15 с грузит CPU, поэтому отдельное право, а не часть `chat@llm`. Эпизод графа передаётся колбэком (`image_tools` не импортирует `bot.tools`); колбэк не полагается на порядок вызовов чужого модуля и молча пропускается без `chat_id`.
- `find_image` — без `requires`: ищет только по картинкам СВОЕГО чата (таблица `images` бота, mycraft не будит); картинки появляются только через `generate_image`.
- `look_at_photo` (мультимодальный /ai, 2026-08-10): точечный повторный просмотр уже сохранённого фото. Файл лежит на mycraft (ресайз и хранение — служба `llm`, `llm/vision.py`); тул передаёт ключ и вопрос. Свои картинки Альфред не видит, пока не посмотрит этим тулом (2026-10-02): байты берутся из БД так, как их видел гость; ответ гостя на картинку Альфреда — значит, о ней речь. Результат — эпизод графа (Этап 42.2).

## swarm_status / swarm_events (`swarm.py`)
- `swarm_status` (read-only, LLM_INTEGRATION_PLAN.md §8.3): сбор через `wake_core.collect_reports` — тот же веерный опрос, что у /swarm (`bot/swarm_view.py`), без Telegram-рендеринга; второго пути к данным нет. Права `variants`: `nodes` → команда `/nodes`, `health`/`disks` → `/status`. Различие «спит — норма» и «пропала машина, обязанная быть в сети» (ARCHITECTURE §11 п. 4) отдаётся полем `sleeping_is_normal`, а не эмодзи: как это сказать — решает персонаж. Торренты были значением `what` (2026-07-27), затем уехали в отдельный тул `torrents`.
- `swarm_events`: журнал уже произошедшего (`store.record_event` пишет туда те же строки, что уходят в рассылку). Решение владельца 2026-08-04: раньше у Альфреда не было доступа даже к случившемуся. Право — то же, что у `/nodes` (`CommandRight`), нового не заводили: те же данные о рое в прошедшем времени.

## node_manage (`node_manage.py`)
Те же действия, что кнопки карточки ноды (/nodes) и `nodectl check_update/update/restart_node`; права ровно те же (`действие@node`). `check_all` — то же право, что `check_update`, сразу по всему рою (`wake_core.check_updates_summary`, общее с кнопкой панели /swarm). `update` ставит файлы БЕЗ рестарта процесса (`node/update.py`), новая версия заработает только после `restart_node`. `restart_node` перезапускает ноду-супервизор целиком; на своей ноде Альфред ненадолго пропадёт и вернётся сам. Сервер сам отсекает неподдерживаемое действие (`ERR_UNKNOWN_ACTION` в `proto/server.py::_run_command`), заранее знать, что умеет нода, не нужно. Чужая нода сверяется со свежим списком роя, иначе вместо ошибки был бы голый таймаут.
Авто-ожидание (`_auto_await_event`): код сам ставит `remind(after_event=…)` сразу после `update`/`restart_node`, а не просит модель (решение владельца 2026-08-05: модель словами обещала «прослежу», но тул не звала). Подробности трёх заходов — в incidents.md.

## torrents (`torrents.py`)
Раньше «что качается» было значением `what` у `swarm_status` (2026-07-27). С действиями, которые не только читают (`add`/`pause`/`resume`), держать закачки в тулe «состояние роя» неверно и по смыслу, и по правам: там одно право на весь тул, а тут разное на каждое действие. Один тул с enum, а не пять: общее описание у всех одно, а права раздельные (`VariantRights`). `search_smart` — альтернативный путь к `search` тем же логином и трекерами, отдельного права нет. Источник раздачи: magnet-ссылка от человека либо `source` из выдачи СВОЕГО поиска; base64-файл не пускаем (файл человек присылает вложением, `bot/handlers/torrents.py`). Произвольный http отсекает служба (`torrents/service.py::_add_sync`) — копии знания о плагинах в боте не держим. Нода со службой ищется опросом роя (`_service_host`): службы переезжают кнопкой в боте. Параметр `magnet` — историческое имя, принимает и `source`: переименование сломало бы работающие формулировки. Описание намеренно сжато (2026-07-29): декларации уходят в контекст на каждом раунде, вместе с выдачей поиска они выбивали окно в 8k токенов — ответ приходил пустым или обрывался.

## dismiss (`chat_controls.py`)
«Ты свободен» гасит модель и машину под ней. Единственный тул, ничего не делающий при вызове (см. `DismissalBox`). Машина здесь не параметр: это ровно нода, с которой только что говорили (`LLM_NODE`), иначе «выключись» означало бы «выключи любую машину роя», включая ту, где живёт бот, — даже как опечатка недопустимо. Права: `model` → `sleep@llm`, `sleep` → `suspend@node`, `off` → `poweroff@node` (те же, что у кнопок карточки).

## voice_mode (`chat_controls.py`)
Личная настройка формата ОТВЕТА, `requires=None`. Состояние per-chat в `app_state` (`bot/voice_mode.py`), эффект немедленный (в отличие от `dismiss`): текущий ответ ещё может уйти текстом, следующий — голосом.

## recall_tool_result (`chat_controls.py`)
Находка 2026-09-04: длинные результаты тулов (в первую очередь `web_search`) сокращаются перед отдачей модели (`llm_chat.py::_inline_or_cache`) — несколько подряд добивали окно контекста (`num_ctx` в `llm/model-profiles.toml`), и модель возвращала пустой ответ. Полный текст лежит в `ctx.tool_result_cache` под id из пометки «сокращено»; этот тул — единственный способ его достать. Без `requires`: раскрывает не больше, чем породивший результат тул.

## memory (`memory.py`)
Модель не выбирает, чью память трогать: `chat_id` проставляет бот из контекста («вспомни, что говорили в другом чате» не должно работать — память сознательно раздельная, `memory/service.py`). Подмешивает факты и бот перед каждым запросом (`bot/ai_flow.py`): на тул надежда плохая, зовёт его модель далеко не всегда. `remember` дублирует текст эпизодом в графовую память (Этап 41) — best-effort поверх уже успешной записи (`piggyback_graph_episode`: короткий таймаут 2 с, все ошибки подавляются; mycraft со службой `graph_memory` штатно спит). Лимит `_GRAPH_EPISODE_MAX_CHARS = 400` совпадает с `graph_memory/service.py::MAX_EPISODE_CHARS`: служба отклоняет более длинный текст `ERR_BAD_REQUEST`, а piggyback проглатывает все ошибки — эпизод терялся бы молча.

## vpn (`vpn.py`, Этап 33; модель устройств — Этап 57, 57.8)
Секреты (ключи, ссылки vless, QR, `.conf`) НИКОГДА не проходят через модель и не выпускаются тулом: их отдают только кнопки /vpn сообщениями бота с удалением по TTL. Тул лишь присылает нужный экран с кнопкой — те же экраны, что в /vpn; поэтому `ctx.notifier.send_document/send_photo` здесь нет вовсе (иначе секрет осел бы в `ai_turns`/контексте). `chat_id` подставляет бот; `chat_id=0` — пробник `vpn_check`, не человек. Прокси Telegram (`proxy_link` без `server`) отдаёт ссылки СРАЗУ со всех серверов (решение владельца 2026-09-20). Сводка по всем гостям (`all_guests`) — только с `peers@vpn`; сверка самим тулом, а не доверие декларации. Подключение другого человека (`recipient`) — только админ. Права действий `settings` → `vpn_card@vpn`, `report` → `usage@vpn` (как у кнопок). Справка в описании собрана из `vpn_facts.ANSWERS` — те же слова, что на кнопках «Помощь».

## web_search (`web_search.py`, LLM_INTEGRATION_PLAN.md §9)
Интернет через собственный SearXNG (служба `net` на mycraft). Таймаут вызова = `net.request_timeout_s` + 5 с запаса на дорогу alfred ↔ mycraft (находка 2026-09-25: без явного таймаута действовали 10 с `ProtoClient` по умолчанию при 20 с на поиск, медленный brave обрывал ответ целиком). Недоступный поисковик — обычный результат, персонаж сам решит, как сказать. Сырая выдача — тоже эпизод графа (Этап 42.3).

## tell (`tell.py`, `delivery.py`, IMPLEMENTATION_PLAN.md этап 28)
Право `tell@llm` — «действие@служба» на ту же службу `llm`: передача сообщений — умение Альфреда, а не отдельная команда бота. Владельцу можно написать по РОЛИ («хозяину/владельцу/админу», `to_owner_role`) всегда; по личному имени он такой же человек, как все — нужно подтверждённое знакомство (решение 2026-09-27: владелец через `*` писал гостю, с которым знакомства не было). Права `tell_guests@llm` (этап 36) и групповой флаг «семья» убраны. Официально написать любому гостю владелец может через `notify_guest`. Адресат — только по `recipient_id` (Этап 54.5): раньше искали по придуманному моделью имени, и `tell` отвечал «такого нет» (14 неудач к 2026-10-08). Шапка «📨 Альфред … по просьбе X» обязательна: получатель должен видеть, что это не бот сам придумал написать, а Альфред передаёт просьбу человека.
Лимиты (находка 2026-08-06): раньше был один лимит на автора (10/час) — рассылка одного `notify_guest` десятерым тратила его целиком так же, как 10 повторов одному человеку, хотя риски разные (легитимная рассылка и зациклившаяся модель). Решение владельца — два независимых потолка: `TELL_MAX_PER_RECIPIENT_PER_HOUR = 10` на пару (кто просил, кому) и `TELL_MAX_TOTAL_PER_HOUR = 100` на инициатора. Порядок проверки важен: сперва тесный потолок, чтобы зациклившаяся на одном человеке модель не жгла общий бюджет. Доставленное сообщение записывается как ход диалога получателя (`ai_turns`): реплаем на него разговор продолжается (`bot/handlers/ai.py::AiReplyContinuation`). Через службу `tasks` доставка fire-and-forget (`ctx.emit`, `EVENT_DELIVER_MESSAGE`); проверку знакомства бот делает сам перед отправкой (`require_acquaintance` в событии).

## notify_persona / notify_guest (`notify.py`)
Официальное уведомление гостю от владельца — другой канал, чем `tell` (личная передача просьбы). Видимость обоих тулов (право `invite` есть только у владельца) уже отличает владельца, поэтому обработчики прав не перепроверяют. Два вызова, а не один — намеренно (2026-08-05, живой запрос после первой версии с обёрткой текста): если бы персонажа выбирал сам `notify_guest`, текст модель писала бы нейтрально, а стиль был бы только в шапке — тонкая имитация. `notify_persona` выбирает случайного персонажа и отдаёт промпт, КАК писать в его манере; текст сочиняется следуя ему и только потом уходит `notify_guest`. При уведомлении нескольких гостей `notify_persona` зовётся заново на каждого. Модель иногда копирует `persona` вместе с эмодзи («Граф 🦇», баг 2026-08-05), поэтому `_resolve_persona` терпим к лишнему вокруг названия.

## guests_list (`guests_list.py`)
Справочник гостей для владельца (то же право, что у `/guests`: `guest_rights.py` сознательно не даёт `invite` гостям точечно — это «сделало бы гостя соадминистратором»). Только чтение. Голое имя службы в `right` (без `@`) трактуется как «есть хоть какое-то право на службу» (баг 2026-08-06: модель регулярно передаёт «vpn», а не «usage@vpn», фильтр не совпадал ни с чем и выглядел как честное «гостей нет»). Вместо перечня прав — их число: полный перечень (бывает больше десятка) раздувал ответ настолько, что модель при пересказе сама обрезала список гостей и не отмечала обрезку (2026-08-06). Имя — из карточки человека, прочие имена — в «ещё» (находка 2026-10-10: брат владельца числился как «Kein (…, ещё: Андрей Александрович Севбо)», и модель ответила «Андрея Севбо в списке нет» — имя она читает по началу строки).
