# Исполнитель `devlab`

Этап 61.2a (2026-11-01): ядро исполнителя для заданий `test`. Этап 61.2b (2026-11-01): контейнерный
`PodmanTestRunner`. Служба `devlab` (`protocol.EXECUTOR_SERVICE`, runner
`sa_home_bot.devlab.executor.app:run_executor`), назначается на mycraft. Агентский слот — `AgentWorker` (60.5.4, `agent.md`); с `TestWorker` их роднит `WorkerLoops`.

## Устройство
- `executor/app.py` — `run_executor`: конфиг `[devlab]`, `ExecutorHub`, `TestWorker` и `AgentWorker` рядом
  (каждый в своей задаче со своими poll и claim), один общий heartbeat (`beat_forever`), останов по сигналу.
  `build_runner` возвращает `PodmanTestRunner`: чужой код исполняется только в контейнере.
- `executor/worker.py` — `TestWorker`: три фоновых цикла (heartbeat, poll, claim) и обработка задания.
- `executor/hub.py` — `ExecutorHub`: `claim`, `post`, `poll`, `upload_log` поверх `devlab/hubhttp.HubHttp`
  (bearer, базовый URL, heartbeat; тот же базовый класс у `models/hubclient.HubClient` шлюза).
- `executor/mirror.py` — `ProjectMirror`: bare-кэш проекта и работа с git хаба.
- `executor/spec.py` — разбор `.devlab.toml`; `executor/report.py` — сводка из junit и текста pytest.
- `executor/runner.py` — интерфейс `TestRunner` (`run(RunRequest) -> RunResult`, `cancel(job_id)`).
  В тестах — `FakeTestRunner` из `tests/unit/support/fakes.py`.
- `executor/wrapper.py` — общее для контейнерных исполнителей (60.5.3): `WrapperClient` (вызов обёртки через
  `sudo -n -u devlab`, `checked`, `exec` с запасом `EXEC_GRACE_S`, `create`, `remove_container`, `cleanup`,
  отправка дерева `push_tree`), `pack_directory` (с фильтром путей), `extract_files`, `job_name`, `RunnerError`.
- `executor/image.py` — образ по рецепту: `ImageRecipe`, `containerfile`, `image_tag`, `ensure_image` (кэш по
  хэшу, сборка с сетью). Один код для `PodmanTestRunner` и `PodmanSandbox`.
- `executor/podman.py` — `PodmanTestRunner`: контейнерный запуск через обёртку 60.1 (см. ниже).
- `executor/agent_sandbox.py` — `PodmanSandbox`, контейнер задачи агента (`agent.md`).

## Цикл
1. heartbeat каждые `heartbeat_interval_s`: `{busy, jobs}`; `busy` истинно, пока есть текущее задание
   любого работника (слоты и общий heartbeat — ниже).
2. claim с `kinds=["test"]` (слот test; agent не берём), `models=[]`; пусто: пауза `poll_interval_s`.
3. Задание, по порядку:
   1. `git fetch` всех веток хаба в bare-зеркало `<work_dir>/mirrors/<проект>.git` (`+refs/heads/*:refs/hub/*`,
      `--prune`); `ref` — ветка или sha, резолвится в коммит;
   2. `.devlab.toml` читается из этого коммита (`git show`); нет файла — значения по умолчанию;
   3. `git archive` коммита в `<work_dir>/jobs/<id>`;
   4. команда: `cmd` задания, иначе `[test] cmd`; аргументы: `args` задания, иначе `[test] args`
      (задание заменяет, не дополняет); если среди первых трёх слов есть `pytest`, добавляется
      `--junitxml=.devlab-junit.xml`; запуск через `TestRunner` с таймаутом `[test] timeout_s`;
   5. итоги: junit-xml (если есть и в нём есть `testcase`), иначе последняя строка pytest
      (`N passed, M failed, ...`) и строки `FAILED`/`ERROR` короткой сводки; до 50 упавших, выдержка
      до 500 символов; хвост вывода 4 КиБ; таймаут — `exit_code` 124 и метка в начале хвоста;
   6. `PUT /api/log` для `output.log` и `junit.xml`; затем `post test_done`;
   7. ветка `test/*` на хабе удаляется (`git push :refs/heads/<ref>`), только если `ref` начинается с
      `test/`; ветки `base/`, `agent/` и sha не трогаются;
   8. каталог задания удаляется.
4. Любое исключение исполнителя (git, `.devlab.toml`, runner, хаб) — `post failed` с текстом
   (ограничен 1000 символов, токен вырезается); цикл продолжается, ветка `test/*` всё равно
   удаляется.
5. poll: сообщение `stop` по текущему заданию вызывает `runner.cancel(job_id)`; по возвращении `run`
   исполнитель шлёт `stopped` (хаб уже перевёл задание в `stopped`), `test_done` не шлётся.
6. Состояние `<work_dir>/state.json`: `cursor` (poll переживает рестарт, прочитанное не разбирается
   повторно), `current` (задание в работе), `project` и `ref` (для уборки ветки `test/*` осиротевшего
   задания). `current` сбрасывается только после доставки итога на хаб (`test_done`, `stopped` или `failed`).
7. Восстановление (60.9.2). Непустой `current` при старте (и в начале каждого `claim_once`) — задание не
   закрыто на хабе. Если есть `pending_failed` (текст недоставленного `failed`, пишется в `state.json`
   при сбое отправки), шлётся этот `failed`; иначе `requeue`: хаб возвращает test-задание в `queued`
   (не больше `TEST_MAX_REQUEUES` = 2 раз, затем `failed` с причиной «исполнитель перезапускался во время
   прогона N раз»), ветка `test/*` остаётся для повторного прогона. Если хаб отвергает `requeue` (старый
   хаб, чужой статус, HTTP 4xx), шлётся `failed` «исполнитель перезапущен во время прогона» и ветка
   `test/*` (из `state.project`/`state.ref`) удаляется; то же при лимите возвратов (в ответе
   `kind=failed`) и (60.9.9) когда хаб отвергает `failed` (`TransitionRefused`: ответ `{"error", "status"}`, поле `HubRequestError.refused_status`;
   для старого хаба запасной разбор текста «переход <статус> → …») с конечным статусом (`done`/`failed`/`stopped`): задание уже закрыто, ветка лишняя. Сетевая (непостоянная) ошибка: `current` не сбрасывается, новое задание не берётся
   (`claim_once` возвращает False), повтор тем же путём на следующем цикле. Прочий постоянный отказ обоих
   сообщений очищает `current`; ветку `test/*` в этом случае не удаляем (статус задания неизвестен: возможно, `queued`).
   `_post_quietly` возвращает признак успеха: итог `failed` из `handle` считается доставленным
   (`current` сбрасывается, ветка удаляется) только при успешной отправке.
8. Уборка осиротевших копий (60.9.9, `executor/sweep.py`). `run_executor` до запуска циклов берёт
   `AgentWorker.held_jobs` (задание `job` из `agent-state.json` и все запаркованные `parked`: контейнер и копия
   нужны для продолжения) и: удаляет из `<work_dir>/jobs/` и `<work_dir>/agent/` всё, чего нет в наборе (каталоги
   и хвосты `*.tar`); зовёт подкоманду обёртки `sweep <id…>`. `state.current` test-работника не держится:
   его копия пересоздаётся при повторном прогоне после requeue. Если `agent-state.json` нет, а `agent/` непуста,
   `agent/` не чистится (предупреждение в лог); ошибка на одной записи не прерывает остальные. Ошибки уборки
   только в лог (старая обёртка без `sweep` отвечает кодом 2 — исполнитель стартует всё равно).

## Слоты и heartbeat (60.5.7)
- Слот test постоянный: `TestWorker` берёт только `kind=test` и не ждёт агента. Агентские слоты:
  `agent_slots` (по умолчанию 1, максимум 4). Каждый слот — отдельный экземпляр `AgentWorker` со
  своим состоянием (`agent-state.json`, `agent-outbox.json`, каталог задач `agent/`). Слот 0
  использует общий `work_dir` (совместимость с уже лежащими файлами на mycraft), слоты 1.. —
  `work_dir/agent-<i>/`. Каталог создаётся при старте.
- Heartbeat один на службу (хаб хранит запись на имя токена): `busy` истинно, если занят любой
  работник, `jobs` — объединение их текущих заданий (`WorkerLoops.jobs`, `heartbeat_body`).
  Работники запускаются с `heartbeat=False`.
- Состояний два, и они не сливаются: `state.json` (курсор poll и `current` test) и
  `agent-state.json` (курсор, задание, parked, расход агента), плюс `agent-outbox.json`. Курсоры
  независимы: каждый работник читает ящик исполнителя сам и разбирает только свои сообщения.
  Сообщение про задание, которое держит/запарковал ДРУГОЙ слот, игнорируется (фильтр по `parked`
  и `current` в `_on_message`).
- Каталог моделей и клиент шлюза (`ModelCatalog`, `GatewayModels`) создаются в `run_executor`,
  токен у них тот же, что у хаба. Лимиты агента из `[devlab] agent_max_*`; модели в настройках нет.
- Правило одной базы (2026-11-03): общий `SlotRegistry` считает базы заданий, которые сейчас в
  работе у слотов (счётчик, а не множество: продолженное задание может делить базу с идущим).
  `claim` идёт под замком реестра и передаёт хабу `busy_bases`; хаб выбирает только агентские
  задания с другими базами (`queue.claim`, условие `base_branch NOT IN`). Сначала было сделано
  «взять и вернуть в очередь» — второй слот крутил claim → requeue каждые `poll_interval_s`, поэтому
  фильтр перенесён в хаб. Старый хаб поле не знает и игнорирует — тогда правило просто не действует.
  Продолженное после ответа владельца задание (`parked` → resume) берётся локально, без claim, и
  базу только отмечает. База освобождается в `finally` вокруг работы задания.
- Ресурсы контейнера: `agent_cpus / agent_slots`, память — `split_memory` (в мегабайтах, минимум
  2048m; при одном слоте строка конфига без изменений). `cpuset` общий для всех слотов.
- Уборка при старте (`sweep_orphans`) проходит каталоги всех слотов, оставляя задания любого слота.
- Выкат: [deploy.md](deploy.md).

## Слоты по виду моделей (2026-11-18)

Новое поле `[devlab] agent_slot_models` (список строк: `"any"`, `"local"`, `"remote"`, максимум 4 элемента)
позволяет ограничить каждый агентский слот видом моделей, которые он может брать:

- `agent_slot_models = ["local", "remote"]` — два слота: первый работает только с локальными моделями
  (`remote = false` в каталоге), второй — только с удалёнными (`remote = true`).
- Пустой список (по умолчанию) — поведение как раньше: создаётся `agent_slots` слотов вида `any`,
  каждый может брать задание на любой модели.

Число слотов определяется длиной `agent_slot_models` (если непустой) или `agent_slots` (если пустой).
Ресурсы (`agent_cpus`, `agent_memory`) делятся на число слотов. В логе запуска выводится список видов
через запятую: `агентских слотов 2 (local, remote)`.

## Профили ролей (2026-11-18)

Профиль роли в `[devlab.profiles.<имя>]` получает два новых флага для поведения `finish`:

- `allow_no_changes = false` — если `true`, `finish` без правок не отклоняется (тестировщик может принять работу, ничего не дописав); тесты и стражи при этом всё равно гоняются.
- `require_verdict = false` — если `true`, в `summary` у `finish` должна быть строка, начинающаяся с `ВЕРДИКТ: принято` или `ВЕРДИКТ: доработать`; без неё `finish` отклоняется с понятной причиной, агент видит её и исправляется.

По умолчанию оба `false` — поведение как раньше.

С 2026-11-21 есть и `code_mode = false` — инструмент `execute` для роли, см. `docs/devlab/agent.md`,
«Code Mode: скрипт модели».

С 2026-11-21 там же `quick_steps = 0` и `quick_params = {}` — поля запроса к модели на первых `quick_steps`
шагах (например, выключить размышления), см. там же, «Итерация 2».

С 2026-11-22 там же `params = {}` — поля запроса к модели на каждом шаге роли (например, включить
рассуждение бесплатной модели: `{ reasoning = { enabled = true } }`); на первых `quick_steps` шагах
`quick_params` ложатся поверх. Зачем: Nemotron через OpenRouter без явного `reasoning` отвечал без
рассуждений (150–250 ток. на шаг) и шёл мелкими шагами.

## Исчерпанный лимит закрывает слот (2026-11-19)

Шлюз вместе с каталогом моделей шлёт остатки дневного лимита: `limits[<модель>]` с ключами
`LIMIT_RPD_LEFT` и `LIMIT_PROVIDER_LEFT`. Запись каталога считается исчерпанной (`exhausted`),
если любой из этих остатков — целое число (не логическое) и равно 0; отсутствующие значения и
`None` исчерпанием не считаются. `ModelCatalog.names` не предлагает исчерпанные записи, поэтому
исполнитель не берёт задание на модели, у которых все шлюзы исчерпаны: задание ждёт в очереди, а
не падает на HTTP 429. После сброса лимита остаток становится больше нуля и модель снова
предлагается сама. Задание, оборванное лимитом посреди работы, возвращается в очередь
(`MSG_REQUEUE`, Р16.1) — исчерпание закрывает только новые `claim`, не прерывая начатую работу.

## Контейнерный запуск (61.2b)
`PodmanTestRunner.run` вызывает обёртку `sudo -n -u <devlab.user> /usr/local/libexec/sa-home-devlab …`
(`utils/process.run`, тесты подменяют `spawn`). Имя задания в обёртке — id задания в нижнем регистре
(`[a-z0-9-]`, иначе `RunnerError`). Шаги:
1. `sync-in <id>`: каталог задания пакуется в tar (в памяти) и уходит в stdin; обёртка кладёт его в
   `~devlab/work/<id>`.
2. Образ: `image` из `.devlab.toml` (пусто — `[devlab] test_image`) + `setup`/`setup_files`/`env`.
   Тег `devlab/t<24 hex sha256>`; хэш берётся от версии формата, текста Containerfile и sha256 каждого
   `setup_files`. `images` показывает, что образ уже есть: тогда сборка пропускается, иначе
   `build <id> <тег>` (Containerfile со stdin, контекст — копия задания, СЕТЬ ПРИ СБОРКЕ ЕСТЬ, таймаут
   `build_timeout_s`). Containerfile: `FROM`, `WORKDIR /setup`, `ENV`, `COPY` файлов в `/setup/`, по
   `RUN ["sh","-c",<команда>]` на строку `setup` (JSON-кавычки, команда не может выйти за свою
   инструкцию), `WORKDIR /work`. Имя образа и ключи `env` проверяются, `setup_files` — только
   относительные пути внутри кода задания. Ошибка сборки — `RunnerError` с хвостом вывода, задание
   закрывается `failed`.
3. `rm` (на случай хвоста прошлого запуска) и `create <id> <тег> <cpus> <память> <cpuset>`: без сети,
   `--cpus`, `--memory`, `--cpuset-cpus` из `[devlab]` (`test_cpus`, `test_memory`, `test_cpuset`).
4. `exec <id> <ceil(timeout_s)> <shlex.join(argv)>`, вывод stdout+stderr вместе. `timeout` внутри
   контейнера даёт код 124 (это `timed_out`); если обёртка не вернулась за `timeout_s + 30 с`, процесс
   убивается, контейнер удаляется, `timed_out=True`.
5. `sync-out <id> .devlab-junit.xml`: обёртка отдаёт tar одного файла, исполнитель извлекает только
   регулярный файл с этим именем (до 32 МиБ) в каталог задания. Нет файла — не ошибка.
6. `rm` контейнера и `clean` рабочей копии у devlab. После успешного `sync-out` уборка идёт фоновой задачей
   runner-а (`_cleanups`): `run` возвращает результат, не дожидаясь её; следующий `run` того же имени ждёт
   её конца, `aclose()` дожидается всех. При ошибке, таймауте шага и отмене уборка выполняется в `finally`
   под `asyncio.shield`, до возврата.

Порядок: результат -> хаб -> уборка (находка 2026-11-01: pytest закончился за 2 с до рестарта ноды, а
`test_done` ждал `cleanup` ~10 с, и `recover` пометил задание `failed`). В `TestWorker._run_job` выгрузка логов
и `test_done` идут отдельной задачей под `asyncio.shield`; отмена `handle` во время отправки дожидается её,
потом сбрасывает `state.current` и busy и пробрасывает `CancelledError`.

`cancel(job_id)`: помечает прогон отменённым, `rm` контейнера, отменяет текущий шаг и ждёт его конца.
`run` возвращает `exit_code=130`; `sync-out` в этом случае не делается. Отмена самой корутины `run`
(останов службы) пробрасывается, но контейнер всё равно удаляется.

Тег образа в кэше живёт, пока его не снимет `prune`/ручная чистка: автоматической уборки старых
образов нет (открыто). Для sa-home-bot `setup` ставит git и зависимости из `pyproject.toml` с экстрами `dev` и `mcp`
(выкат 2026-11-01: без `mcp` не собираются тесты MCP хаба и инструментов агента)
(`setup_files = ["pyproject.toml"]`), `env.PYTHONPATH=/work/src` вместо установки самого пакета, поэтому
правка кода не пересобирает образ.

## git и токен
Адрес — `<hub_url>/git/<проект>.git`, токен роли `executor`. Заголовок передаётся не аргументами, а
окружением процесса: `GIT_CONFIG_COUNT=1`, `GIT_CONFIG_KEY_0=http.extraHeader`,
`GIT_CONFIG_VALUE_0=Authorization: Bearer <токен>`; в argv токена нет. Окружение процесса видно только
владельцу и root. Ошибки git и хаба перед записью в журнал и в `failed` очищаются от токена. Имя
проекта проверяется (`[A-Za-z0-9][A-Za-z0-9._-]*`), чтобы оно не выходило за каталог зеркал.

## `.devlab.toml`
Файл в корне проекта, читается из коммита задания. Раздел `[test]` (неизвестные ключи — ошибка):

| поле | тип | значение |
|---|---|---|
| `cmd` | строка | команда по умолчанию (разбор `shlex`), например `python -m pytest -q` |
| `args` | список строк | аргументы по умолчанию, если у задания `args` пусты |
| `timeout_s` | число > 0 | таймаут прогона, по умолчанию 1800 |
| `image` | строка | базовый образ; пусто — `[devlab] test_image` |
| `setup` | список строк | команды подготовки окружения (RUN при сборке, сеть есть) |
| `setup_files` | список строк | файлы кода, доступные `setup` в `/setup/` и входящие в ключ кэша образа |
| `env` | таблица | переменные окружения образа (`[test.env]`) |

Верхнеуровневое `project = "<имя>"` — имя проекта на хабе для `nodectl devlab snapshot`
([client-test.md](client-test.md)), исполнитель его не использует.

Раздел `[agent]` исполнитель `test` не читает (разбирается, но не используется; [agent.md](agent.md)), прочие неизвестные разделы игнорируются. В sa-home-bot файл лежит в корне:
`python -m pytest -q -n auto` (pytest-xdist в dev-экстре; исполнитель `-n` сам не добавляет, число воркеров берёт xdist по ядрам cpuset контейнера).

## Признак «занят» и сон mycraft (60.6.1, 2026-11-01)
Пока исполнитель занят, нода не гасит машину по простою (`maybe_auto_poweroff_idle`) и не шлёт
`idle_power_blocked`: владельцу не пишут о том, чего он не просил.

Схема:
1. Исполнитель поднимает локальный ProtoServer (`[devlab].socket`, по умолчанию `./data/devlab.sock`,
   `endpoint_attr="devlab.socket"` в реестре служб) и в `hello`/`describe` отдаёт `ServiceInfo.busy`.
   Поле в payload появляется только при `true`; у старых служб его нет, это «не занят».
2. `PeerLink` ноды к локальной службе читает `busy` из `hello` при подключении и в каждом heartbeat
   (раз в 5 с); при обрыве связи сбрасывает в `false` (мёртвая служба машину не держит).
3. `NodeRouter.busy_services()` перечисляет живые занятые локальные службы; `maybe_auto_poweroff_idle`
   при непустом списке пишет строку в журнал и выходит. Механизм общий: любая служба ноды может
   отдать `busy`, devlab лишь первая. Пока llm спит после естественного простоя, она повторяет
   `llm_went_idle` раз в `WENT_IDLE_REPEAT_S` (600 с), и отложенное выключение пересматривается.
   Находка 2026-11-03: событие было однократным; в 09:14 devlab был занят, выключение отложилось и
   больше не пересматривалось — mycraft простоял включённым весь день. Тихий ручной роспуск
   (`quiet`) повторов не даёт. Пока идёт CPU-задача llm (STT, TTS, картинка), повтора нет, а её
   окончание откладывает следующий на полные 10 минут: озвучка и распознавание не будят gemma и
   не сбрасывают «сон», и без этой защиты повтор мог погасить машину посреди ответа Альфреда
   (требование владельца 2026-11-03). Уведомление `idle_power_blocked` уходит только при смене набора
   блокирующих сессий, иначе повтор раз в 10 минут спамил бы админов.

Исполнитель занят (`devlab/executor/busy.py::BusyTracker`), если верно хоть одно:
- есть задача `running` (test или agent): `started` при взятии, `finished` при `test_done`/`done`/
  `failed`/`stopped`. Трекер один на оба воркера и общий heartbeat: `send_heartbeat` кладёт `queued`
  из ответа хаба в тот же `BusyTracker`;
- хаб сообщает непустую очередь: ответ на heartbeat исполнителя содержит `queued` (число заданий в
  `queued`; расширение 60.6.1, старый хаб без поля даёт 0);
- есть задача в `waiting_owner` и с момента `question` не прошло `[devlab].owner_wait_s` (3600 с);
  `question` ставит только агент (`test` не спрашивает), время вопроса лежит в `agent-state.json`
  (`parked[<id>].asked_at`) и перезапуск службы его не обнуляет; `answer` переводит задачу в
  «выполняется» (в том числе после рестарта), `resume`/`stop`/закрытие парковки снимают удержание;
- `outbox_size()` больше нуля: пока сообщения агента из `agent-outbox.json` не дошли до хаба, машину
  не усыпить (`AgentWorker` присваивает `BusyTracker.outbox_size` при создании; у `test` outbox нет,
  его сообщения уходят сразу или логируются).

`devlab_release` (MCP хаба, сообщение `release` в `poll`) снимает удержание по задаче: исполнитель
вызывает `released` (агент помечает запись `parked` как `released`, чтобы рестарт не вернул удержание). Хаб принимает `release` только для `waiting_owner`, это сообщение не будит mycraft
(`wake.md`). Перед отпусканием клиент проверяет, что всё уже в хабе: push `wip`, сообщения. `answer`
переводит задачу в удержание «выполняется», `resume` и `stop` тоже снимают ожидание. Освободившийся по
`owner_wait_s` исполнитель задачу не теряет: хаб разбудит mycraft ответом (`wake.md`).

## Соседство с ботом на CPU (60.6.2, в проде v0.154.x, вживую не проверено)
Контейнеры тестов и агента уступают живым CPU-задачам бота (распознавание, озвучка, картинки).
Шлюз моделей делает то же для llama.cpp, подробности и цифры стенда в [models.md](models.md).

Вес. Контейнеры запускает пользователь `devlab` через sudo-обёртку и rootless podman, они не попадают
в user-slice пользователя ноды. Под cgroup v2 `--cpu-shares`/`--cpu-weight` у `podman create`
делят CPU только между контейнерами одного `devlab` (соседи по `user@<uid>.service`), с ботом они не
соревнуются: сравниваются вески `user-<uid_devlab>.slice` и `user-<uid_ноды>.slice` (оба под
`user.slice`, по умолчанию 100). Поэтому вес поставлен на слайс пользователя: фикс `devlab-cpu-weight`
кладёт `/etc/systemd/system/user-<uid>.slice.d/50-sa-home-devlab.conf` (`[Slice] CPUWeight=10`) и
делает `daemon-reload`. Флаги `--cpu-shares` у `create` не добавлены: они были бы пустым действием.
Это решение выведено из семантики cgroup v2, на живой машине не проверено (см. «Проверить вживую» в
[deploy.md](deploy.md)). Ночью вес контейнеров не повышается: тесты ночью работают на своих ядрах `6-11,18-23`, а
вес сказывается только при нехватке CPU.

Контроллеры (находка выката 2026-11-01). `--cpuset-cpus` требует контроллер `cpuset` в
`user@<uid>.service/cgroup.controllers`, а systemd отдаёт менеджеру пользователя по умолчанию лишь
`cpu memory pids`. Фикс `devlab-delegate` кладёт drop-in `user@<uid>.service.d/50-sa-home-devlab-delegate.conf`
(`Delegate=cpu cpuset io memory pids`) и перезапускает `user@<uid>.service` (рестарт убивает
запущенные контейнеры `devlab`). `check()` сверяет текст drop-in и наличие `cpuset` в
`cgroup.controllers` менеджера. Дочерние cgroup под `user@<uid>` (в том числе `libpod-*.scope`,
которые создаёт rootless podman внутри менеджера) получают `cpuset` через `cgroup.subtree_control`:
при `Delegate=` systemd сам включает делегированные контроллеры на промежуточных уровнях, руками
писать в `subtree_control` не нужно. Это вывод из документации systemd, вживую не проверено.

Ядра. Контейнеры тестов `test_cpuset = "6-11,18-23"`, агента `agent_cpuset = "6-11"` (как и раньше);
дневные ядра шлюза `0-5,12-17` с ними не пересекаются.

Пауза. `run_executor` создаёт `devlab/neighbor.py::NeighborGate` и подписывается на события `llm`
(`[devlab].neighbor_socket`, по умолчанию `[llm].socket`; нет сокета, цикл молча повторяет раз в 5 с).
Первое `llm_cpu_task_started` вызывает `WrapperClient.pause()`: подкоманда обёртки `pause` без имени
ставит на паузу все запущенные контейнеры `devlab-*` (`podman pause`), последнее
`llm_cpu_task_finished` вызывает `unpause`. Вложенность, `freeze_max_s` (300 с, `[devlab]`) и
обрыв связи работают как у шлюза. Подробности и поведение при потере событий в models.md.

Тонкости паузы контейнеров:
- `podman exec` в приостановленный контейнер не работает, поэтому `exec`, `start`, `stop` и
  `interrupt` ждут разморозки (`NeighborGate.wait_thawed`), а контейнер, созданный в заморозку,
  сразу ставится на паузу.
- Таймаут команды считается без времени заморозки. Внутриконтейнерный `timeout` считает по стенным
  часам и счётчик паузы не знает, поэтому теперь он только страховка (`exec_backstop`: лимит ×2 + 30 с),
  а срок следит `WrapperClient.exec` на хосте: `потрачено = стена − (frozen_total сейчас − frozen_total на старте)`.
  Когда срок вышел, подкоманда `interrupt` шлёт `TERM`, через 2 с `KILL` всем процессам контейнера
  (кроме PID 1), `exec` завершается, а вывод сохраняется. Результат: `exit_code 124`, `timed_out`.
  Прежний путь «убили контейнер, вывода нет» остаётся для случая, когда `interrupt` не помог за
  `EXEC_GRACE_S`.
- Не вычитается: `agent_max_wall_s` (потолок всей задачи агента, 8 ч), `build_timeout_s` и
  `SYNC_TIMEOUT_S` (сборка и синхронизация не внутри контейнера, не замораживаются).

Подкоманды обёртки (`/usr/local/libexec/sa-home-devlab`, ставит `nodectl fix`):
- `pause [имя]` и `unpause [имя]`: имя проверяется как у остальных (`[a-z0-9-]`), без имени
  выбираются `podman ps --filter name=devlab- --filter status=running|paused`, пустой список не ошибка;
- `sweep [имя…]` (60.9.9): имена проверяются как у остальных, до любых действий; список контейнеров берётся
  до первого `rm` (сбой `podman ps` — код 2, ничего не удалено); удаляет контейнеры
  `devlab-*` и записи `$HOME/work/<имя>` и `<имя>.containerfile`, имён которых нет среди аргументов, затем
  `podman image prune --force` (висячие образы после оборванной сборки; кэш `devlab/t<хэш>` не трогается).
  Права те же, что у остальных подкоманд (пользователь `devlab`, `sudo -n`, без новых путей);
- `interrupt имя`: `podman exec devlab-<имя> sh -c 'kill -TERM -1; sleep 2; kill -KILL -1'`.

## Тишина видеокарты (2026-11-18)
Каждый heartbeat (`send_heartbeat`) возвращает полный ответ хаба целиком, а не только счётчик
`queued`; в ответе есть поле `silence` (`{"until": ISO | null}`, `protocol.FIELD_SILENCE`). Если в
конфиге задан `switch_url` (адрес strata-switch), `run_executor` создаёт `SilenceRelay`
(`executor/silence_relay.py`) и `beat_forever` после heartbeat пересылает значение `silence` в
`POST /v1/silence` телом `{"silence": <то же значение>}`: strata-switch после перезапуска получает
тишину заново. Сессия создаётся лениво при первом `push` и закрывается в `close` рядом с
`gateways.close()` при останове. Сбой (HTTP не 200, `aiohttp.ClientError`, таймаут) не поднимается,
предупреждение в лог только при первой неудаче подряд; при успехе и изменении значения —
`info`. Ответ без `silence` (старый хаб) не пересылается. `switch_url` пустой — пересылки нет.
Спрос на локальную модель (2026-11-18): хаб в том же ответе heartbeat отдаёт `local_demand`
(`protocol.FIELD_LOCAL_DEMAND`, `False` при активной тишине) — есть ли задание в `STATUS_QUEUED` или
`STATUS_RUNNING` на модель каталога без `MODEL_REMOTE`; `SilenceRelay.push` пересылает его тем же
запросом в `main_demand` (`strata_switch.MAIN_DEMAND_FIELD`), лог при смене пары (тишина, спрос).

### Тишина: вторая линия защиты (2026-11-23)

Случай 2026-11-23: тишина дошла до strata-switch мгновенно, но идущий запрос GLM доработал до конца
(~5 минут). Теперь кроме обрыва в strata-switch исполнитель сам обрывает свои запросы к локальным
моделям. `SilenceWatch` (`executor/routing.py`) получает признак тишины из heartbeat (`beat_forever`),
при тишине отменяет задачи запросов `FailoverChat` к записям каталога с `remote = False`
(`guard`); отмена превращается в `ModelError(silence=True, transient=True)`: агент ждёт
`SILENCE_WAIT_S` и повторяет шаг, раунд не тратится. Разрыв соединения с локальной моделью при
действующей тишине тоже считается тишиной, а не отказом шлюза. Удалённые модели не затрагиваются.
Отмену самого задания (`Task.cancelling()`) `guard` не перехватывает. При выкате нужен рестарт
ноды mycraft (`restart_node`: исполнитель живёт в службе `devlab` внутри `sa-home-node.service`) и
пользовательского юнита `strata-switch.service`.

## Режим парковки исполнителя (2026-11-26)

Режим парковки — флаг на процесс исполнителя, означающий «не брать новых заданий, но доделать
начатое». `run_executor` создаёт один `ParkMode` на процесс (`executor/park.py`) и передаёт его в
настройки обоих работников (`WorkerSettings.park`, наследуется в `AgentSettings.park`) и в
`BusyTracker` (`park=`): один объект на процесс. При активном флаге работники не берут новые задания
из очереди хаба (обе `claim_once` возвращают False и не делают запрос к хабу), а задания, начатые до
включения, и исходящие сообщения агента (`agent-outbox.json`) продолжают обрабатываться и досылаться.

`busy` при активном режиме парковки считает занятость иначе (`BusyTracker.busy`, `executor/busy.py`):
очередь хаба (`queued`) и удержание по владельцу (`waiting_owner`) больше не входят в `busy`; входят
только задачи в работе (`running`) и исходящие сообщения (`outbox_size > 0`). Пока режим активен,
исполнитель свободен при непустой очереди хаба — нода может уснуть, но не усыпается, пока агент
досылает сообщения или работает начатое задание. Флаг в False (`set_parked(False)`, действие `unpark`
службы) возвращает прежнюю семантику: очередь хаба и удержание владельца снова считаются занятостью.

## Жизнь запаркованного задания агента (2026-11-27)

Запланированная остановка (`Crane.PARK`) возникает, когда агент дойдёт до лимита шагов/времени/токенов
и пул лимитов не пуст — исполнитель даёт ему «ещё один отрезок» после парковки. В отличие от
обычного крана (`COST`, `TOKENS`, `STEPS`, `WALL`), который шлёт на хаб `question` (задача получает
статус `waiting_owner` и ждёт ответа владельца), кран `PARK` обрабатывается локально:

1. **Парковка (первый проход).** Агент доходит до крана `PARK` → `AgentLoop.run` возвращает
   `AgentResult(status=ASKED, crane=PARK, dialog=Dialog(parked=True))`. `_conclude` вызывает
   `_park_for_restart` (не `_park`):
   - диалог сохраняется в `<work_dir>/agent/<job_id>/dialog.json` с `parked=true`, `answer=null`;
   - песочница останавливается (`sandbox.stop()`), контейнер сохраняется в `_parked_sandboxes`;
   - wip-ветка фиксируется пустой вехой `milestone("парковка перед рестартом")` — коммит создаётся
     даже без правок, чтобы на хабе осталась история;
   - запись в `agent-state.json`:
     ```json
     { "parked": { "<job_id>": { "job": {...}, "answered": true, "parked_for_restart": true } } }
     ```
     `answered=true` + `parked_for_restart=true` — маркер «это парковка, не вопрос владельцу»;
   - `BusyTracker.finished(job_id)` — задача уходит из «работает», не входит в `holding_for_owner()`;
   - **хаб не получает `MSG_QUESTION`** — с точки зрения хаба задача всё ещё `running` (нет перехода
     в `waiting_owner`), очередь хаба не знает о парковке.

2. **Хранение.** Задание лежит в `agent-state.json` (в `parked`), контейнер в памяти исполнителя,
   каталог `<work_dir>/agent/<job_id>/` с диалогом и wip-веткой на хабе. Перезапуск исполнителя
   не теряет такие задания: при старте `AgentWorker` восстанавливает их из `agent-state.json`
   (`parked_for_restart=true` не вызывает `busy.started`, задача не считается активной).

3. **Возобновление (после рестарта или просто следующего цикла).** `claim_once` видит запись с
   `parked_for_restart=true` (или `answered=true` без этого флага — для совместимости) и берёт её
   **до** запроса новых заданий у хаба. `handle` с `resumed=true`:
   - поднимает сохранённый контейнер (`sandbox.resume()`);
   - открывает репозиторий с wip-веткой (в ней уже есть коммиты до парковки);
   - вызывает `AgentLoop.run(system, task, resume=dialog)` — `Dialog.resumed_messages()` возвращает
     исходные сообщения без добавления «ответ владельца: …» (поле `parked=true` подавляет префикс);
   - агент продолжает работу с тем же контекстом.

4. **Завершение.** Агент доходит до `finish` → `_conclude` с `status=FINISHED`:
   - `repo.finish(summary)` создаёт `agent/<job_id>` ветку (даже если новых правок на этом отрезке
     нет — коммит парковки делает `HEAD` отличным от `base`);
   - `MSG_DONE` уходит на хаб с полным `take_report()` (токены обоих отрезков суммируются);
   - wip-ветка удаляется, контейнер и каталог задания удаляются, запись из `parked` удаляется.

**Отличия от вопроса владельцу (`Crane.COST` и др.):**
- Нет `MSG_QUESTION` на хабе — хаб не переводит задачу в `waiting_owner`.
- Нет удержания в `BusyTracker.holding_for_owner()` — `busy` не считает задачу занятой во время парковки.
- После рестарта такие задания поднимаются **перед** новыми `claim` из очереди хаба.
- Диалог при resume не получает префикс `ANSWER_PREFIX` («ответ владельца: …»), модель видит
  историю как сплошной диалог.

**Обычный кран (вопрос владельцу) для сравнения:** `_park` шлёт `MSG_QUESTION`, `busy.waiting_owner`,
в `parked` запись с `answered=false`, задача в `waiting_owner` до ответа/релиз/рестарт; после ответа
`_accept_answer` ставит `answered=true`, `busy.started`, задача продолжается как обычно. Рестарт
поднимает только `answered=true` (ответ уже есть), `parked_for_restart` не используется.
