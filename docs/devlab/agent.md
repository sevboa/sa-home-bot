# Агент-разработчик `devlab`

Этап 60, задача 60.5. Модель + обвязка, которые выполняют задание вида `agent`. Код: `devlab/agent/`.
60.5.1 (сделано) — цикл агента; 60.5.2 (сделано) — ветки агента, раздел «Git агента» ниже; он ничего не знает ни о хабе, ни о git, ни о Podman. Остальное
(ветки, контейнер, работник, вопросы владельцу, расход, слоты) — 60.5.2–60.5.7, см.
`IMPLEMENTATION_PLAN.md`.

## Состав
- `model.py` — `ChatModel` (`complete(messages, tools) -> ModelReply`) и `GatewayChat`:
  `POST <base_url>/v1/chat/completions` к шлюзу `devlab_models` без stream, с
  `Authorization: Bearer <токен исполнителя>` и `X-Devlab-Job: <id задания>` (по нему шлюз пишет
  расход). В теле запроса поле `user` — `devlab <id задания>`: по нему маршрутизатор Strata
  подписывает, кто держит модель (см. `docs/platform-llm/strata-switch.md`, раздел «Состояние»).
  Токены `usage` возвращаются в `ModelReply`. Таймаут запроса `MODEL_TIMEOUT_S` = 30 мин
  (стенд 60.2: на CPU один запрос с большим окном идёт десятки минут). Любая беда транспорта и
  разбора — `ModelError`; тело ошибки шлюза (`{"error": ...}`) приводится к тексту.
- `sandbox.py` — интерфейс `Sandbox`: `read_bytes`, `write_bytes`, `list_files`,
  `exec(argv, timeout_s)`, `changed_paths()` (изменения относительно базы). Пути относительные,
  выход за корень — `SandboxPathError`. `LocalSandbox` на каталоге (тесты и отладка); контейнерная
  реализация — `PodmanSandbox` (60.5.3, ниже). `ExecResult.summary` режет вывод до конца (ошибки в конце) и помечает таймаут.
- `spec.py` — `AgentSpec`: команда тестов, `checks`, `allowed_commands`, `forbidden_paths`,
  `secret_paths`, `diff_prefixes`, таймауты, лимит вывода. Собирается `AgentSpec.from_project(ProjectSpec)`
  из `.devlab.toml`: `test_argv` и `test_timeout_s` берутся из `[test]` (`cmd`+`args`, `timeout_s`), остальное из `[agent]`.
- `tools.py` — `ToolBox` и схемы: `list_files`, `read_file` (по строкам, ≤200 за вызов), `grep`,
  `edit_file` (один фрагмент, ровно одно вхождение), `write_file` (оба дописывают `\n` в конец
  непустого текстового файла без него и говорят об этом в результате; бинарные и пустые не трогают),
  `run_command` (только разрешённые префиксы, без оболочки), `run_tests` (обязательный `paths` —
  пути через пробел, каждый через `safe_relative`, команда = `test_argv` + пути, узкий прогон;
  без `paths` — `ToolError`, полный набор гоняет страж `finish`; `step_done` гоняет только изменённые тестовые файлы), `finish`. Отказ стража начинается со строки «исправь и
  вызови finish/step_done снова; полный вывод стража ниже». Системное сообщение советует узкие тесты
  через `paths`, полный набор проверит `finish`. Ошибка инструмента — `ToolError`,
  текст уходит модели. `forbidden_paths` закрывает запись, `secret_paths` — запись и чтение (glob или префикс-каталог с `/`, один матчер `agent/paths.py`).
- `context.py` — окно. Оценка `len(json)/3` токенов; размер диалога считается один раз, дальше ведётся по изменённым сообщениям (без квадратичного пересчёта).
  - Бюджет: `context_tokens - reply_tokens - схемы инструментов`. Перед каждым запросом, если диалог не влезает, свёртка идёт ступенями. Ступени 0–3 сворачивают старое с запасом, до `FOLD_TARGET_SHARE` (60%) бюджета, чтобы следующие шаги только дописывали хвост (см. «Стабильный префикс ради кэша промпта»); ступени 4–5 и обрезка последней единицы работают только до границы бюджета:
    0. размышления (`reasoning_content`) старых ответов ассистента удаляются;
    1. старые выводы инструментов (кроме `keep_recent` последних) -> `[вывод свёрнут: N симв.]`;
    2. длинные аргументы старых вызовов (`write_file`) -> JSON аргументов разбирается, короткие поля (`path` и т.п.) остаются, строки длиннее 300 симв. заменяются на первые 200 симв. + `… [обрезано N симв.]` (не-JSON: `{"обрезано": "<начало>…", "симв.": N}`), результат всегда валидный JSON;
    3. текст старых ответов ассистента длиннее `FOLD_ARGUMENTS_MIN_CHARS` -> `[ответ свёрнут: N симв.]`;
    4. выводы инструментов и ответы владельца (`ANSWER_PREFIX`) длиннее `RECENT_OUTPUT_CHARS` (2000) обрезаются до начала и конца с пометкой `[…обрезано N симв.…]`;
    5. самые старые единицы выбрасываются пачкой. Единица — ассистент с `tool_calls` вместе со всеми его `tool`-ответами либо одиночное сообщение; пары не рвутся, висящих `tool_call_id` не бывает. Ответы владельца (`user` с `ANSWER_PREFIX`) не выбрасываются, только сжимаются.
  - Маркер выброшенного: в конец задания (`messages[1]`) дописывается `\n\n[свёрнуто N шагов]`, счётчик копится по регулярке с якорем в конце; отдельных `user`-сообщений нет. `Dialog` текст задания не сравнивает; `pinned_report` считает задание без маркера.
  - Гарантия про последнюю единицу: она не выбрасывается никогда. Если после выбрасывания диалог всё ещё не влезает, у неё сперва удаляются размышления, затем её аргументы (так же, по полям) и текст обрезаются до `RECENT_OUTPUT_CHARS` по одной обрезке, пока не влезет; не влезло и так — `CONTEXT_OVERFLOW` (не работать вслепую).
  - Системное сообщение и задание не сворачиваются. `CONTEXT_OVERFLOW` называет размеры системного сообщения и задания (симв. и ток.), схем инструментов, бюджет диалога и окно, советует сократить `[agent] rules` или `task.md`; `AgentWorker` дописывает список файлов правил с размерами (`overflow_hint`; размер каждого файла пишется и в лог). Такое задание падает до первого запроса к модели.
  - Окно берётся из каталога моделей (`CatalogEntry.context`, поле `context` heartbeat): у внешней модели (`remote`) это `context` целиком, у локальной — `min(context, agent_context_tokens)` (замер 60.2: больше 16k Flint на CPU деградирует), у записи без `context` — `agent_context_tokens` (по умолчанию 16000). Если у модели несколько шлюзов, берётся минимум по записям (при failover окно не должно оказаться больше, чем у запасного шлюза). Из `context` каталога берётся 90% (`CATALOG_WINDOW_SHARE`): оценка токенов идёт по символам (`len(json)/3`) и на кириллице может недосчитать. Мусорный или отрицательный `context` в каталоге считается отсутствующим. Окно пересчитывается на каждый сегмент задания (старт, resume, рестарт исполнителя). Окно 64k увеличивает токены на запрос (`agent_max_tokens`, расход бесплатной модели), но не число запросов. Резерв `reply_tokens` вычитается из окна в `AgentLoop` как раньше.
- Потолок токенов и бесплатные модели (2026-11-19): у моделей, у которых все записи каталога бесплатные и удалённые (`free` и `remote` у каждой), потолок токенов задания (`agent_max_tokens`) не применяется — `token_ceiling(entries, limits.max_tokens) * factor` в `_limits_for` даёт 0, а `max_tokens == 0` в `_crane` означает выключенный потолок. Почему так: бесплатный лимит OpenRouter считает запросы, а не токены; при большом окне (256k) потолок токенов обрывал задание через десяток запросов. Запросы вместо этого ограничивают `max_steps` на сегмент и лимиты шлюза (`rpd`/`rpm`). Для GLM, локальных и платных моделей потолок прежний.
- `guard.py` — `FinishGuard.verify()`: непустой дифф (в путях `diff_prefixes`, если заданы), затем
  тесты и каждый `check` в песочнице. Возвращает список причин отказа.
- `loop.py` — `AgentLoop.run(system, task) -> AgentResult`.

## Поведение цикла
- Закончить можно только вызовом `finish(summary)`; страж отклоняет без диффа и при красных
  тестах/стражах, текст отказа возвращается модели как результат инструмента, цикл продолжается.
- Ответ без вызова инструмента (в том числе «готово» текстом) не засчитывается: модели
  напоминают, после `max_idle_replies` подряд — `STUCK`.
- Ошибка инструмента (в том числе неожиданное исключение и невалидный JSON аргументов) не роняет
  цикл: модель получает `ошибка: ...`. `CancelledError` не глотается.
- `ModelError` завершает цикл `MODEL_FAILED` с причиной; повтор и смена модели решает вызывающий
  (60.5.4–60.5.6). Токены считаются по всем ответам, в `AgentResult`.
- Исходы: `FINISHED`, `ASKED`, `MODEL_FAILED`, `CONTEXT_OVERFLOW`, `STUCK`.
- `on_change(описание)` — async-колбэк после `edit_file`, `write_file`, `run_command`; в 60.5.2 по нему
  делается коммит (репозиторий сам решает, чистое ли дерево).

## Шлюз
Исполнитель ходит в шлюз тем же токеном `executor`, что и в хаб (шлюз проверяет его через
introspect). Код выбора — `executor/routing.py` (60.5.6).
- Решение владельца 2026-11-01: одна модель (один ключ OpenRouter) стоит на шлюзах jeeves и wooster;
  jeeves может умереть, служба может переехать на американский сервер. Локальная модель (llamacpp на
  mycraft) — свой шлюз, единственный.
- `ModelCatalog` читает `POST /api/catalog` хаба (записи с `url`, только свежие heartbeat), держит
  кэш `CATALOG_TTL_S` = 15 с; хаб недоступен — берётся прошлый кэш, а без кэша ошибка.
  `CatalogEntry`: `name`, `gateway`, `url`, `free`, `price_in`, `price_out`, `remote`.
- `FailoverChat` (`GatewayModels` строит его на задание): перебирает шлюзы модели, предпочитая тот,
  что ответил в прошлый раз. Транспортная ошибка, HTTP 5xx и 429 (`ModelError.transient`) — следующий
  шлюз с теми же `messages`, то есть диалог не теряется (он живёт у исполнителя, а не у шлюза).
  4xx (кроме 429) и таймаут запроса не переключают. Обошли все — пауза `ROUTE_RETRY_S` и новый круг с
  обновлённым каталогом, всего `ROUTE_ROUNDS` = 6, затем `ModelError` («все шлюзы ... отказали»).
- Повторы при временной ошибке (2026-11-18): 6 раундов, пауза 5→10→20→40→60 с.
- Тишина видеокарты (2026-11-18): шлюз `strata-switch` отвечает 503 с телом `{"error": "тишина видеокарты до …", "code": "gpu_silence"}`. `GatewayChat` помечает такую ошибку `ModelError(silence=True, transient=True)`. `FailoverChat` пробует остальные шлюзы раунда; если ответа нет и хотя бы один ответил тишиной, раунд не тратится: пауза `SILENCE_WAIT_S` (60 с) и тот же раунд заново. Задание остаётся `running` сколько угодно долго, в том числе в бессрочной тишине. Ревью 2026-11-18: первая версия агента после трёх тишин переходила дальше и тратила раунды, в часовой тишине задание падало бы через ~18 мин.
- Цена ответа (`price_reply`): фактическая `usage.cost` провайдера, иначе токены * цена шлюза из каталога;
  у `free` цена 0. `free` и `usage.cost > 0` — `ModelReply.paid_free`.

## Git агента (60.5.2)
`repo.py`, `AgentRepo` поверх `ProjectMirror` (общий `GitRunner` из `executor/mirror.py`: токен
только в окружении `GIT_CONFIG_*`, из ошибок вырезается). Ветки: `base/<id>` (снимок клиента) →
`wip/<id>` (ход работы) → `agent/<id>` (итог). Репозиторий рабочей копии лежит отдельно от неё
(`git_dir` рядом с `workdir`), так что в каталог, который уйдёт в контейнер, `.git` не попадает.
- `open()`: fetch зеркала; если `wip/<id>` на хабе есть, рабочая копия встаёт на его вершину,
  иначе на `base/<id>`. Если локальная копия уже впереди вершины хаба (не успели запушить до
  рестарта), она сохраняется, а не затирается; хвост уйдёт следующим push.
- `on_change(описание)` подключается к `AgentLoop`: `git add -A`, пустые изменения не коммитятся,
  тема коммита — описание действия. Автор настраивается: `CommitAuthor`, по умолчанию
  `agent_author(модель)` = `devlab-agent (<модель>)`.
- Склейка push: не чаще раза в `push_interval_s` (30 с). Первое изменение уходит сразу, дальнейшие
  копятся и уходят таймером, который выставляется на остаток интервала; неудавшийся push не
  роняет цикл (лог, повтор по таймеру/`flush()`). `milestone(название)` (для `step_done`) и
  `finish`/`abandon` пушат всегда и с ошибкой, если не вышло.
- `milestone`: коммит `веха: <название>` (допускается пустой: веха фиксирует шаг даже без правок).
- `finish(резюме)`: докоммитить хвост, push `wip`, squash одним коммитом на `base/<id>` с деревом
  `wip` (сообщение: резюме, id задания, автор, список вех), push `+agent/<id>`, удаление
  `wip/<id>` на хабе и локального репозитория. Каталог `workdir` не трогается.
- `abandon(причина)` для `failed`/`stopped`: то же, но сообщение `не завершено: <причина>`; если
  правок относительно базы нет, `agent/<id>` не создаётся. Клиенту остаётся видимым `agent/<id>`
  с частичным результатом (если он есть); `wip/<id>` не остаётся никогда.
- Права: пушатся только `wip/<id>` (создать/обновить/удалить) и `agent/<id>` (создать/обновить),
  всё в рамках `refpolicy` для роли `executor`.
- Тесты: `tests/unit/test_devlab_agent_repo.py` (настоящие git и хаб).

## Контейнер задачи (60.5.3)
`devlab/executor/agent_sandbox.py`, `PodmanSandbox` — реализация `Sandbox` в долгоживущем контейнере.
Общее с `PodmanTestRunner` (вызов обёртки, образ и его кэш) вынесено в `executor/wrapper.py` и `executor/image.py`.

### Где источник истины
Рабочая копия на хосте исполнителя (`AgentRepo.workdir`). Почему:
- репозиторий агента смотрит именно в этот каталог, `on_change` видит правки без дополнительной синхронизации;
  `read_bytes`/`write_bytes`/`list_files`/`changed_paths` — это `LocalSandbox` на нём (быстро, без вызовов обёртки на чтение);
- контейнер можно остановить или потерять (рестарт хоста, `podman rm`), рабочая копия при этом цела;
  `waiting_owner` не зависит от жизни контейнера.
- Копия в контейнере (`~devlab/work/<id>`, bind-mount в `/work`) — зеркало. Если с прошлой синхронизации был
  `write_bytes` (флаг `_stale`), перед командой дерево отправляется `refresh` (содержимое заменяется, каталог остаётся
  тем же inode). После КАЖДОЙ команды `sync-out` забирает всё дерево, расхождения применяются на хосте: изменённые и
  новые файлы пишутся, исчезнувшие удаляются. Так форматтер в контейнере попадает в рабочую копию, а `ToolBox` после
  `run_command` зовёт `on_change`.
- Не отправляются в контейнер и не возвращаются: кэши (`IGNORED_DIRS`), `.devlab-junit.xml`, `secret_paths`.

### Правила путей
- `secret_paths` (`.env`, `config.toml`): не уходят в контейнер (команда агента не может `cat .env`), не видны в
  `list_files`/`grep`, чтение и запись — `SandboxPathError`, из контейнера не возвращаются.
- `forbidden_paths`: чтение можно, `write_bytes` отказывает. Если команда в контейнере всё же изменила такой файл, на
  хост это НЕ переносится, а следующая команда начинается с `refresh` и откатывает контейнер к хостовой копии.
- Два списка нужны потому, что `forbidden_paths` в 60.5.1 означает «закрыто для правок» (агент должен читать `tests/`).

### Жизненный цикл
- `start()`: `sync-in` (без секретов) → `ensure_image` (рецепт `[test]`: `image`, `setup`, `setup_files`, `env`; кэш по
  хэшу, сборка с сетью) → `rm` хвоста и `create <id> <тег> <cpus> <память> <cpuset>` (без сети, квоты агента).
- `exec(argv, timeout_s)`: под замком (команды по одной), `timeout` внутри контейнера (код 124 → `timed_out`), внешний
  запас `EXEC_GRACE_S`. После таймаута контейнер удаляется (мог зависнуть процесс), `_lost`; следующая команда создаёт его
  заново из того же образа и делает `refresh`. Образ не пересобирается.
- `stop()` (для `waiting_owner`): `podman stop`; хостовая копия и `~devlab/work/<id>` остаются. `exec` на остановленном — `RunnerError`.
- `resume()`: `start`; если не вышло, полный `sync-in` + образ + `create` заново. Перед первой командой всегда `refresh`.
- `aclose()`: `rm` контейнера и `clean` копии у `devlab` под `asyncio.shield`. Хостовая рабочая копия не трогается.
- Ресурсы агента: `[devlab] agent_cpus/agent_memory/agent_cpuset` (конфиг владельца исполнителя, не проекта: проект не
  выбирает, сколько ядер ему дать). Квоты диска нет: на bind-mount у rootless podman её нет (открыто).
- `baseline` (необязательный) — хэши исходного дерева для `changed_paths`; после рестарта работник 60.5.4 передаёт
  `LocalSandbox(<checkout base/<id>>).snapshot()`, иначе правки до рестарта пропадут для `FinishGuard`.

### `[agent]` в `.devlab.toml`
`rules` (файлы правил в системный промпт; читает работник 60.5.4), `checks` (команды-стражи строками), `allowed_commands`
(префиксы для `run_command`), `forbidden_paths`, `secret_paths`, `diff_prefixes`, `allow_remote_models` (по умолчанию
`false`; применит 60.5.6), `command_timeout_s`, `narrow_test_timeout_s` (по умолчанию 300), `output_chars`. Неизвестный ключ в `[agent]` — `SpecError` (опечатка не
должна молча снимать защиту). Команда тестов и её таймаут — из `[test]`. sa-home-bot: rules = CLAUDE.md, checks =

## Работник агента (60.5.4)
`devlab/executor/agent_worker.py`, `AgentWorker` — связывает цикл, репозиторий и контейнер. Общие три фоновых цикла
(heartbeat, poll, claim) вынесены в `WorkerLoops` (`executor/worker.py`), от него наследуются `TestWorker` и `AgentWorker`.
- Вход: `ExecutorHub`, `ModelFactory` (`(модель, id задания) -> ChatModel`; боевая — `GatewayModels(catalog, token)`
  с общей сессией), `SandboxFactory` (боевая — `podman_sandbox_factory(cfg)`, в тестах `LocalSandbox`) и `AgentSettings`
  (`WorkerSettings` + `limits`, `push_interval_s`, `retry_interval_s`) и `Catalog` (60.5.6: список моделей для `claim`, проверка
  модели; выбор и переключение шлюзов — раздел «Шлюз»). `ExecutorHub.claim(kinds, models)` теперь принимает модели.
- Задание: `claim` вида `agent` → `post started` → в каталоге `<work_dir>/agent/<id>/` свой зеркальный bare-репозиторий,
  `work/` (рабочая копия), `git/` (репозиторий агента), `base/` (временный экспорт базы) → `AgentRepo.open()`
  (база — `job.base_branch`, не обязательно `base/<id>`; для этого у `AgentRepo` появился параметр `base_branch`) →
  `.devlab.toml` и файлы `[agent] rules` читаются из коммита базы → `baseline` = снимок экспорта базы (одинаков для
  первого запуска и для продолжения) → `sandbox.start()` → `AgentLoop` с `on_change=repo.on_change`.
- Промпт (`agent/prompt.py`): системное сообщение — вводная и файлы `rules`; task.md — первое пользовательское сообщение.
  При продолжении к task.md дописывается список файлов, уже изменённых относительно базы.
- `ManagedSandbox` (`agent/sandbox.py`) — `Sandbox` плюс `start/stop/resume/aclose`; у `LocalSandbox` это пустышки.
- Исходы: `FINISHED` → `repo.finish` (повтор без предела: результат нельзя потерять) → `done` (резюме, токены, модель);
  `MODEL_FAILED`/`CONTEXT_OVERFLOW`/`STUCK` и исключения → `repo.abandon` (3 попытки) → `failed` с причиной;
  `stop` из `poll` отменяет задачу цикла → `abandon` → `stopped` (`agent/<id>` остаётся с частичным результатом,
  `wip/<id>` нет). Каталог задания удаляется после закрытия.
- Журнал шагов (60.9.6): `agent/trace.py::StepTrace` пишет `<job root>/steps.jsonl` — строка JSON на событие:
  `{"event": "start", "resumed"}` в начале каждого отрезка, по строке на ответ модели (`step`, `t`, `model_s` — время запроса к модели, `tokens_in/out`,
  `cost_usd`, `window` — оценка окна в токенах после свёртки, `folded` — свёртка сработала, `text` — первые 300 симв.
  ответа без вызовов, `skipped` — число вызовов, пропущенных после `ask_owner` (0, если вопроса не было), `calls`: `name`, `args` — аргументы, длинные значения обрезаны через `context.shrink_arguments`,
  `result` — первые 300 симв. итога и `result_chars`, `rejected` — `finish`/`step_done` отклонён стражем) и
  `{"event": "end", "status", "reason", "crane", "steps"}` (исход, стоп-кран, сбой модели, переполнение окна).
  Файл ограничен `protocol.STEPS_MAX_BYTES` (256 КиБ): при переполнении остаётся хвост до половины предела по границе
  строки. Если одна запись длиннее половины предела и хвост пуст, остаётся эта запись в сокращённом виде:
  `calls` заменены счётчиком `calls_dropped`, строковые поля обрезаны, файл остаётся валидным JSONL. Строки проходят `scrub` работника (токены не пишутся). Выгружается на хаб (`PUT /api/log`, имя
  `steps.jsonl`) при `question`, `done`, `failed`, `stopped` до удаления каталога и при остановке парковки; сбой
  выгрузки — `warning`, исход не меняется. Переживает парковку и рестарт (файл дописывается), на новом задании
  стирается вместе с каталогом.
- Остановка службы (отмена): под `shield` `repo.flush()`, затем `repo.aclose()` и `sandbox.aclose()`; состояние остаётся.
- Состояние `<work_dir>/agent-state.json`: `cursor` и `job` (задание целиком). На старте непустой `job` значит, что задание
  всё ещё `running` на хабе: первым в claim-цикле берётся оно же (без нового `claim` и без второго `started`), рабочая
  копия поднимается с вершины `wip/<id>` (или локальной, если она впереди).
- Исходящий outbox `<work_dir>/agent-outbox.json`: каждое сообщение хабу (`started`, `done`, `failed`, `stopped`) сначала
  дописывается на диск, потом уходит; недоступность хаба и 5xx оставляют его в очереди (порядок сохраняется, повтор
  каждый `poll_interval_s` и на старте), 4xx (`HubRequestError.permanent`) — сообщение отвергнуто, логируется и снимается.
  Задание считается закрытым локально, как только терминальное сообщение записано в outbox.
- Учёт расхода — раздел «Расход» ниже. `poll` у `TestWorker` и `AgentWorker` идут
  раздельно (общая служба — 60.5.7); у агента свой `agent-state.json`, чтобы не делить курсор с `state.json`.
- Тесты: `tests/unit/test_devlab_agent_worker.py` (настоящие хаб и репозитории, `ScriptedChatModel`, `LocalSandbox`): полный
  путь, stop, рестарт посреди задачи, outbox при недоступном хабе, отказ модели.

## Вопросы владельцу, resume, стоп-краны (60.5.5)
Код: `agent/loop.py`, `agent/dialog.py`, `executor/agent_worker.py`.

### Инструменты
- `step_done(title)`: страж `FinishGuard.verify_step()` — каждый `check` и узкий прогон изменённых тестовых файлов
  (`changed_test_files`: изменённые и не удалённые `test_*.py` / `*_test.py`, команда `test_argv` + пути без xdist,
  таймаут `narrow_test_timeout_s`); полный набор не гоняется, диффа не требует. Красный: шаг не
  принят, текст отказа уходит модели. Зелёный: колбэк `on_step`, работник делает `repo.milestone(title)` (push всегда) и
  шлёт `step_done` (`text` = название). Расход в `step_done` не кладётся (60.5.6).
- `ask_owner(question)`: цикл завершается `ASKED` с `Dialog` (сообщения, вопрос, `call_id` вызова). Остальные вызовы
  из того же ответа модели получают результат «не выполнено», результат самого `ask_owner` дописывается при ответе
  (`tool` с `ответ владельца: ...`).

### Стоп-краны
`AgentLimits`: `max_steps` 60 (обращений к модели), `max_wall_s` 8 ч, `max_red_runs` 5 подряд, `max_cost_usd` 2.0,
`max_tokens` (0 = выкл.). Проверка в начале каждой итерации; сработал: `ASKED` с вопросом «Стоп-кран: <причина>...»
и `call_id = None` (ответ при продолжении приходит user-сообщением). Красный прогон: красный `run_tests` или
отклонённый `step_done`; зелёный прогон обнуляет счётчик, красный отказ `finish` не считается (причина может быть
«нет диффа»). Шаги, красные прогоны и время считаются на отрезок работы между вопросами: ответ владельца на стоп-кран
выдаёт новый отрезок. Потолки $ и токенов сквозные на всю задачу: `spend()` и `tokens()` цикла отдают
накопленный итог (60.5.6), ответ на кран `cost`/`tokens` поднимает потолок ещё на один `max_cost_usd`
(`max_tokens`): потолок = значение * (1 + число таких ответов), счётчик в `SpendState.extensions`.
`AgentResult.crane` (`Crane`) говорит, какой кран сработал.

Кран повторов (60.9.8, `Crane.REPEAT`, `AgentLimits.max_repeats = 3`, в `DevlabConfig` поля нет). Ключ вызова: имя
инструмента + канонический JSON аргументов (`sort_keys`), к нему отпечаток дерева (`ToolBox.tree_fingerprint()`:
`changed_paths()` и хэш содержимого изменённых файлов). Окно: последние 6 вызовов отрезка. Тот же ключ при том же
отпечатке второй раз: вызов выполняется, а к результату дописывается `REPEAT_HINT` («этот вызов уже был, результат
тот же, попробуй иначе»). Если результат зелёный (начинается с `OK_HEAD`, «[код 0]»), дописывается `REPEAT_GREEN_HINT`:
не повторять проверку и вызвать `finish`, если шаги сделаны. Находка стенда 2026-11-14: на зелёном дереве «попробуй
иначе» уводил Qwen3.8 от финиша, и кран срабатывал вместо `finish`. Повтор чтения (`READ_ONLY_TOOLS`) получает `REPEAT_READ_HINT`: фрагмент уже прочитан и не менялся, не перечитывать, переходить к правке, проверке или `finish`; следующий такой же вызов остановит задание. Находка стенда 2026-11-16: GLM-XS на t4 после готовых правок трижды подряд читал один кусок `loop.py`, общий «попробуй иначе» не помог, кран сработал вместо `finish`. Третий раз: вызов не выполняется, остальные вызовы того же ответа получают
`REPEAT_SKIPPED`, кран с причиной «модель повторяет `<имя> <path|command>`», `call_id = None`. Правка файла между
вызовами меняет отпечаток, и повтор не считается. Счётчик живёт в `Segment`, поэтому ответ владельца выдаёт новый
отрезок и кран не срабатывает снова мгновенно. `REPEAT` не в `SPEND_CRANES` работника: ответ не продлевает $/токены.
В журнале шагов (`steps.jsonl`) запись `end` получает `crane: "repeat"`.
Отпечаток дерева кэшируется в `Segment` и сбрасывается после любого вызова не из `READ_ONLY_TOOLS` (`list_files`,
`read_file`, `grep`): правят дерево `edit_file`, `write_file`, `run_command`, `run_tests`. Серия чтений снимает дерево
один раз; сам снимок берётся из хэшей песочницы (`Sandbox.changed_digests()`), файлы повторно не читаются. Вызовы с
битым JSON аргументов, `finish`, `step_done` и `ask_owner` под кран не считаются и в окно не попадают.

### waiting_owner в работнике
- `question` (`text` + токены отрезка): сначала диалог пишется в `<задание>/dialog.json`, `sandbox.stop()` (ошибка
  только в лог), `repo.flush()` (повтор без предела: wip должна быть на хабе), задание уходит в `parked` в
  `agent-state.json` (`job` обнуляется), слот свободен. Каталог задания и остановленный контейнер остаются.
- `answer` из `poll` дописывается в `dialog.json` и помечает запись `answered`; следующий `claim_once` берёт такую запись
  раньше нового `claim` (без второго `started`), поднимает контейнер (`resume()` у удержанного объекта, после рестарта
  исполнителя новый `start()`) и продолжает `AgentLoop.run(..., resume=dialog)` с того же места. Если рестарт случился
  после взятия ответа, `dialog.json` с ответом всё ещё на диске: продолжение пойдёт с него (сообщения после ответа
  не сохраняются, модель переделывает хвост по рабочей копии).
- `stop` для ждущего задания: открыть репозиторий, `abandon` (`agent/<id>` с частичным результатом), `stopped`, зачистка.
- `resume` с хаба (замена модели и/или замечания): запись `parked` и каталог зачищаются, диалог старой модели не
  переносится; задание возвращается через обычный `claim` с новой моделью. Новый агент получает task.md, журнал
  шагов (вехи `веха: ...` из `wip/<id>`, `AgentRepo.milestones()`), замечания из `payload.text` и список изменённых
  файлов. Замечания лежат в `job.params.remarks` (хаб кладёт их при `resume`) и приходят вместе с `claim`, поэтому
  гонка `claim`/`poll` их не теряет (60.5.6); при рестарте посреди задачи они попадут в промпт снова.
- Занятость (60.6.1, `BusyTracker` исполнителя, `executor.md`): `running` с `handle` (и с восстановления
  `agent-state.json` после рестарта); `question` ставит `waiting_owner`, время вопроса пишется в
  `parked[<id>].asked_at` и держит машину `[devlab].owner_wait_s`; `release` помечает запись `released`
  (удержание снято, задание остаётся в `parked`, хаб разбудит mycraft ответом); `answer` возвращает
  «выполняется»; `resume`/`stop`/закрытие парковки и конец задания снимают всё. Непустой
  `agent-outbox.json` держит машину независимо от задач.
- Тесты: `tests/unit/test_devlab_agent_owner.py` (хаб, настоящий репозиторий, `ScriptedChatModel`, `LocalSandbox` со
  шпионом): вопрос-ответ, рестарт до и после ответа, resume со сменой модели, stop в ожидании, step_done
  красный/зелёный, каждый кран.

## Модель и расход (60.5.6)
Код: `agent/spend.py`, `executor/routing.py`, `executor/agent_worker.py`.
- Какие задания берёт исполнитель: `claim` шлёт `ModelCatalog.names()` (модели живых шлюзов с адресом)
  вместо `[]`; каталог недоступен — `claim_once` ничего не берёт. После `claim` `_check_model` сверяет модель
  с каталогом и `allow_remote_models` из `.devlab.toml` (по умолчанию `false`): внешняя модель при запрете
  или модель, пропавшая из каталога, дают `failed` с причиной (владелец может `resume` с другой моделью).
- `MeteredChat` оборачивает модель задания: после каждого ответа `JobSpend.record` копит токены и $ в
  `agent-state.json` (`spend[<id задания>]`, `SpendState`), так что учёт переживает рестарт и отрезки
  между вопросами. База — `job.tokens`/`job.cost_usd` хаба на момент свежего `claim`; продолжение после
  ответа или рестарта берёт сохранённое состояние, а не снимок задания.
- Расход уходит в хаб дельтой с каждым сообщением (`step_done`, `question`, `done`, `failed`, `stopped`:
  `tokens`, `cost_usd`; `JobSpend.take_report`), хаб складывает его в `jobs.tokens/cost_usd`, их видит
  `devlab_status`. Запись `spend` убирается, когда задание закрыто (в `parked` остаётся).
- Потолок $ по умолчанию `AgentLimits.max_cost_usd` = 2.0 на всю задачу.
- Тихая трата: ответ `free` модели с `usage.cost > 0` — `PaidFreeModelError` (после учёта расхода), цикл
  отдаёт `ASKED` с краном `paid_free` и вопросом «Стоп-кран: бесплатная модель начала тратить деньги ...».
  Ответ с тратой отброшен, при «продолжай» запрос повторится и, если провайдер снова списывает, кран сработает
  снова; разумный ответ владельца — `resume` с другой моделью. OpenRouter отдаёт `usage.cost` по умолчанию;
  провайдер, который его не шлёт, считается по цене шлюза (у `free` — нулю, и трата не видна).
- Смена модели (2026-11-18): при запуске на другой модели — новый отрезок лимитов (`extensions + 1`).
- Тесты: `tests/unit/test_devlab_agent_spend.py` (каталог с двумя шлюзами одной модели и отказ одного,
  запрет remote, $ через рестарт и вопрос, сквозной потолок, free с ненулевой стоимостью, гонка
  `claim`/`poll` для замечаний), `test_devlab_models.py` (поля `models`/`route`, фактическая стоимость, `url`).

## Напоминание о шагах в конце запроса (2026-11-14)

`GatewayChat.complete` дописывает `FLOW_REMINDER` (`agent/prompt.py`, `with_flow_reminder`) к каждому сообщению,
которое закрывает шаг: последнему сообщению запроса и каждому сообщению, за которым идёт ответ ассистента (задание,
последний `tool`-ответ шага, ответ владельца). Свёрнутые выводы (`[вывод свёрнут…]`) напоминание не получают. В
диалоге оно не хранится, добавляется при сборке запроса; так уже отправленная часть запроса не меняется от шага к
шагу (с 2026-11-15, до этого напоминание стояло только в последнем сообщении). Текст английский,
в той же редакции, что прошла стенд; у GLM свой русский текст (`GLM_FLOW_REMINDER`, см. «Профиль GLM»). Суть: идти по «Шагам» задания, на зелёном шаге вызывать `step_done`, в конце
прогнать «Финальный прогон» и ruff и вызвать `finish` в том же ответе.

Почему так: к шагу 60–70 при контексте 60–80 тыс. токенов указания системного промпта про `step_done` и `finish`
тонут. Qwen3.8 IQ3_XXS на T4 доделывал код, но не закрывал шаги и упирался в потолок токенов. С напоминанием
в конце (стенд, через прокси) 12 из 13 прогонов T4/T6/T7/T11 кончились принятым `finish`, судья ставил T4 14.8/20
вместо 11.8.

## Возврат размышлений модели (2026-11-14)

`ModelReply.as_message` кладёт `reasoning_content` ответа с вызовами инструментов в само сообщение ассистента, и
оно идёт в истории диалога вместе с ответом: окно его учитывает, свёртка удаляет размышления старых ответов первой

модель OpenRouter теряла свой план на каждом шаге и, как Qwen без возврата размышлений на стенде, ходила кругами.

## Профиль GLM (2026-11-15, переписан 2026-11-16)

`agent/prompt.py` держит две вводные: `SYSTEM_INTRO` (прежняя) и `GLM_INTRO` — Markdown с заголовками
(`# Роль`, `## Как работать`, `## Формат хода`, `## Процесс анализа`) и позитивными формулировками правил. Выбор
делает подстрока `glm` в имени модели (без учёта регистра): `intro_for(model)` и `reminder_for(model)`.
Для GLM `build_system(rules, model, commands, today)` после вводной добавляет блок `## Обстановка`
(`glm_setting`): сегодняшнюю дату, разрешённые команды `run_command` из `allowed_commands` проекта и то, что агент
не коммитит, не деплоит и из правил проекта его касаются правила про код, тесты и документацию. `AgentWorker`
передаёт `job.model` и `spec.allowed_commands`, дата берётся на исполнителе. Напоминание о шагах у GLM русское
(`GLM_FLOW_REMINDER`), `GatewayChat` выбирает его по имени модели. Прежние модели (Qwen3.8, gpt-oss, flint)
получают прежний системный промпт и английское `FLOW_REMINDER` байт в байт.

Зачем отдельный промпт: GLM-5.3 (движок Project Maya) после RL лучше слушает Markdown-заголовки и позитивные
указания («делай так», а не «нельзя так») и выполняет их буквально, поэтому ошибка в промпте стоит ему ходов.

Находки 2026-11-16 (стенд, Maya-XS, t2 и t12), из которых выросла редакция:
- прежняя вводная велела читать код через `run_command` (`sed -n`, `rg`), а таких команд нет в
  `allowed_commands`; теперь чтение идёт через `read_file`/`grep`;
- указание из `CLAUDE.md` про `PYTHONPATH=$PWD/src` в worktree агент принимал на себя и запускал тесты
  через `PYTHONPATH=… | tail` — отказ и потерянный ход (t2, t12); блок «Обстановка» говорит, что песочница
  уже настроена;
- шаг задания «готово, когда: тест красный» агент закрывал `step_done`, а тот принимает только зелёный полный
  набор: на t2 один отказ (~95 с), на t12 три отказа подряд и стоп-кран «5 красных прогонов подряд», задание не
  сдано. Теперь вводная, напоминание и текст отказа `STEP_REJECTED` (общий для всех моделей) говорят, что такой
  шаг закрывается вместе с правкой;
- без даты в промпте агент ставил у находок выдуманную дату (2026-11-01 вместо 2026-11-15);
- «один инструмент за ход» модель и так нарушала двумя `read_file` в одном ходе, а каждый лишний ход стоит
  10–15 с; теперь независимые чтения разрешены пачкой, правки и проверки по одной.

Задания стенда берут правила (`rules`) из базового коммита, поэтому редакция живёт в коде, а не в `CLAUDE.md`
или `.devlab.toml`.

Параметры запроса этой модели (`reasoning_effort`, `logit_bias`, сэмплинг) задаются не в коде, а в `params`
записи модели на шлюзе (`devlab/models.md`: шлюз подставляет `params` в каждый запрос, поля самого запроса
важнее). Тесты: `tests/unit/test_devlab_agent_prompt.py`.

## Чтение файла по окну (2026-11-19)

`read_file` отдаёт не больше 200 строк за вызов, поэтому агент перечитывает длинные файлы кусками (на стенде одни
и те же места `queue.py` по 3–4 раза). Предел строк теперь идёт от окна задания: `read_max_lines(window_tokens)`
в `tools.py` делит окно в токенах на `READ_TOKENS_PER_LINE` = 60 и зажимает в `[READ_MIN_LINES` = 200,
`READ_MAX_LINES_CAP` = 2000]. `ToolBox.__init__` принимает `read_lines` (по умолчанию 200 — прежнее поведение),
`_read_file` использует его. `AgentWorker` перед `AgentLoop` вычисляет окно один раз — `window_tokens(entries,
self._settings.limits.context_tokens)` — и передаёт его в `ToolBox(sandbox, spec, read_max_lines(window))` и в
`_limits_for(..., window)` (который больше не вызывает `window_tokens` второй раз). Схема `read_file` описана как
«за вызов отдаёт сколько поместится, в ответе видно, сколько строк всего». Тесты: `tests/unit/test_devlab_agent.py`
(`read_max_lines`, чтение 450 строк за один вызов при `read_lines=500`).

## Code Mode: скрипт модели (2026-11-21)

Роль с Code Mode получает инструмент `run_script(code)`: модель пишет Python, и за один ход скрипт читает
сразу несколько файлов, ищет и печатает только нужные куски, ставит в очередь правки и узкие тесты. На стенде
2026-11-20 модель без такого инструмента читала файлы по одному (23 `read_file` на задачу).

Модуль `devlab/agent/script.py`. `script_argv(code)` собирает `[python, "-I", "-c", source]` для
`Sandbox.exec` (тот же контейнер задания, корень проекта — текущий каталог, `-I`: модули проекта не
импортируются). `source` = пролог + код модели (вставлен через `repr`) + исполнение в отдельном
пространстве имён через `exec(compile(code, "<script>", "exec"))`. Пролог — строка в коде, не файл в дереве.
Функции пролога:
- `ls(prefix="")` — отсортированные относительные пути файлов, каталоги `IGNORED_DIRS` песочницы пропущены;
- `read(path, start=1, end=None)` — строки с номерами `"{n}\t{line}"`, как у `read_file`;
- `read_many(paths)` — словарь путь → текст файла целиком в том же виде;
- `grep(pattern, prefix="", context=0)` — список `"path:n:line"` для совпадений и `"path-n-line"` для
  соседних строк; файлы больше 200 000 байт и не UTF-8 пропускаются, не больше 200 совпадений
  (`SCRIPT_GREP_MAX_MATCHES`, у `grep`-инструмента 50);
- `edit(path, old, new)`, `write(path, content)`, `run_tests(paths)` — файлы не трогают, только дописывают
  действие в список; аргументы — строки, иначе `TypeError` сразу в скрипте; `run_tests` принимает список
  путей (или одну строку) и кладёт их через пробел, как `paths` у инструмента.

Правки отложены, потому что политика путей роли (`write_prefixes`, `forbidden_paths`, секреты), дописывание
перевода строки и журнал шагов живут на хосте в `ToolBox`; скрипт в контейнере их обошёл бы.

Последней строкой пролог печатает `ACTIONS_MARKER` (`"DEVLAB_ACTIONS "`) и JSON
`{"failed": bool, "actions": [{"tool": имя, "args": {...}}]}`. Имя действия — имя функции пролога
(`ACTION_EDIT`/`ACTION_WRITE`/`ACTION_RUN_TESTS`), а не инструмента: `tools.py` будет импортировать
`script.py`, и обратный импорт констант инструментов замкнул бы цикл; соответствие действие → инструмент
лежит в `tools.py`. Исключение в коде печатает трассировку в stdout и ставит `failed`; `sys.exit(0)` —
не сбой. `parse_output` берёт последнюю строку с маркером, вывод — текст без неё; нет маркера или JSON
битый — `failed=True`, действий нет, вывод целиком. Тесты: `tests/unit/test_devlab_agent_script.py`.

Флаг роли: `code_mode = true` в `[devlab.agent_profiles.<роль>]` (`DevlabProfileConfig.code_mode`, по
умолчанию выключен). Работник агента переносит его в `AgentSpec.code_mode` тем же `replace`, что и
`write_prefixes`; задание без роли идёт с `code_mode=False`. Тест:
`test_profile_fields_reach_toolbox_spec` в `tests/unit/test_devlab_agent_worker.py`.

Инструмент `run_script` (`TOOL_RUN_SCRIPT`, схема `RUN_SCRIPT_DEFINITION` в `tools.py`) есть в
`ToolBox.definitions` и в обработчиках только при `spec.code_mode`; без флага `call` отвечает «неизвестный
инструмент», набор и размер схем прежние. `ToolBox._run_script`:
- снимает `changed_digests` песочницы до и после исполнения; если скрипт сам изменил файлы (`open(..., "w")`,
  `os.remove`), действия не исполняются, ответ называет пути и велит менять файлы только через
  `edit()`/`write()`, а изменённое вернуть через `edit_file`/`write_file` (`mutating=True`). Отката нет:

- `mutating` — если исполнено хоть одно `edit`/`write`; `green` — из последнего исполненного

### 2026-11-22 (Code Mode по схеме Cloudflare)

Имя инструмента `run_script` и всё, что в этом разделе выше про отложенные действия и очередь после
скрипта, устарело: ниже текущее устройство.

Разбор прогона бесплатной модели (nemotron через OpenRouter, 68 запросов, провал): модель писала
нормальный Python, а наш API вёл себя не как Python.
- `edit()`/`write()` откладывались до конца скрипта: модель печатала «готово», правка падала потом, а
  `read()` в том же скрипте её не видел.
- Запись через `open(..., "w")` отклонялась, и ошибка советовала `edit_file`/`write_file`, которых в
  Code Mode нет.
- `read()` отдавал строки с номерами, их нельзя подставить в `old`, поэтому модель читала через `open()`.
- Функции были описаны строками без сигнатур (модель писала `import grep`), про запрет `subprocess` не
  было сказано.
- `run_tests()`/`run()` откладывались, и нельзя было написать «прогнать тесты, зелёные — finish, красные —
  ask_owner».

Что сделано:
- Инструментов два: `search(query)` (`TOOL_SEARCH`; бывший `find()`, из скрипта убран) возвращает Python-
  заглушки с типами и строкой описания из `SCRIPT_API` (`script.py`), пустой `query` — все; и
  `execute(code)` (`TOOL_EXECUTE`, бывший `run_script`). `step_done`, `finish`, `ask_owner` из списка
  инструментов убраны, это функции внутри кода.
- Всё исполняется сразу. `edit()`/`write()` пишут файл на месте; `edit()` при 0 или >1 совпадений
  кидает `EditError`, запрещённый путь тоже. `read()` — чистый текст, `read_numbered()` — с номерами.
  `run()`/`run_tests()` запускают процесс прямо из скрипта (в пролог сохранён настоящий `Popen.__init__`,
  для кода модели подменённый) и возвращают `Result` (`code`, `output`, `ok`; `str` = «[код N]» и вывод).
  Недопустимая команда — `Result` с кодом 126, а не исключение. Остальные процессы запрещены текстом
  «процессы запускай через run()/run_tests()».
- Запись через `open()`/`pathlib` допустима: пролог подменяет `open` и перед записью запоминает исходные
  байты файла. По окончании скрипта изменённые файлы проверяются теми же правилами, что `edit_file`
  (`forbidden_paths`, `secret_paths`, `write_prefixes`); нарушитель откатывается, в выводе строка
  «правка отклонена…». Файлы, изменённые мимо `open` (`os.rename`), откатить нельзя, о них сказано в
  выводе. Правки самих процессов `run()`/`run_tests()` не проверяются, как и раньше.
- `step_done`/`finish`/`ask_owner` кидают сигнал, унаследованный от `BaseException`: он не ловится
  `except Exception`, всё до него уже исполнено. Цикл обрабатывает запрос теми же стражами
  (`_close_from_script`), ответ приписывается строкой «step_done: …»/«finish: …». `ask_owner` из скрипта
  ставит вопрос владельцу и привязывает диалог к вызову `execute`.
- Таймаут: `AgentSpec.script_timeout_s` = `command_timeout_s` + `narrow_test_timeout_s` + 30 с (по
  умолчанию 630 с). Внутри скрипта каждый `run()`/`run_tests()` получает свой таймаут, но не больше
  остатка бюджета (`script_timeout_s` − 20 с); при нехватке времени вернётся `Result` с кодом -1.
- Промпт (`CODE_MODE_INTRO`, `CODE_MODE_SETTING`, `CODE_MODE_REMINDER`): сигнатуры как заглушки, «функции
  определены, import не нужен», примеры шага и финала, про очередь после скрипта ничего нет. Потолок
  вывода `SCRIPT_OUTPUT_CHARS` и подсказка обрезки прежние. Без `code_mode` определения, промпты и тексты
  не менялись.
- Метрики стенда: имя вызова в журнале шагов теперь `execute` (`code_chars`, `script_failed`, `rejected`
  те же).

Тесты: `tests/unit/test_devlab_agent_script.py`, `test_devlab_agent_run_script.py`,
`test_devlab_agent_prompt.py`.
