# Агент-разработчик `devlab`

Этап 60, задача 60.5. Модель + обвязка, которые выполняют задание вида `agent`. Код: `devlab/agent/`.
60.5.1 (сделано) — цикл агента; 60.5.2 (сделано) — ветки агента, раздел «Git агента» ниже; он ничего не знает ни о хабе, ни о git, ни о Podman. Остальное
(ветки, контейнер, работник, вопросы владельцу, расход, слоты) — 60.5.2–60.5.7, см.
`IMPLEMENTATION_PLAN.md`.

## Состав
- `model.py` — `ChatModel` (`complete(messages, tools) -> ModelReply`) и `GatewayChat`:
  `POST <base_url>/v1/chat/completions` к шлюзу `devlab_models` без stream, с
  `Authorization: Bearer <токен исполнителя>` и `X-Devlab-Job: <id задания>` (по нему шлюз пишет
  расход). Токены `usage` возвращаются в `ModelReply`. Таймаут запроса `MODEL_TIMEOUT_S` = 30 мин
  (стенд 60.2: на CPU один запрос с большим окном идёт десятки минут). Любая беда транспорта и
  разбора — `ModelError`; тело ошибки шлюза (`{"error": ...}`) приводится к тексту.
- `sandbox.py` — интерфейс `Sandbox`: `read_bytes`, `write_bytes`, `list_files`,
  `exec(argv, timeout_s)`, `changed_paths()` (изменения относительно базы). Пути относительные,
  выход за корень — `SandboxPathError`. `LocalSandbox` на каталоге (тесты и отладка); контейнерная
  реализация — `PodmanSandbox` (60.5.3, ниже). `ExecResult.summary` режет вывод до конца (ошибки в конце) и помечает таймаут.
- `spec.py` — `AgentSpec`: команда тестов, `checks`, `allowed_commands`, `forbidden_paths`,
  `secret_paths`, `diff_prefixes`, таймауты, лимит вывода. Собирается `AgentSpec.from_project(ProjectSpec)`
  из `.devlab.toml`: `test_argv` и `test_timeout_s` берутся из `[test]` (`cmd`+`args`, `timeout_s`), остальное из `[agent]`.
- `tools.py` — `ToolBox` и схемы: `list_files`, `read_file` (по строкам, ≤200 за вызов), `grep`,
  `edit_file` (один фрагмент, ровно одно вхождение), `write_file`, `run_command` (только
  разрешённые префиксы, без оболочки), `run_tests`, `finish`. Ошибка инструмента — `ToolError`,
  текст уходит модели. `forbidden_paths` закрывает запись, `secret_paths` — запись и чтение (glob или префикс-каталог с `/`, один матчер `agent/paths.py`).
- `context.py` — окно. Оценка `len(json)/3` токенов. Перед каждым запросом, если диалог не влезает
  в `context_tokens - reply_tokens - схемы инструментов`, старые выводы инструментов (кроме
  `keep_recent` последних) заменяются на `[вывод свёрнут: N симв.]`, затем длинные аргументы
  старых вызовов (`write_file`). Системное сообщение и задание не сворачиваются. Не влезло и так —
  `CONTEXT_OVERFLOW`. По умолчанию окно 16000 (замер 60.2: больше 16k Flint на CPU деградирует).
- `guard.py` — `FinishGuard.verify()`: непустой дифф (в путях `diff_prefixes`, если заданы), затем
  тесты и каждый `check` в песочнице. Возвращает список причин отказа.
- `loop.py` — `AgentLoop.run(system, task) -> AgentResult`.

## Поведение цикла
- Закончить можно только вызовом `finish(summary)`; страж отклоняет без диффа и при красных
  тестах/стражах, текст отказа возвращается модели как результат инструмента, цикл продолжается.
- Ответ без вызова инструмента (в том числе «готово» текстом) не засчитывается: модели
  напоминают, после `max_idle_replies` подряд — `STUCK`.
- Ошибка инструмента (в том числе неожиданное исключение и невалидный JSON аргументов) не роняет
  цикл: модель получает `ошибка: ...`. `CancelledError` не глотается.
- `ModelError` завершает цикл `MODEL_FAILED` с причиной; повтор и смена модели решает вызывающий
  (60.5.4–60.5.6). Токены считаются по всем ответам, в `AgentResult`.
- Исходы: `FINISHED`, `ASKED`, `MODEL_FAILED`, `CONTEXT_OVERFLOW`, `STUCK`.
- `on_change(описание)` — async-колбэк после `edit_file`, `write_file`, `run_command`; в 60.5.2 по нему
  делается коммит (репозиторий сам решает, чистое ли дерево).

## Шлюз
Исполнитель ходит в шлюз тем же токеном `executor`, что и в хаб (шлюз проверяет его через
introspect). Код выбора — `executor/routing.py` (60.5.6).
- Решение владельца 2026-11-01: одна модель (один ключ OpenRouter) стоит на шлюзах jeeves и wooster;
  jeeves может умереть, служба может переехать на американский сервер. Локальная модель (llamacpp на
  mycraft) — свой шлюз, единственный.
- `ModelCatalog` читает `POST /api/catalog` хаба (записи с `url`, только свежие heartbeat), держит
  кэш `CATALOG_TTL_S` = 15 с; хаб недоступен — берётся прошлый кэш, а без кэша ошибка.
  `CatalogEntry`: `name`, `gateway`, `url`, `free`, `price_in`, `price_out`, `remote`.
- `FailoverChat` (`GatewayModels` строит его на задание): перебирает шлюзы модели, предпочитая тот,
  что ответил в прошлый раз. Транспортная ошибка, HTTP 5xx и 429 (`ModelError.transient`) — следующий
  шлюз с теми же `messages`, то есть диалог не теряется (он живёт у исполнителя, а не у шлюза).
  4xx (кроме 429) и таймаут запроса не переключают. Обошли все — пауза `ROUTE_RETRY_S` и новый круг с
  обновлённым каталогом, всего `ROUTE_ROUNDS` = 3, затем `ModelError` («все шлюзы ... отказали»).
- Цена ответа (`price_reply`): фактическая `usage.cost` провайдера, иначе токены * цена шлюза из каталога;
  у `free` цена 0. `free` и `usage.cost > 0` — `ModelReply.paid_free`.

## Git агента (60.5.2)
`repo.py`, `AgentRepo` поверх `ProjectMirror` (общий `GitRunner` из `executor/mirror.py`: токен
только в окружении `GIT_CONFIG_*`, из ошибок вырезается). Ветки: `base/<id>` (снимок клиента) →
`wip/<id>` (ход работы) → `agent/<id>` (итог). Репозиторий рабочей копии лежит отдельно от неё
(`git_dir` рядом с `workdir`), так что в каталог, который уйдёт в контейнер, `.git` не попадает.
- `open()`: fetch зеркала; если `wip/<id>` на хабе есть, рабочая копия встаёт на его вершину,
  иначе на `base/<id>`. Если локальная копия уже впереди вершины хаба (не успели запушить до
  рестарта), она сохраняется, а не затирается; хвост уйдёт следующим push.
- `on_change(описание)` подключается к `AgentLoop`: `git add -A`, пустые изменения не коммитятся,
  тема коммита — описание действия. Автор настраивается: `CommitAuthor`, по умолчанию
  `agent_author(модель)` = `devlab-agent (<модель>)`.
- Склейка push: не чаще раза в `push_interval_s` (30 с). Первое изменение уходит сразу, дальнейшие
  копятся и уходят таймером, который выставляется на остаток интервала; неудавшийся push не
  роняет цикл (лог, повтор по таймеру/`flush()`). `milestone(название)` (для `step_done`) и
  `finish`/`abandon` пушат всегда и с ошибкой, если не вышло.
- `milestone`: коммит `веха: <название>` (допускается пустой: веха фиксирует шаг даже без правок).
- `finish(резюме)`: докоммитить хвост, push `wip`, squash одним коммитом на `base/<id>` с деревом
  `wip` (сообщение: резюме, id задания, автор, список вех), push `+agent/<id>`, удаление
  `wip/<id>` на хабе и локального репозитория. Каталог `workdir` не трогается.
- `abandon(причина)` для `failed`/`stopped`: то же, но сообщение `не завершено: <причина>`; если
  правок относительно базы нет, `agent/<id>` не создаётся. Клиенту остаётся видимым `agent/<id>`
  с частичным результатом (если он есть); `wip/<id>` не остаётся никогда.
- Права: пушатся только `wip/<id>` (создать/обновить/удалить) и `agent/<id>` (создать/обновить),
  всё в рамках `refpolicy` для роли `executor`.
- Тесты: `tests/unit/test_devlab_agent_repo.py` (настоящие git и хаб).

## Контейнер задачи (60.5.3)
`devlab/executor/agent_sandbox.py`, `PodmanSandbox` — реализация `Sandbox` в долгоживущем контейнере.
Общее с `PodmanTestRunner` (вызов обёртки, образ и его кэш) вынесено в `executor/wrapper.py` и `executor/image.py`.

### Где источник истины
Рабочая копия на хосте исполнителя (`AgentRepo.workdir`). Почему:
- репозиторий агента смотрит именно в этот каталог, `on_change` видит правки без дополнительной синхронизации;
  `read_bytes`/`write_bytes`/`list_files`/`changed_paths` — это `LocalSandbox` на нём (быстро, без вызовов обёртки на чтение);
- контейнер можно остановить или потерять (рестарт хоста, `podman rm`), рабочая копия при этом цела;
  `waiting_owner` не зависит от жизни контейнера.
- Копия в контейнере (`~devlab/work/<id>`, bind-mount в `/work`) — зеркало. Если с прошлой синхронизации был
  `write_bytes` (флаг `_stale`), перед командой дерево отправляется `refresh` (содержимое заменяется, каталог остаётся
  тем же inode). После КАЖДОЙ команды `sync-out` забирает всё дерево, расхождения применяются на хосте: изменённые и
  новые файлы пишутся, исчезнувшие удаляются. Так форматтер в контейнере попадает в рабочую копию, а `ToolBox` после
  `run_command` зовёт `on_change`.
- Не отправляются в контейнер и не возвращаются: кэши (`IGNORED_DIRS`), `.devlab-junit.xml`, `secret_paths`.

### Правила путей
- `secret_paths` (`.env`, `config.toml`): не уходят в контейнер (команда агента не может `cat .env`), не видны в
  `list_files`/`grep`, чтение и запись — `SandboxPathError`, из контейнера не возвращаются.
- `forbidden_paths`: чтение можно, `write_bytes` отказывает. Если команда в контейнере всё же изменила такой файл, на
  хост это НЕ переносится, а следующая команда начинается с `refresh` и откатывает контейнер к хостовой копии.
- Два списка нужны потому, что `forbidden_paths` в 60.5.1 означает «закрыто для правок» (агент должен читать `tests/`).

### Жизненный цикл
- `start()`: `sync-in` (без секретов) → `ensure_image` (рецепт `[test]`: `image`, `setup`, `setup_files`, `env`; кэш по
  хэшу, сборка с сетью) → `rm` хвоста и `create <id> <тег> <cpus> <память> <cpuset>` (без сети, квоты агента).
- `exec(argv, timeout_s)`: под замком (команды по одной), `timeout` внутри контейнера (код 124 → `timed_out`), внешний
  запас `EXEC_GRACE_S`. После таймаута контейнер удаляется (мог зависнуть процесс), `_lost`; следующая команда создаёт его
  заново из того же образа и делает `refresh`. Образ не пересобирается.
- `stop()` (для `waiting_owner`): `podman stop`; хостовая копия и `~devlab/work/<id>` остаются. `exec` на остановленном — `RunnerError`.
- `resume()`: `start`; если не вышло, полный `sync-in` + образ + `create` заново. Перед первой командой всегда `refresh`.
- `aclose()`: `rm` контейнера и `clean` копии у `devlab` под `asyncio.shield`. Хостовая рабочая копия не трогается.
- Ресурсы агента: `[devlab] agent_cpus/agent_memory/agent_cpuset` (конфиг владельца исполнителя, не проекта: проект не
  выбирает, сколько ядер ему дать). Квоты диска нет: на bind-mount у rootless podman её нет (открыто).
- `baseline` (необязательный) — хэши исходного дерева для `changed_paths`; после рестарта работник 60.5.4 передаёт
  `LocalSandbox(<checkout base/<id>>).snapshot()`, иначе правки до рестарта пропадут для `FinishGuard`.

### `[agent]` в `.devlab.toml`
`rules` (файлы правил в системный промпт; читает работник 60.5.4), `checks` (команды-стражи строками), `allowed_commands`
(префиксы для `run_command`), `forbidden_paths`, `secret_paths`, `diff_prefixes`, `allow_remote_models` (по умолчанию
`false`; применит 60.5.6), `command_timeout_s`, `output_chars`. Неизвестный ключ в `[agent]` — `SpecError` (опечатка не
должна молча снимать защиту). Команда тестов и её таймаут — из `[test]`. sa-home-bot: rules = CLAUDE.md, checks =
`ruff check src tests` и `test_no_comments_in_code`, `diff_prefixes = ["src/"]`, `forbidden_paths` = `.devlab.toml`,
CLAUDE.md, pyproject.toml, `deploy/`; секреты — `.env`, `config.toml*`, `instances/*`, `*.sqlite`, `data/`.

### Ограничения
- Файлы, созданные в контейнере не-root пользователем, принадлежат subuid и не удаляются `refresh`/`clean` (так же у
  `PodmanTestRunner`); образы по умолчанию работают от root.
- `sync-out` после каждой команды забирает всё дерево (tar в памяти, файлы больше 32 МиБ пропускаются): для проекта
  размером с sa-home-bot доли секунды, для больших нужен выборочный sync.
- Тесты: `tests/unit/test_devlab_agent_sandbox.py` (фейковая обёртка с состоянием контейнера),
  `tests/unit/test_devlab_wrapper_script.py` (`refresh` в настоящем `sh`).

## Работник агента (60.5.4)
`devlab/executor/agent_worker.py`, `AgentWorker` — связывает цикл, репозиторий и контейнер. Общие три фоновых цикла
(heartbeat, poll, claim) вынесены в `WorkerLoops` (`executor/worker.py`), от него наследуются `TestWorker` и `AgentWorker`.
- Вход: `ExecutorHub`, `ModelFactory` (`(модель, id задания) -> ChatModel`; боевая — `GatewayModels(catalog, token)`
  с общей сессией), `SandboxFactory` (боевая — `podman_sandbox_factory(cfg)`, в тестах `LocalSandbox`) и `AgentSettings`
  (`WorkerSettings` + `limits`, `push_interval_s`, `retry_interval_s`) и `Catalog` (60.5.6: список моделей для `claim`, проверка
  модели; выбор и переключение шлюзов — раздел «Шлюз»). `ExecutorHub.claim(kinds, models)` теперь принимает модели.
- Задание: `claim` вида `agent` → `post started` → в каталоге `<work_dir>/agent/<id>/` свой зеркальный bare-репозиторий,
  `work/` (рабочая копия), `git/` (репозиторий агента), `base/` (временный экспорт базы) → `AgentRepo.open()`
  (база — `job.base_branch`, не обязательно `base/<id>`; для этого у `AgentRepo` появился параметр `base_branch`) →
  `.devlab.toml` и файлы `[agent] rules` читаются из коммита базы → `baseline` = снимок экспорта базы (одинаков для
  первого запуска и для продолжения) → `sandbox.start()` → `AgentLoop` с `on_change=repo.on_change`.
- Промпт (`agent/prompt.py`): системное сообщение — вводная и файлы `rules`; task.md — первое пользовательское сообщение.
  При продолжении к task.md дописывается список файлов, уже изменённых относительно базы.
- `ManagedSandbox` (`agent/sandbox.py`) — `Sandbox` плюс `start/stop/resume/aclose`; у `LocalSandbox` это пустышки.
- Исходы: `FINISHED` → `repo.finish` (повтор без предела: результат нельзя потерять) → `done` (резюме, токены, модель);
  `MODEL_FAILED`/`CONTEXT_OVERFLOW`/`STUCK` и исключения → `repo.abandon` (3 попытки) → `failed` с причиной;
  `stop` из `poll` отменяет задачу цикла → `abandon` → `stopped` (`agent/<id>` остаётся с частичным результатом,
  `wip/<id>` нет). Каталог задания удаляется после закрытия.
- Остановка службы (отмена): под `shield` `repo.flush()`, затем `repo.aclose()` и `sandbox.aclose()`; состояние остаётся.
- Состояние `<work_dir>/agent-state.json`: `cursor` и `job` (задание целиком). На старте непустой `job` значит, что задание
  всё ещё `running` на хабе: первым в claim-цикле берётся оно же (без нового `claim` и без второго `started`), рабочая
  копия поднимается с вершины `wip/<id>` (или локальной, если она впереди).
- Исходящий outbox `<work_dir>/agent-outbox.json`: каждое сообщение хабу (`started`, `done`, `failed`, `stopped`) сначала
  дописывается на диск, потом уходит; недоступность хаба и 5xx оставляют его в очереди (порядок сохраняется, повтор
  каждый `poll_interval_s` и на старте), 4xx (`HubRequestError.permanent`) — сообщение отвергнуто, логируется и снимается.
  Задание считается закрытым локально, как только терминальное сообщение записано в outbox.
- Учёт расхода — раздел «Расход» ниже. `poll` у `TestWorker` и `AgentWorker` идут
  раздельно (общая служба — 60.5.7); у агента свой `agent-state.json`, чтобы не делить курсор с `state.json`.
- Тесты: `tests/unit/test_devlab_agent_worker.py` (настоящие хаб и репозитории, `ScriptedChatModel`, `LocalSandbox`): полный
  путь, stop, рестарт посреди задачи, outbox при недоступном хабе, отказ модели.

## Вопросы владельцу, resume, стоп-краны (60.5.5)
Код: `agent/loop.py`, `agent/dialog.py`, `executor/agent_worker.py`.

### Инструменты
- `step_done(title)`: страж `FinishGuard.verify_green()` (тесты и каждый `check`, без требования диффа). Красный: шаг не
  принят, текст отказа уходит модели. Зелёный: колбэк `on_step`, работник делает `repo.milestone(title)` (push всегда) и
  шлёт `step_done` (`text` = название). Расход в `step_done` не кладётся (60.5.6).
- `ask_owner(question)`: цикл завершается `ASKED` с `Dialog` (сообщения, вопрос, `call_id` вызова). Остальные вызовы
  из того же ответа модели получают результат «не выполнено», результат самого `ask_owner` дописывается при ответе
  (`tool` с `ответ владельца: ...`).

### Стоп-краны
`AgentLimits`: `max_steps` 60 (обращений к модели), `max_wall_s` 8 ч, `max_red_runs` 5 подряд, `max_cost_usd` 2.0,
`max_tokens` (0 = выкл.). Проверка в начале каждой итерации; сработал: `ASKED` с вопросом «Стоп-кран: <причина>...»
и `call_id = None` (ответ при продолжении приходит user-сообщением). Красный прогон: красный `run_tests` или
отклонённый `step_done`; зелёный прогон обнуляет счётчик, красный отказ `finish` не считается (причина может быть
«нет диффа»). Шаги, красные прогоны и время считаются на отрезок работы между вопросами: ответ владельца на стоп-кран
выдаёт новый отрезок. Потолки $ и токенов сквозные на всю задачу: `spend()` и `tokens()` цикла отдают
накопленный итог (60.5.6), ответ на кран `cost`/`tokens` поднимает потолок ещё на один `max_cost_usd`
(`max_tokens`): потолок = значение * (1 + число таких ответов), счётчик в `SpendState.extensions`.
`AgentResult.crane` (`Crane`) говорит, какой кран сработал.

### waiting_owner в работнике
- `question` (`text` + токены отрезка): сначала диалог пишется в `<задание>/dialog.json`, `sandbox.stop()` (ошибка
  только в лог), `repo.flush()` (повтор без предела: wip должна быть на хабе), задание уходит в `parked` в
  `agent-state.json` (`job` обнуляется), слот свободен. Каталог задания и остановленный контейнер остаются.
- `answer` из `poll` дописывается в `dialog.json` и помечает запись `answered`; следующий `claim_once` берёт такую запись
  раньше нового `claim` (без второго `started`), поднимает контейнер (`resume()` у удержанного объекта, после рестарта
  исполнителя новый `start()`) и продолжает `AgentLoop.run(..., resume=dialog)` с того же места. Если рестарт случился
  после взятия ответа, `dialog.json` с ответом всё ещё на диске: продолжение пойдёт с него (сообщения после ответа
  не сохраняются, модель переделывает хвост по рабочей копии).
- `stop` для ждущего задания: открыть репозиторий, `abandon` (`agent/<id>` с частичным результатом), `stopped`, зачистка.
- `resume` с хаба (замена модели и/или замечания): запись `parked` и каталог зачищаются, диалог старой модели не
  переносится; задание возвращается через обычный `claim` с новой моделью. Новый агент получает task.md, журнал
  шагов (вехи `веха: ...` из `wip/<id>`, `AgentRepo.milestones()`), замечания из `payload.text` и список изменённых
  файлов. Замечания лежат в `job.params.remarks` (хаб кладёт их при `resume`) и приходят вместе с `claim`, поэтому
  гонка `claim`/`poll` их не теряет (60.5.6); при рестарте посреди задачи они попадут в промпт снова.
- `release` и `owner_wait_s` не обрабатываются (60.6/60.5.7).
- Тесты: `tests/unit/test_devlab_agent_owner.py` (хаб, настоящий репозиторий, `ScriptedChatModel`, `LocalSandbox` со
  шпионом): вопрос-ответ, рестарт до и после ответа, resume со сменой модели, stop в ожидании, step_done
  красный/зелёный, каждый кран.

## Модель и расход (60.5.6)
Код: `agent/spend.py`, `executor/routing.py`, `executor/agent_worker.py`.
- Какие задания берёт исполнитель: `claim` шлёт `ModelCatalog.names()` (модели живых шлюзов с адресом)
  вместо `[]`; каталог недоступен — `claim_once` ничего не берёт. После `claim` `_check_model` сверяет модель
  с каталогом и `allow_remote_models` из `.devlab.toml` (по умолчанию `false`): внешняя модель при запрете
  или модель, пропавшая из каталога, дают `failed` с причиной (владелец может `resume` с другой моделью).
- `MeteredChat` оборачивает модель задания: после каждого ответа `JobSpend.record` копит токены и $ в
  `agent-state.json` (`spend[<id задания>]`, `SpendState`), так что учёт переживает рестарт и отрезки
  между вопросами. База — `job.tokens`/`job.cost_usd` хаба на момент свежего `claim`; продолжение после
  ответа или рестарта берёт сохранённое состояние, а не снимок задания.
- Расход уходит в хаб дельтой с каждым сообщением (`step_done`, `question`, `done`, `failed`, `stopped`:
  `tokens`, `cost_usd`; `JobSpend.take_report`), хаб складывает его в `jobs.tokens/cost_usd`, их видит
  `devlab_status`. Запись `spend` убирается, когда задание закрыто (в `parked` остаётся).
- Потолок $ по умолчанию `AgentLimits.max_cost_usd` = 2.0 на всю задачу.
- Тихая трата: ответ `free` модели с `usage.cost > 0` — `PaidFreeModelError` (после учёта расхода), цикл
  отдаёт `ASKED` с краном `paid_free` и вопросом «Стоп-кран: бесплатная модель начала тратить деньги ...».
  Ответ с тратой отброшен, при «продолжай» запрос повторится и, если провайдер снова списывает, кран сработает
  снова; разумный ответ владельца — `resume` с другой моделью. OpenRouter отдаёт `usage.cost` по умолчанию;
  провайдер, который его не шлёт, считается по цене шлюза (у `free` — нулю, и трата не видна).
- Тесты: `tests/unit/test_devlab_agent_spend.py` (каталог с двумя шлюзами одной модели и отказ одного,
  запрет remote, $ через рестарт и вопрос, сквозной потолок, free с ненулевой стоимостью, гонка
  `claim`/`poll` для замечаний), `test_devlab_models.py` (поля `models`/`route`, фактическая стоимость, `url`).
