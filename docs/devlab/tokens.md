# Токены и роли (60.3.1, 2026-10-31; привязка к нодам 60.3.8)

- `devlab/hub/store.py` — SQLite `<data_dir>/hub.sqlite`, таблица `tokens`
  (name, role, hash, created, revoked).
- `devlab/hub/service.py` — действия ноды `issue_token name= role=` и `revoke_token name=`
  (`nodectl call devlab_hub issue_token name=... role=...`).
  Они объявлены в `actions`: `nodectl call` (proto `command`) принимает только действия из
  `actions`, `capabilities` не вызываемы. Кнопками в Telegram они не становятся: карточка службы
  в панели роя рисует только действия ноды. Токен в Telegram не выпускается и не показывается
  (решение владельца). Находка 2026-11-01: в v0.151.0 действия были только в `capabilities`,
  и `nodectl call devlab_hub issue_token` отвечал «нет такого действия» — исправлено в v0.151.1.
- `devlab/hub/http.py` — middleware проверяет `Authorization: Bearer`; нет токена, плохой или
  отозванный — 401. Маршрут `/health` помечен `@public` и открыт.

## Решения
- Токен `dlh_` + `secrets.token_urlsafe(32)`, в БД только sha256. Открытый вид возвращается один раз
  в ответе `issue_token` и нигде не хранится и не логируется.
- Имя токена уникально. Повторный выпуск под активным именем отклоняется, под отозванным
  заменяет строку.
- Ограничение по ролям: декоратор `@roles(...)` на обработчике. Без него маршрут доступен любой
  роли с действующим токеном; чужая роль получает 403. `/mcp`, `/git/`, `/api/` повесят свои роли так же.

## Доступ только для нод роя (60.3.8, решение владельца 2026-11-01)
Мастерской пользуются только компьютеры, на которых стоит нода роя. Любой компьютер tailnet
пользоваться ей не должен. Git остаётся на хабе, GitHub не используется.

- Имя токена = имя ноды роя. Любой запрос с токеном (роли client, executor, gateway) принимается,
  только если `request.remote` входит в адреса ноды с таким именем, иначе 403. Неверный токен
  по-прежнему 401. `/health` открыт.
- Список «нода → IP» строит `devlab/hub/nodes.py` (`SwarmNodes`): состояние своей ноды через
  `ServiceLink` на `settings.node.socket` (`peers[].endpoints`, имена разрешаются в IPv4) плюс адрес
  самого хаба. Кэш на `NODES_TTL_S` (30 с); если рой не ответил, остаётся последний известный
  список, а IP пира, который не разрешился, остаётся прежним.
- Хаб и клиент на одной машине (alfred): запрос идёт на tailscale-IP alfred и приходит с него же, а
  хаб слушает только этот адрес. Адрес хаба всегда входит в список под именем его ноды
  (`settings.node.id` или hostname).
- Выпуск по рою: `POST /connect` (публичный маршрут, `devlab/hub/connect_http.py`).
  Нужен заголовок `X-Swarm-Token` с общим `[swarm].token` (`hmac.compare_digest`), поэтому токен
  получает установленная нода, а не любой процесс на машине. Ноду хаб определяет по
  `request.remote`: адрес из tailnet подделать нельзя. Выпускается токен роли client на имя ноды.
  Повторный `connect` с той же ноды перевыпускает токен: старый перестаёт работать (ожидаемо,
  токен на ноде один). Если у ноды уже есть активный токен executor или gateway, `connect`
  отвечает 400 и ничего не меняет: имя токена уникально, поэтому одна нода держит один токен.
- Клиент: `nodectl devlab connect` (`devlab/connect.py`) ходит на
  `http://<[devlab_hub].hub_node>:<port>` (по умолчанию alfred), пишет токен в
  `~/.config/sa-home-bot/devlab-token` (права 600) и, если `claude` есть в PATH, выполняет
  `claude mcp add --scope user --transport http devlab <url>/mcp --header "Authorization: Bearer <токен>"`.
  Токен в stdout не печатается; без `claude` печатается команда с `$(cat <файл>)`.
- Ручной `issue_token` остаётся для executor и gateway. Имя обязано быть нодой роя, пока список нод
  известен (больше одной ноды); если известна только нода хаба, проверка пропускается.
- Миграция: выпущенный токен `alfred` (client) совпадает с нодой и работает без изменений.
  Токены с не нодовыми именами перестанут проходить: перевыпустить на имя ноды.

## Известное ограничение роя (2026-11-01)
`src` в конверте proto ставит клиент, нода его не штампует, а обработчик службы конверта не видит
(`ServiceHandler.run_command(action, args)`). Поэтому надёжно узнать ноду-отправителя из
proto-запроса нельзя, и выпуск токена сделан по HTTP с проверкой адреса источника.
