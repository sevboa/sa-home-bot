# Эпик (Этап Б1–Б2, 2026-11-24)

План: `plans/devlab-task-sizes-epics.md`, этап Б. Эпик — упорядоченный список задач одной фичи,
которые хаб выполняет строго по очереди в общей ветке `epic/<id>`. Код: `devlab/hub/epics.py`
(`HubEpics`, `store.epics`), проверка плана `devlab/hub/epic_plan.py`, git-операции
`devlab/hub/repos.py` (`create_branch`, `merge_branch`, `tests_listing`).

## MCP
- `devlab_epic_submit(project, base_branch, tasks)`: `tasks` — объекты `{title, task, model, profile,
  paths, depends_on}` (`profile` по умолчанию `executor`, `depends_on` — индексы прежних задач с нуля).
  Ответ `{epic, warnings}`; `warnings` — модели, которых нет в каталоге.
- `devlab_epic(id)`: статус эпика (`running`, `waiting_owner`, `done`), `question`, `current` (индекс
  первой незавершённой задачи) и по каждой задаче отметка: `job_id`, `job_status`, `outcome`
  (`done` / `failed` / `stopped` / пусто), `commit`, `marked` (время), `failures`. Эпик виден только
  своему клиенту.

## Как идёт эпик
- Постановка создаёт ветку `epic/<id>` от `base_branch` прямо в bare-репозитории хаба
  (`update-ref`, хук `pre-receive` не участвует; исполнители в `epic/` не пушат) и ставит в очередь
  только первое задание. Остальные создаются по одному, когда предыдущее влито: так следующее
  заведомо не обгонит слияние, а «строго по очереди» не зависит от `depends_on` в очереди.
- Задание эпика — обычное `agent`-задание с `base_branch = epic/<id>` и `params.epic`,
  `params.epic_index`, `params.paths`. `_valid_base_branch` принимает `epic/<имя>`. Исполнитель
  забирает базу как любую ветку (зеркало тянет все `refs/heads/*`), менять исполнителя не пришлось.
- `HubQueue.observers`: после каждого `post_from_executor` и `post_from_client` вызывается
  `HubEpics.sync(job_id)`; для заданий вне эпиков это один SELECT. Ошибка наблюдателя пишется в лог и
  не ломает ответ исполнителю.
- `done`: `agent/<job>` вливается в `epic/<id>`: fast-forward, а если ветка эпика ушла вперёд,
  merge-коммит (`git merge-tree --write-tree` + `commit-tree`, без рабочей копии). Конфликт или
  отсутствие ветки: эпик `waiting_owner`, задача не отмечена, следующая не стартует. В отметку идёт
  новая голова ветки эпика.
- Провал: `failed` в первый раз хаб возвращает в очередь сам (`resume` с пометкой); второй раз подряд
  (`EPIC_MAX_TASK_FAILURES` = 2) эпик уходит в `waiting_owner`, в ящик клиента падает
  `epic_waiting` с текстом вопроса на последнее задание. `stopped` сразу ждёт владельца. Следующие
  задачи не стартуют. Когда владелец вернёт задание `devlab_resume`, эпик снова `running`,
  счётчик провалов задачи обнуляется.
- Рестарт хаба: `run_hub` зовёт `resume_all()`: каждый незавершённый эпик проходит с последней отметки
  (недолитое `done` вливается, следующее задание заводится), повторный вызов ничего не дублирует.
  Рестарт исполнителя покрыт обычным `requeue` очереди.

## Проверка плана кодом (Б2)
`check_plan(tasks, existing_tests)` возвращает список причин, `devlab_epic_submit` при непустом
отказывает `HubError` со всем списком сразу:
- `task` длиннее `TASK_LONG_CHARS`;
- `depends_on`: индекс вне плана, ссылка вперёд, цикл (включая на себя);
- `paths` пуст, путь пустой, абсолютный или с `..`;
- тест-файл (`tests/**/test_*.py`) с одним basename в двух задачах плана;
- тест-файл по новому пути, чей basename уже есть в `tests/` базы под другим путём (дубли basename
  ломают импорт pytest). Список берётся `git ls-tree` по базовой ветке; правка уже существующего пути
  разрешена.
Параллельных задач нет, поэтому конфликтов файлов между задачами проверка не ищет.
