# Эпик (Этап Б1–Б2, 2026-11-24)

План: `plans/devlab-task-sizes-epics.md`, этап Б. Эпик — упорядоченный список задач одной фичи,
которые хаб выполняет строго по очереди в общей ветке `epic/<id>`. Код: `devlab/hub/epics.py`
(`HubEpics`, `store.epics`), проверка плана `devlab/hub/epic_plan.py`, git-операции
`devlab/hub/repos.py` (`create_branch`, `merge_branch`, `tests_listing`).

## MCP
- `devlab_epic_submit(project, base_branch, tasks)`: `tasks` — объекты `{title, task, model, profile,
  paths, depends_on}` (`profile` по умолчанию `executor`, `depends_on` — индексы прежних задач с нуля).
  Ответ `{epic, warnings}`; `warnings` — модели, которых нет в каталоге.
- `devlab_epic(id)`: статус эпика (`running`, `waiting_owner`, `done`), `question`, `current` (индекс
  первой незавершённой задачи) и по каждой задаче отметка: `job_id`, `job_status`, `outcome`
  (`done` / `failed` / `stopped` / пусто), `commit`, `marked` (время), `failures`. Эпик виден только
  своему клиенту.

## Как идёт эпик
- Постановка создаёт ветку `epic/<id>` от `base_branch` прямо в bare-репозитории хаба
  (`update-ref`, хук `pre-receive` не участвует; исполнители в `epic/` не пушат) и ставит в очередь
  только первое задание. Остальные создаются по одному, когда предыдущее влито: так следующее
  заведомо не обгонит слияние, а «строго по очереди» не зависит от `depends_on` в очереди.
- Задание эпика — обычное `agent`-задание с `base_branch = epic/<id>` и `params.epic`,
  `params.epic_index`, `params.paths`. `_valid_base_branch` принимает `epic/<имя>`. Исполнитель
  забирает базу как любую ветку (зеркало тянет все `refs/heads/*`), менять исполнителя не пришлось.
- `HubQueue.observers`: после каждого `post_from_executor` и `post_from_client` вызывается
  `HubEpics.sync(job_id)`; для заданий вне эпиков это один SELECT. Ошибка наблюдателя пишется в лог и
  не ломает ответ исполнителю.
- `done`: `agent/<job>` вливается в `epic/<id>`: fast-forward, а если ветка эпика ушла вперёд,
  merge-коммит (`git merge-tree --write-tree` + `commit-tree`, без рабочей копии). Конфликт или
  отсутствие ветки: эпик `waiting_owner`, задача не отмечена, следующая не стартует. В отметку идёт
  новая голова ветки эпика.
- Провал: `failed` в первый раз хаб возвращает в очередь сам (`resume` с пометкой); второй раз подряд
  (`EPIC_MAX_TASK_FAILURES` = 2) эпик уходит в `waiting_owner`, в ящик клиента падает
  `epic_waiting` с текстом вопроса на последнее задание. `stopped` сразу ждёт владельца. Следующие
  задачи не стартуют. Когда владелец вернёт задание `devlab_resume`, эпик снова `running`,
  счётчик провалов задачи обнуляется.
- Рестарт хаба: `run_hub` зовёт `resume_all()`: каждый незавершённый эпик проходит с последней отметки
  (недолитое `done` вливается, следующее задание заводится), повторный вызов ничего не дублирует.
  Рестарт исполнителя покрыт обычным `requeue` очереди.

## Проверка плана кодом (Б2)
`check_plan(tasks, existing_tests)` возвращает список причин, `devlab_epic_submit` при непустом
отказывает `HubError` со всем списком сразу:
- `task` длиннее `TASK_LONG_CHARS`;
- `depends_on`: индекс вне плана, ссылка вперёд, цикл (включая на себя);
- `paths` пуст, путь пустой, абсолютный или с `..`;
- тест-файл (`tests/**/test_*.py`) с одним basename в двух задачах плана;
- тест-файл по новому пути, чей basename уже есть в `tests/` базы под другим путём (дубли basename
  ломают импорт pytest). Список берётся `git ls-tree` по базовой ветке; правка уже существующего пути
  разрешена.
Параллельных задач нет, поэтому конфликтов файлов между задачами проверка не ищет.

## Пропуск и закрытие тест-файлов (Б3, 2026-11-24)
Хаб при создании задания эпика (`HubEpics._enqueue`, функции `later_test_files` и
`tester_locked_files` в `epic_plan.py`) кладёт в params два списка. Вне эпика их нет, поведение прежнее.
- `params.epic_skip_tests`: тест-файлы (`tests/**/test_*.py`) задач, которые идут позже текущей, кроме
  файлов, чьи paths есть у текущей или более ранних задач. `FinishGuard.verify_green` добавляет к
  полному прогону `--ignore=<путь>` только для файлов, которые есть в рабочей копии. `run_tests`
  без paths не принимает, так что полный набор запускает только finish.
- `params.epic_locked`: все paths задач профиля `tester`, стоящих раньше текущей (минус paths самой
  текущей). Для задачи профиля `tester` список пуст: свои файлы тестер править может.
  Исполнитель кладёт список в `AgentSpec.locked_paths`; `ToolBox._check_writable` и скрипт Code Mode
  (`_CONFIG["locked"]`) отвечают «файл тестера, не меняй; не согласен — ask_owner». Чтение открыто.

## Тестер до кода и архитектор (Б4, 2026-11-24)
- Флаг профиля `expect_red` (`DevlabProfileConfig` → `AgentSpec.expect_red`). Для задания с ним
  `FinishGuard.verify_green` считает «своими» тест-файлы, которые задание создало или изменило
  (`changed_test_files`). Они могут быть красными: полный прогон идёт с `--ignore` на них, остальной
  набор обязан быть зелёным как обычно (`epic_skip_tests` и прощение красных на базе работают).
- Свои тест-файлы обязаны собираться: `pytest --collect-only -q <файлы>` без ошибок. Правило для
  моделей: на уровне модуля импортируется только то, что уже есть в репозитории, а ещё не написанный
  код импортируется внутри тела тестовой функции (`from пакет import новое`). Тогда без кода тест
  падает красным, а не ломает сбор. Текст отказа повторяет это правило. `importorskip` не берём:
  он превращает красный в пропуск, и разработчику нечего озеленять. `verify_step` у таких заданий
  свои файлы только собирает, а не требует зелёными.
- После зелёной остальной части хранитель прогоняет свои файлы отдельно и кладёт упавшие id в
  `red_tests`. `AgentLoop` дописывает в summary done блок: строка `protocol.RED_TESTS_MARKER` и
  строки `- <id>`.
- Хаб в `_enqueue` для не-тестерской задачи собирает красные тесты предыдущих задач профиля
  `tester` (последнее `done` по их job, `parse_red_tests`), кладёт в `params.epic_red_tests` и
  дописывает в текст задания блок «Красные тесты тестера» (`red_tests_note`).
- Профиль `tester` в конфиге исполнителя: `expect_red = true`. Профилю `architect` новых полей не
  нужно: `write_prefixes` (например `plans/`) ограничивает запись, `allow_no_changes = false`
  требует файла результата в `paths`.
- 2026-11-24: страж finish (`FinishGuard.verify`) без строки «Менять можно только» ищет правки в
  `write_prefixes` профиля, а не в `diff_prefixes` проекта. До этого архитектор (`ynm45m`) записал
  `plans/epic-park.json`, но finish отклонялся «нет изменений в src/, tests/». Тест:
  `test_write_prefixes_scope_finish`.

## Как поставить фичу эпиком (2026-11-25)
1. **Архитектору — задание.** `devlab_submit` с `profile=architect`, высоким `priority`,
   `base_branch=base/<имя>`. Фича описана результатом и критерием; в конце путь к файлу плана
   `plans/<имя>.json`. Роль архитектора и вводная лежат файлами на исполнителе
   (`devlab-roles/architect.md`, `intro_file` профиля), не в репозитории. Профиль пишет только в
   `plans/` (`write_prefixes`); страж finish проверяет правки там (с v0.233.1).
2. **Управляющий принимает план.** JSON-список `{title, task, profile, paths, depends_on}`. Сначала
   задачи `tester`: каждому свой НОВЫЙ тест-файл, имя файла обязательно в тексте задачи (`paths`
   агенту не показываются и исполнителем не принуждаются). Потом `executor-code`. Задача пишется от
   результата: поведение, какой тест станет зелёным, образец в коде, файлы; реализацию и новые имена
   выбирает исполнитель. Ориентир ~1000 знаков, больше 1500 хаб отклонит (`TASK_LONG_CHARS`).
   `depends_on` — индексы прежних задач с нуля. План проверяется кодом (`check_plan` в
   `devlab/hub/epic_plan.py`), его можно прогнать локально до отправки.
3. **Постановка.** `devlab_epic_submit(project, base_branch, tasks)`, у каждой задачи `model`.
   Задачи идут строго по очереди в ветке `epic/<id>`. Тестер (`expect_red`) оставляет красные, но
   собираемые тесты; хаб передаёт разработчику список красных (`epic_red_tests`). Провал останавливает
   эпик, вопрос приходит в ящик.
4. **Подводные камни.**
   - Задачи эпика встают в очередь с `priority` 0 (параметра приоритета у эпика нет) и ждут чужую
     очередь с более высоким приоритетом.
   - Приоритет поставленного задания не меняется: только `stop` и повторная постановка.
   - Рестарт исполнителя без `--force` ждёт, пока опустеет вся очередь хаба (`BusyTracker.busy`
     учитывает `_queued`). Лечит будущая парковка (эпик `epic-park`).
5. **Профили исполнителя.** `tester` — тестер эпика (тесты до кода, `expect_red`); `reviewer` —
   проверка готового диффа и вердикт; `architect` — план; `executor-code` — разработка; `docs` —
   только `docs/`.

## Не сделано
Профили `tester` и `architect` заведены в конфиге исполнителя. Живой прогон эпика с тестером начат
2026-11-24 (эпик `m4tvxx`). `paths` как таковые исполнителем не принуждаются (кроме закрытых

## Эпик в Telegram и остановка (Б5, 2026-11-24)
- Статус `stopped`: владелец остановил эпик. `HubEpics.stop(id)` ставит его и останавливает текущее
  задание (если оно в очереди, идёт или ждёт ответа); `_advance` и `resume_all` остановленный эпик не
  трогают. `HubEpics.resume(id)` возвращает в очередь текущее задание (если оно `failed`/`stopped`),
  обнуляет счётчик провалов задачи, ставит `running` и двигает эпик дальше; у завершённого эпика обе
  операции отказывают. MCP: `devlab_epic_resume`, `devlab_epic_stop` (только свой эпик).
- Действие хаба `owner_epic_post` (`id`, `kind` = `resume`|`stop`) для бота; `owner_jobs` теперь
  отдаёт `epics` (эпики `running`/`waiting_owner`: `id`, `title` = название первой задачи плана,
  `status`, `question`, `done`, `total`, `current_title`, `current_job`), а у заданий эпика — `epic_total`
  (`HubEpics.task_totals`). Названия у эпика в схеме нет, поэтому показывается заголовок первой задачи.
- /jobs: секция «🧩 Эпики» на первой странице: `id`, название, «сделано/всего», текущая задача,
  состояние («идёт» / «❓ ждёт владельца»). Строка задания эпика: «· эпик N/M»; карточка: «Эпик: id,
  задача N из M».
- Оповещение: `epic_waiting` идёт тем же путём, что `question` (`DevlabNotifier`, все админы),
  с кнопками «Продолжить эпик» (`dl:epr:<эпик>`) и «Остановить эпик» (`dl:eps:<эпик>`, подтверждение
  `dl:epsc`, отмена `dl:epc`). Аргумент кнопок — id эпика, а не задания. Сообщение без `payload.epic`
  не оповещается. `nodectl devlab watch` `epic_waiting` не отбрасывает (по умолчанию пропускаются
  только `started` и `step_done`), менять не пришлось.
- Живьём не проверено: кнопки и секция в настоящем Telegram, остановка эпика на реальном исполнителе.
